## 2026-09-12 — 4.9 and 4.10 merged (v2.0.12 / v2.0.13); two parallel-worktree gotchas worth keeping

Both merged after APPROVE; details in `03-backlog.md`. Two environment lessons from running four worktrees at once, recorded so the next parallel batch doesn't relearn them:

1. **`reuseExistingServer` + a shared port = testing the wrong build.** Playwright reuses whatever answers on its port. With several worktrees each starting `next dev` on ad-hoc ports, a leftover server from another worktree (or a zombie that listens but never answers) gets reused silently — the PDP specs "failed" against a dead server and the cart spec rendered the *old* cart page from a different branch. Rule: before any Playwright run pick a port that `netstat -ano | findstr :31xx` shows as NOT listening; after the run confirm it is free again. `PLAYWRIGHT_PORT` (added in 4.9/4.10) makes this possible; it doesn't make it automatic.
2. **Vitest was crawling `.claude/worktrees/**`.** Every worktree copy's Playwright specs were picked up as Vitest files (28 "failed files", 0 failed tests). `vitest.config.ts` now excludes `.claude/**`. Real count on `redesign` after 4.10: 11 files / 115 tests.

Also: hardcoded catalog SKUs in e2e fixtures do not survive a shared dev database — parallel runs and manual sessions drain stock. The cart spec now resolves a stocked variant at run time; future specs should do the same (`findStockedVariant` in `tests/e2e/public-cart.spec.ts` is the pattern).

## 2026-09-10 — Incident: e2e tests wrote fixture data into production; fixed with a hard guard

Found while building 4.2 (Register): `tests/e2e/auth-login.spec.ts`, merged as part of 4.1, loaded only plain `.env` (production) — it never loaded `.env.redesign` at all. Every run of that suite (the verifier's live run during 4.1, plus debugging while building 4.2) wrote its Prisma-seeded fixture users straight into **production**, not the isolated `redesign` Neon branch.

**Confirmed and remediated same-day**: independently queried production and confirmed 7 synthetic rows (`name: null`, `email: null`, `role: CUSTOMER`) matching the exact phones/timestamps from these test runs, with zero related Orders/SavedAddresses/Carts/etc. One unrelated real customer found in the same query window (a genuine registration, real name, unrelated phone) was explicitly left untouched. With the user's explicit approval, the 7 rows were deleted by exact id (not a broad match), after confirming no `Order` rows existed for any of them (`Order.user` is `onDelete: Restrict` in the schema — deletion would have failed loudly rather than silently orphaning a real order, which held here).

**Root cause**: `@prisma/client`'s own import auto-loads the project's plain `.env` as a side effect before any of a test file's own code runs (ESM import hoisting executes all imports before other top-level code, regardless of textual order) — so a test file has to explicitly `override: true` a `.env.redesign` load to beat it, not just load `.env.redesign` "first" in source order.

**Fix, now the standard pattern for every e2e spec that touches the DB**: `tests/e2e/test-env.ts` exports `loadRedesignTestEnv()` — loads `.env.redesign` with `override: true` then `.env`, and then hard-aborts (throws before any Prisma client is constructed) if the resulting `DATABASE_URL`'s *host* matches production's host (parsed directly from `.env`, never trusting `process.env`). This catches not just the original bug but the deeper failure mode: silent fallback to production if `.env.redesign` is ever missing on whatever machine runs the suite. Only hostnames are ever compared or logged, never full connection strings, per this project's standing rule against printing secret values. Verified: passes under the real environment, correctly throws when `.env.redesign` is simulated missing, and a full 23-test Playwright run still passes with fixtures confirmed landing in `redesign` (not production) afterward. Both `auth-login.spec.ts` and `auth-register.spec.ts` now call this shared helper instead of duplicating env-loading logic — any future e2e spec that seeds/queries the DB directly should too.

## 2026-09-09 — Gap-analysis additions

Found during a PM self-review of the plan; folded in per user approval.

- **Database branching**: every new feature we've approved (wishlist, reviews, notification center, `AdminActionLog`) needs Prisma schema changes. Decision: mirror the git branch with a Neon database branch — Neon supports free copy-on-write branching (confirmed 2026-09-09: up to 10 branches/project on the free tier, ~$1.50/branch-month beyond that). All `redesign`-phase migrations run against a `redesign` Neon branch, never the production database. **Not** using `.env.local` for this — that file isn't tied to the git branch (it's just a file on disk) and would silently keep pointing local `main` work at the redesign database too. Instead: a separate `.env.redesign` (gitignored, template committed as `.env.redesign.example`) loaded only via dedicated npm scripts — `dev:redesign`, `db:push:redesign`, `db:migrate:redesign`, `db:studio:redesign` (via `dotenv-cli`, added as a devDependency). Regular `npm run dev`/`db:push`/etc. are untouched and still point at production via `.env`. **Manual step required**: this session has no Neon API credentials, so the branch itself must be created by the user — in the Neon console, or `neonctl branches create --name redesign`; then fill `.env.redesign` from that branch's connection details (pooled → `DATABASE_URL`, direct/unpooled → `DIRECT_URL`). At cutover, either promote the branch to primary or replay its migration history onto production via `prisma migrate deploy`.
- **Existing `DIRECT_URL` note** (found while checking env config, not urgent): production's `.env` currently has `DATABASE_URL` and `DIRECT_URL` set to the same pooled (`-pooler`) connection string. Prisma's documented pattern for Neon is `DIRECT_URL` = the unpooled endpoint (no `-pooler`), used only for migrations. It's likely working today because Neon's pooler generally tolerates DDL, but it's not the supported configuration — worth fixing when convenient, not a redesign blocker. Get the new `redesign` branch's connection strings right from the start (see above) rather than carrying this forward.
- **Preview/checkpoint visibility**: since `git.deploymentEnabled` blocks automatic Vercel builds for `redesign`, define explicit moments where a preview is worth the (small) cost: end of Phase 1's design demo, end of each Phase 4 surface, and just before any merge to `main`. Rollback if a merged surface breaks in production: `git revert` the merge commit on `main` (fast, since Vercel redeploys `main` automatically on push) — a full feature-flag system is unwarranted overhead for a single-tenant app at this scale given the branch model already keeps unfinished work fully out of production until a deliberate merge.

## 2026-09-09 — Branching & versioning

- **Branching**: all redesign work happens off a long-lived `redesign` branch, created from `main` at the tag `pre-redesign-baseline`. `main` stays production and keeps shipping urgent fixes independently. Every `ui-implementer` task branches off `redesign` (not `main`) and PRs back into `redesign`. Periodically merge `main` → `redesign` to absorb production fixes and avoid a painful merge at the end. `redesign` only merges into `main` when a surface (or the whole redesign) is verified ready to ship — no direct-to-`main` merges from task branches.
- **Vercel deployment cost**: `vercel.json#git.deploymentEnabled` explicitly disables auto-deployment for `redesign` and every `redesign/*` task branch (minimatch pattern), while leaving `main` enabled — confirmed via Vercel's own docs (`git.deploymentEnabled`, see https://vercel.com/docs/project-configuration/git-configuration#git.deploymentenabled). Vercel evaluates the `vercel.json` in the commit being pushed, so this takes effect the moment it's committed to `redesign` and is inherited by every task branch created from it — no push, PR, or task-branch build will consume Vercel build minutes until we deliberately flip it back. To preview the redesign before merging to `main`, change the `"redesign": false` entry to `true` (or remove it) temporarily, or just deploy locally / preview via `vercel --local-config` / `npm run build` locally instead of relying on a hosted preview.
- **Versioning**: `package.json#version` is the single source of truth (no other file references it). `main`'s `package.json` still reads `0.1.0`, but the live production app is functionally the platform's first real version — so the redesign is versioned as the product's **v2**, not folded into a belated "1.0". The `redesign` branch starts flat at **`2.0.0`** (no prerelease suffix, per user 2026-09-09) and auto-increments from there:
  - **`npm run version:task`** — patch bump (`2.0.0` → `2.0.1`), run once a task is implemented, verified (APPROVE from `ui-verifier`), and merged into `redesign`. "Automatic" here means: a standardized command the PM runs at that exact checkpoint every time, not a git hook — there's no CI pipeline wired to this repo to trigger it unprompted.
  - **`npm run version:feature`** — minor bump (`2.x.y` → `2.(x+1).0`), run once a *major feature* ships — a full surface rebuild (e.g. all of Phase 4's Auth screens) or an approved item from `02-proposals.md` (e.g. wishlist, reviews). Not every `03-backlog.md` phase warrants this — infrastructure-only phases (e.g. Phase 2's baseline measurement) don't ship a user-facing feature, so they don't get a minor bump on their own.
  - Both use `npm version`, which updates `package.json` + `package-lock.json`, commits, and tags in one step.
  - When the redesign merges to `main`, whatever `2.x.y` it has reached at that point ships as-is — no renormalizing back to a round number.
  - (Optional follow-up, not done yet: formally re-tagging current `main` as `1.0.0` to make the v1/v2 framing explicit in the version history — ask before touching `main`'s version.)
- A tag `pre-redesign-baseline` marks the exact `main` commit the redesign diverged from, for reference/rollback.
