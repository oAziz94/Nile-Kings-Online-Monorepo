# Partner — Products (stock list + variant detail)

Route(s): `app/(partner)/partner/products/page.tsx` (list, client, wrapped in `React.Suspense`) and `app/(partner)/partner/products/[id]/page.tsx` (per-product variant/stock editor, client). Covered together — the detail page is a straightforward drill-down of the list with no independent identity, sharing the same API and inventory model.
Key files: `app/api/partner/inventory/route.ts` (GET list/detail, PATCH stock update), `lib/admin/variant-sort.ts` (`sortVariants`), `lib/size-display.ts` (`getDisplaySizeLabel`, `isKidsCategory`), `hooks/use-list-url-state.ts`, `hooks/use-row-scroll-restore.ts`, `components/dashboard/{page-header,panel-card,kpi-card,empty-state,pagination,search-input,table-scroll}.tsx`, `components/shared/product-image-preview.tsx`

## Business requirements
- **Goal/KPI**: this is the partner's authoritative record of what they physically have on hand — directly drives sellable-stock accuracy (prevents overselling once `sellable = available − reserved` hits 0) and reduces admin/support load by letting each partner self-serve their own stock counts instead of relaying updates to the admin team.
- **Trust/credibility signals**: "قابل للبيع" (sellable) is always shown as a badge colored by whether it's `> 0` (default) or `0` (destructive/red) — an unambiguous at-a-glance signal of what's actually orderable. The list page's badge "تعديل المخزون فقط" (stock editing only) and description "نفس جدول المنتجات في لوحة الإدارة مع صلاحية تعديل مخزون المتغيرات فقط" (same product table as admin, but limited to editing variant stock only) sets partner expectations that this is a read-mostly catalog view, not a product-management tool (no pricing, images, or listing changes here).
- **Friction points**: the detail page's stock input requires the partner to know the exact new total (`stockAvailable`), not a "receive N units" delta — there's no "+N" quick-adjust affordance; every edit is a whole-value overwrite validated only against not going below `stockReserved`. The list's "المتاح/المحجوز/قابل للبيع" are pre-aggregated sums across all variants, which can mask a single critically-low variant inside an otherwise healthy-looking product row (only the detail page's KPI cards surface a per-variant "≤3 units" low-stock count).
- **Compliance/legal**: every manual stock edit writes an immutable `InventoryLedger` row (`reason: MANUAL_ADJUSTMENT`, delta, "Partner dashboard stock edit" note) — an audit trail requirement, not just a UI nicety; the rebuild must keep triggering this write on every successful PATCH even if the UI around it changes.
- **Modern-look rationale**: none specific.

## Elements & behavior

### List (`/partner/products`)
- [ ] **Role/ownership gate**: `requireInventoryPartner()` = `requirePartner()` + partner row must have `partnerType` of `"AGENT"` or `"DISTRIBUTOR"` (i.e. effectively just "any active partner" — both types see this same list, unlike most other partner screens).
- [ ] `PageHeader` — title "المنتجات"; description + `StatusBadge` "تعديل المخزون فقط" as above; "تحديث" refresh button.
- [ ] **Data scope**: shows every `active: true` product in the **entire catalog** (not scoped to a partner-owned subset of products — every partner sees every active product), but each variant's stock numbers are looked up from that specific partner's own `PartnerInventory` row (`partnerInventories: { where: { partnerId: user.partnerId } }`); a variant with no `PartnerInventory` row for this partner renders as `0/0/0` (available/reserved/sellable) rather than being hidden.
- [ ] **Search** (`SearchInput`, debounced): matches product name, slug, category name, or any variant's SKU/name/color name (server-side `OR`, case-insensitive).
- [ ] **Table columns**: الصورة (thumbnail via `ProductImagePreview`, or a package-icon placeholder box) · الاسم · الفئة (category name) · السعر (first variant's `pricePiastres`, EGP) · المتغيرات (variant count, e.g. "٣ متغير") · المتاح (sum of `stockAvailable` across variants) · المحجوز (sum of `stockReserved`) · قابل للبيع (sum of `sellable`, badge colored by `>0`) · إجراءات ("تعديل المخزون" link → `/partner/products/[id]`).
- [ ] **Row scroll-restore** on clicking into a product (same `sessionStorage` pattern as routed-orders).
- [ ] **Pagination**: `PaginationBar`, same page-size options as other lists (10/20/50, default 20).

### Detail (`/partner/products/[id]`)
- [ ] Fetches via the *same* `/api/partner/inventory` GET endpoint with `productId` + `limit=1` (not a dedicated single-product endpoint) — takes `products[0]` from the response.
- [ ] `PageHeader` — title = product name; description = `"{category} · تعديل مخزون متغيرات هذا المنتج فقط."`; `StatusBadge` "متغيرات المنتج"; actions = "رجوع للمنتجات" (`router.back()`) and "تحديث" (refetch).
- [ ] **KPI row** (3 cards): "عدد المتغيرات" (variant count, hint "مقاسات وألوان"); "إجمالي المتاح" (sum of `stockAvailable`, hint = sum of `stockReserved` + "محجوز"); "مخزون منخفض" (count of variants with `sellable <= 3`, gold accent if `>0` else emerald) — this ≤3 threshold is hardcoded and only surfaced here, not on the list page.
- [ ] **Variants table**, one row per variant, columns: الصورة (variant image, falling back to product image, falling back to a dashed placeholder box) · المتغير (color swatch dot if `colorHex` set + display name via `getDisplaySizeLabel(variant.name, forKidsSizes)` — size-label formatting differs for kids' categories, detected via `isKidsCategory(category.slug)` — combined with `colorName` as "`{size}` · `{color}`") · SKU (monospace) · السعر · **المتاح** (editable `<Input>`, the *only* editable field — highlighted with a gold border/background while the draft value differs from the saved value) · المحجوز (read-only) · قابل للبيع (badge, same `>0` coloring as the list) · آخر تحديث (`updatedAt` of the `PartnerInventory` row, formatted or "لم يسجل" if never set) · **الطلبات المحجوزة** (order-verification link, see below) · حفظ (per-row save button).
- [ ] **Order-verification link per variant** ("عرض الطلبات" button, `ClipboardList` icon) — opens `/partner/routed-orders?variantId={variant.id}&status=CREATED,CONFIRMED,PROCESSING` in a **new tab** (`target="_blank" rel="noopener noreferrer"`). Purpose: let warehouse staff cross-check this variant's physical stock count against every order that still owes it to a customer (not yet shipped). See `routed-orders.md` for the receiving screen's behavior. This link is present for every variant row regardless of partner type or current stock level (not conditional on low stock).
- [ ] **Per-row stock save**: editing the "المتاح" input tracks a local draft keyed by `variant.id`; save button is `variant="default"` (filled) only while dirty, else outline, and disabled entirely while not dirty or while that specific row is saving (`savingVariantId` tracks one in-flight save at a time, but nothing blocks starting a save on a *different* row concurrently). Client-side validation before the request: must be a non-negative integer (`Number.isInteger(...) && >= 0`); must be `>= stockReserved` (blocked client-side with a toast **and** re-validated server-side with the identical rule). On success, updates that row's `stockAvailable`, `stockReserved` (in case it changed concurrently server-side), `sellable`, and `updatedAt` from the server's authoritative response, and clears that row's draft.
- [ ] **PATCH `/api/partner/inventory`** (stock update, shared by this per-row save): body `{ variantId, stockAvailable }`. Server re-derives `stockReserved` from the *current* `PartnerInventory` row (race-safe against the client's possibly-stale view) and rejects if the new `stockAvailable` would be less than that. Upserts the `PartnerInventory` row (creates one with `stockReserved: 0` if none existed yet for this partner+variant). Always writes an `InventoryLedger` row with `quantityAvailableDelta = stockAvailable - previousStockAvailable` (0 if no prior row existed) and `quantityReservedDelta: 0`.

## States
- [ ] Empty state (list) — `EmptyState`: "لا توجد نتائج للبحث" if searching, else "لا توجد منتجات متاحة".
- [ ] Empty state (detail, no variants) — `EmptyState` inside the variants panel: "لا توجد متغيرات لهذا المنتج".
- [ ] Empty state (detail, product not found / wrong id) — full-page `EmptyState`: "المنتج غير موجود" / "ارجع إلى قائمة المنتجات واختر منتجاً آخر."
- [ ] Loading state (list) — centered spinner + "جاري تحميل المنتجات" on first load; subsequent refetches keep the table visible with a "جاري التحديث…" line + reduced opacity, same pattern as routed-orders.
- [ ] Loading state (detail) — centered spinner + "جاري تحميل المتغيرات" (blocks the entire page, not per-section, unlike the list's inline refetch indicator).
- [ ] Error state — load failures: destructive toast only (list: "فشل تحميل المنتجات" / detail: "فشل تحميل المتغيرات"), table/page otherwise left as-is (or empty on first load). Save failures (stock PATCH): destructive toast with the server's message when available (e.g. the "less than reserved" message), draft input value is preserved (not reset) so the partner can correct and retry.
- [ ] Permission-restricted state — any authenticated partner without an active `Partner` row of type AGENT or DISTRIBUTOR gets a 403 from the API; since both real partner types pass this check, in practice this state is unreachable from the normal partner login flow (it would only trigger for a malformed/edge-case partner record) and has no dedicated UI treatment beyond the generic destructive-toast load-failure path.

## Edge cases
- [ ] Stock input left at a value **below** the current `stockReserved` — blocked with an inline-toast message quoting the exact reserved count (`لا يمكن أن يكون المخزون أقل من المحجوز (${reserved})`), both client- and server-side.
- [ ] Two browser tabs editing the same variant's stock concurrently — server always re-reads `stockReserved` fresh at save time (not trusting a client-supplied value), so a stale client can still get a consistent reject/accept decision, but the *displayed* `stockReserved` in a stale tab won't reflect another tab's reservation changes until that tab's own next successful save or manual refresh.
- [ ] A variant with **no** `PartnerInventory` row yet for this partner (never stocked) — renders `0` available / `0` reserved / `0` sellable everywhere (list aggregates and detail row alike), not a distinct "not stocked" state; the very first stock save for that variant creates the row via upsert.
- [ ] `productId` query param on the detail page's fetch uses `limit: "1"` against the same paginated list endpoint rather than a dedicated by-id lookup — if that product isn't `active: true`, it will not be found even by direct URL (falls through to the "not found" empty state) — i.e. **inactive products are not reachable via this detail screen at all**, only via the list (which itself only lists `active: true` products).
- [ ] Kids-category size-label formatting (`getDisplaySizeLabel` + `isKidsCategory`) changes how the "المتغير" column renders purely based on the product's `category.slug` — a rebuild that doesn't port `lib/size-display.ts` behavior will show wrong/adult-style size labels for kids products on this screen specifically (also affects other size-label surfaces elsewhere in the app, not unique to this screen, but easy to miss here since it's not obviously flagged in the UI).
- [ ] Clicking "عرض الطلبات" for a variant with zero open orders — lands on `/partner/routed-orders` pre-filtered to an empty result set (standard "لا توجد نتائج للبحث" / "لا توجد طلبات" empty state on that screen, not a dedicated message here).

## Notes
- Both AGENT and DISTRIBUTOR partner types get **identical** access to this entire screen (list + detail + save) — this is one of the few partner surfaces with no type-based restriction anywhere in the stack (contrast with `orders.md`, `distributors.md`, `distributor-requests.md`, `reports.md`, all of which are AGENT-only, or `restock-requests.md`'s POST which is DISTRIBUTOR-only).
- The product catalog shown here is **global** (every active product across the whole store), not a partner-specific product subset — only the *stock numbers* are partner-specific. Don't rebuild this as "the partner's own product list" in a way that filters out products the partner has never stocked; per-partner scoping only applies to the numeric columns.
- The "order-verification link per variant" (commit `a8a7dbd`, 2026-09-09) is a recent, deliberately narrow feature: a single outbound link per variant row to a pre-filtered view of `/partner/routed-orders`. There is no reverse link (routed-orders back to this exact variant row) and no inline count-of-open-orders shown directly in this table — the partner has to actually click through to see the number. `[NEEDS PM INPUT: should the redesign surface an inline "N open orders" badge here to save a click, or preserve the link-out-only pattern?]`
- `sortVariants` (from `lib/admin/variant-sort.ts`) determines display order of variants in both the list's implicit ordering (via the shared inventory query) and the detail table — shared with the admin product screens, so any variant-ordering logic change there will ripple here too.
