# Partner — Routed Orders (the partner's "Orders" list)

Route(s): `app/(partner)/partner/routed-orders/page.tsx` (client component, wrapped in `React.Suspense`)
Key files: `app/api/partner/routed-orders/route.ts` (GET), `app/api/partner/routed-orders/export/route.ts` (POST, shipping-file export), `app/api/partner/me/route.ts`, `hooks/use-list-url-state.ts`, `hooks/use-row-scroll-restore.ts`, `lib/constants/order-status.ts`, `lib/courier-export.ts`, `components/dashboard/{page-header,panel-card,search-input,pagination,empty-state}.tsx`

## Business requirements
- **Goal/KPI**: this is the partner's primary day-to-day operational screen — labeled in-app "الطلبات" (Orders) and described as "نفس جدول الطلبات في لوحة الإدارة، لكن مقتصر على الطلبات المسندة لك" (the same orders table as the admin panel, restricted to orders assigned to you). Directly serves fulfillment throughput: find an order, check its payment/status/notes, and (for agents) bulk-export ready-to-ship orders into the courier's shipment template in one action.
- **Trust/credibility signals**: every money figure (total, subtotal, shipping, COD fee) shown in EGP; payment method surfaced in Arabic ("الدفع عند الاستلام" / "الدفع عبر InstaPay" / "بطاقة") so the partner knows whether they're collecting cash on delivery; status badges use the same color/label system as the rest of the app.
- **Friction points**: the "فتح" (Open row detail) column and its underlying edit screen are AGENT-only — a distributor partner sees the identical order list but has no way to open/edit any individual order from here (no visible affordance explaining why the column is absent). The export button is a global "select rows → export" flow but silently excludes any selected order that isn't `READY_TO_SHIP` (see Edge cases) with no per-row indication of which selections will actually be included until after the export request completes.
- **Compliance/legal**: the exported shipping file feeds an external courier's exact spreadsheet template column-for-column (`COURIER_EXPORT_HEADERS`, explicitly commented "Do not change" in `lib/courier-export.ts`) — any redesign of the export trigger must not alter the file's contents/column order, only its UI entry point.
- **Modern-look rationale**: none specific — standard internal ops table.

## Elements & behavior
- [ ] **Role/ownership gate**: `requirePartner()` only (no AGENT/DISTRIBUTOR restriction — both partner types can view this list). Query is always scoped `assignedPartnerId: user.partnerId` — a partner only ever sees their own assigned orders, never another partner's.
- [ ] `PageHeader` — title "الطلبات"; description as above; "تحديث" (refresh) action button (spinner while `fetching`).
- [ ] **Variant-filter banner** — shown only when a `variantId` URL param is present (arrives via the "عرض الطلبات" link from the product-variant table, see `products.md` → "order-verification link"): a gold-tinted banner reading "الطلبات مفلترة حسب متغير منتج محدد لمطابقة المخزون الفعلي" (orders filtered by a specific product variant to match against physical stock) with an "إلغاء الفلتر" (clear filter) button that clears only the `variantId` param.
- [ ] **Toolbar**: `SearchInput` (debounced 400ms via `useListUrlState`, searches order id / customer phone or name / item product or variant name — server-side `OR` query); status `<Select>` (single-select dropdown: "كل الحالات" + all 7 `ORDER_STATUS_LABELS` — note: only single status selectable from this dropdown even though the API supports comma-separated multi-status, see Notes); "ملف الشحن (`{n}`)" export button showing the live count of selected rows, disabled while exporting or when 0 rows are selected.
- [ ] **Table columns**: checkbox (select row) · الرقم (order id, first 8 chars, monospace) · العميل (phone + optional name in parens) · الإجمالي (total EGP, bold, plus a small sub-breakdown of subtotal/shipping/COD fee stacked underneath) · طريقة الدفع (payment method label) · الحالة (status badge) · ملاحظات (`adminNotes`, expandable — see below) · التاريخ (`formatDateEn`) · فتح (open-detail link — **AGENT only**, column header and cells both omitted entirely for DISTRIBUTOR, not just disabled).
- [ ] **Select-all checkbox** (header row) — selects/deselects every row on the *current page only*; selections accumulate across pages in local state (`selectedOrderIds`) until cleared by a search/filter/page/pageSize change (see Edge cases) or a successful export.
- [ ] **Expandable notes cell** (`ExpandableNotesCell`) — truncates `adminNotes` to a 2-line clamp when the text exceeds 56 chars or contains a newline, with a "المزيد/أقل" (more/less) toggle per row; empty/null notes render as "—".
- [ ] **Shipping-file export** ("ملف الشحن" button): POSTs the selected order ids to `/api/partner/routed-orders/export`; server re-filters to only those selected ids that (a) belong to this partner and (b) currently have `status === "READY_TO_SHIP"` — any selected order not meeting both is silently dropped from the export with no per-row feedback to the partner about which ones were excluded. If **none** of the selected orders qualify, the whole request 400s ("لا توجد طلبات بحالة «جاهز للشحن» ضمن الطلبات المحددة"). On success: marks every exported order's `exportedToCourierAt = now` (so a subsequent export of the same orders is not blocked by this field, but the field is available for future "already exported" UI/logic — not currently surfaced anywhere in the partner UI), returns an `.xlsx` blob built via `buildCourierXlsx` (see `lib/courier-export.ts` — fixed 16-column courier template, only "red columns" + COD value populated, City mapped from the Egyptian governorate to the courier's fixed city-code list, address flattened into one multiline "Street" field), downloaded client-side via an anchor-click/`URL.createObjectURL` pattern, filename `shipments_YYYY_MM_DD.xlsx`. Selection is cleared and a success toast shown after.
- [ ] **Row scroll-restore**: clicking "فتح" remembers the row id in `sessionStorage`; returning to this list (e.g. via browser back) scrolls that exact row back into view.
- [ ] **URL-synced list state** (`useListUrlState`): search text (`q`), `status`, `variantId`, `page`, `pageSize` are all reflected in the URL query string (via `router.replace`, no scroll jump) — so the exact list state survives navigating to a detail page and back, or sharing/bookmarking a filtered URL. Changing search/status/variantId resets to page 0.
- [ ] **Pagination**: `PaginationBar`, page-size options `10/20/50` (default 20), "عرض X–Y من Z" / "لا نتائج" summary text, prev/next buttons only (no jump-to-page).

## States
- [ ] Empty state — no orders match current filters: `EmptyState` with "لا توجد نتائج للبحث" if a search query is active, else "لا توجد طلبات".
- [ ] Loading state — first load (no orders yet): a plain `h-64` skeleton block (not the shared `Skeleton` component, just a muted div). Subsequent refetches (filter/page change) keep the existing table visible at reduced opacity with a "جاري التحديث…" spinner line above it, rather than blanking the table.
- [ ] Error state — load failures (non-OK response or thrown error) surface only as a destructive toast ("فشل تحميل الطلبات", with the error message appended when available); the table is left showing whatever it last successfully loaded (or empty, on first-load failure) — no inline retry button beyond the page-level "تحديث" action.
- [ ] Permission-restricted state — n/a at the page level (both partner types can load this list); the only permission distinction is the **absence** of the "فتح" column/action for DISTRIBUTOR, enforced purely by conditionally omitting the JSX (not a disabled state) once `partnerType` resolves from `/api/partner/me`. Before that resolves, `partnerType` is `null` and the "فتح" column is likewise omitted for everyone until it loads as `"AGENT"`.
- [ ] Export-specific error state — export failures (API error or thrown exception) show a destructive toast with the server's message (or `res.statusText` / the exception message as fallback); selection is preserved (not cleared) on failure so the partner can retry.

## Edge cases
- [ ] Selecting rows, then changing the search text, status filter, `variantId`, page, or page size — `selectedOrderIds` is explicitly reset to empty (a dedicated `useEffect` keyed on these). Selections do **not** persist across a filter/page change, even though the URL-synced filters themselves do.
- [ ] Selecting orders across multiple pages, exporting only some of them, then the export drops non-`READY_TO_SHIP` orders silently — a partner who multi-selects orders in mixed statuses gets a smaller export than the count shown in the button label, with no page-by-page or per-order breakdown of what was skipped.
- [ ] `page` beyond the last valid page for the current `total` (e.g. after a filter narrows the result set) — a dedicated effect clamps `page` back down once `total`/`loading` settle, to avoid rendering a page number past the end.
- [ ] The variant-filter banner and `variantId` query param survive independently of the status filter — a partner can clear just the variant filter (via the banner's button) while keeping any status filter they'd also applied, or vice versa via the status dropdown.
- [ ] Very long `adminNotes` (multi-paragraph) — clamped to 2 lines with expand/collapse; long *unbroken* strings without newlines only trigger the toggle once they exceed the 56-character threshold.
- [ ] The `/api/partner/routed-orders` GET response also returns a `routedOrders` array (up to 100 `RoutedOrder` rows with an `orderNumber` computed field) alongside `orders`/`total` — **the page never reads or renders this field.** It's dead data on the wire as far as this screen is concerned (see Notes).

## Notes
- Despite the route name "routed-orders" and the nav label "الطلبات", this screen's table is driven by the **`Order`** model (`prisma.order.findMany({ where: { assignedPartnerId: ... } })`), not the `RoutedOrder` model — `RoutedOrder` is a separate delivery-routing/tracking record (governorate assignment, round-robin sequence, courier-facing status) linked 1:1 to an `Order`. The API additionally queries and returns up to 100 `RoutedOrder` rows in the same response payload, but the page component only ever destructures `json.data.orders`/`json.data.total` — the `routedOrders` array is computed server-side and shipped to the client for no current UI purpose. Flag for the PM: either this is dead weight to drop, or a planned-but-unbuilt future view (e.g. a delivery-tracking sub-tab) — `[NEEDS PM INPUT]`.
- **This is the screen the "partner order-verification link per variant" feature (commit `a8a7dbd`) targets.** From `products.md`'s variant table, an "عرض الطلبات" button opens this exact page in a **new tab** with `?variantId={id}&status=CREATED,CONFIRMED,PROCESSING` — i.e. pre-filtered to just the open (not-yet-shipped) orders containing that specific variant, so warehouse staff can cross-check physical shelf stock against what's still owed to customers. The comma-joined multi-status filter this link relies on is a **server-only** capability (`Prisma.OrderWhereInput["status"]` becomes `{ in: [...] }` when the `status` query param has 2+ comma-separated values) — the page's own status `<Select>` UI can only ever set a *single* status at a time; a partner cannot construct a multi-status filter through the visible UI, only via this deep-link (or a hand-typed URL). Preserve both behaviors: the single-select dropdown AND the API/URL's ability to carry a multi-status filter.
- The "فتح" column/action is gated purely by `partnerType === "AGENT"` client-side (no server enforcement needed here since the link just routes to `/partner/orders/[id]`, which is itself AGENT-gated server-side — see `orders.md`). A distributor who somehow got a direct link to an order-detail URL would hit that screen's own 403 handling, not anything on this list page.
- Export marks `Order.exportedToCourierAt` but nothing in the partner UI ever displays or filters on that field — it exists for idempotency/audit purposes at the data layer only, currently invisible to the partner.
