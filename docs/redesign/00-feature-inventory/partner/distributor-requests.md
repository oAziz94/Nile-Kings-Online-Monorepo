# Partner — Distributor Requests (agent's inbound restock-request queue)

Route(s): `app/(partner)/partner/distributor-requests/page.tsx` (client component)
Key files: `app/api/partner/restock-requests/route.ts` (GET — shared with `restock-requests.md`), `app/api/partner/restock-requests/[id]/route.ts` (PATCH — approve/reject/fulfill), `lib/inventory/restock-requests.ts` (`approveRestockRequest`, `rejectRestockRequest`, `fulfillRestockRequest`), `lib/inventory/partner-inventory.ts` (`InsufficientPartnerStockError`)

## Business requirements
- **Goal/KPI**: this is the AGENT-side counterpart to `restock-requests.md` — where an agent reviews and actions stock-transfer requests coming in from their downstream distributors. Core to the distributor-hierarchy fulfillment model: it's the only in-app mechanism that actually moves stock from an agent's `PartnerInventory` to a distributor's.
- **Trust/credibility signals**: every request shows exactly which distributor it's from, what's being asked for (product/SKU/quantity per line), and any note the distributor attached — enough context for the agent to make a fulfill/reject decision without leaving the screen. The agent's own response note is preserved and shown back once a request leaves the actionable states, giving both sides a durable record of the exchange.
- **Friction points**: like `restock-requests.md`, there is no visibility here into the agent's own current stock levels for the requested variants *inline in this table* — the agent has to already know (or separately check `/partner/products`) whether they can actually fulfill a request before clicking "تنفيذ التحويل" (execute transfer); an insufficient-stock fulfill attempt only fails *after* the click, via a toast. There's also no bulk action (approve/reject/fulfill multiple requests at once) and no filter/search/sort on this list — every request, in every status, is always shown.
- **Compliance/legal**: fulfilling a request performs a real, immediate stock transfer with full ledger audit trail (`TRANSFER_OUT` on the agent, `TRANSFER_IN` + `RESTOCK_REQUEST_FULFILL` on the distributor) — this is a financially/operationally consequential action disguised as a simple button click; the rebuild must not make "تنفيذ التحويل" easier to trigger accidentally (e.g. no confirmation dialog exists today — see Edge cases — which is itself worth flagging to the PM, not silently adding one without sign-off).
- **Modern-look rationale**: none specific.

## Elements & behavior
- [ ] **Role/data-scope**: uses the same `GET /api/partner/restock-requests` as `restock-requests.md`; for a caller whose `partnerType === "AGENT"`, the `where` clause is `{ sourcePartnerId: user.partnerId }` — i.e. every request where *this agent* is the intended stock source, across **all** of their linked distributors (not filterable to a single distributor from this screen).
- [ ] `PageHeader` — title "طلبات الموزعين"; description "مراجعة طلبات إعادة التوريد القادمة من الموزعين وتنفيذها من مخزونك."; "تحديث" refresh button. No `StatusBadge` role label on this screen (unlike most other partner screens).
- [ ] **Request cards** (not a table — each request renders as its own bordered card): status badge (same 5-state coloring as `restock-requests.md`: FULFILLED/APPROVED→default, REJECTED/CANCELLED→destructive, PENDING→secondary) + relative-formatted date; "من: `{distributor.name}` · `{distributor.phone}`" attribution line; item lines rendered as `"{product} · {sku}{, colorName if set}"` with quantity (`×{qty}`) right-aligned per line; distributor's own notes shown if present ("ملاحظات: ..."); a response textarea + the three action buttons (see below), shown only while the request is actionable.
- [ ] **Actionable window**: action buttons and the response-notes textarea appear only when `request.status` is `"PENDING"` or `"APPROVED"` — "قبول"/"رفض" (approve/reject) shown only when `status === "PENDING"` specifically; "تنفيذ التحويل" (execute transfer/fulfill) shown for **both** PENDING and APPROVED (i.e. an agent can fulfill directly from PENDING without a separate approve step first — approve is not a required gate before fulfill). For any terminal status (REJECTED/FULFILLED/CANCELLED), the card instead shows the saved `responseNotes` as plain read-only text ("رد: ...") if present, nothing otherwise.
- [ ] **Response notes textarea** — pre-filled from any existing draft in local state, else falls back to the already-saved `responseNotes`; free text, sent as part of whichever action button is clicked (not saved independently — there's no standalone "save note" action; the note is only persisted as a side effect of approve/reject/fulfill).
- [ ] **Approve** (`PATCH { action: "approve", responseNotes }`) — server sets `status: APPROVED`, `approvedAt: now`. No stock movement.
- [ ] **Reject** (`PATCH { action: "reject", responseNotes }`) — server sets `status: REJECTED`, `rejectedAt: now`. No stock movement.
- [ ] **Fulfill / "تنفيذ التحويل"** (`PATCH { action: "fulfill", responseNotes }`) — the actual stock-transfer action:
  - Server re-fetches the request fresh, rejects (400) if current status isn't PENDING or APPROVED (protects against double-fulfilling or fulfilling an already-rejected request via a stale UI state).
  - Locks the relevant `PartnerInventory` rows for both partners via a raw `SELECT ... FOR UPDATE` inside a DB transaction (concurrency-safe against simultaneous fulfill attempts or simultaneous stock edits).
  - For each requested line: computes the agent's current sellable (`stockAvailable − stockReserved`); if less than the requested quantity, throws `InsufficientPartnerStockError` — surfaced to the UI as a 400 with the fixed Arabic message "لا يوجد مخزون كافٍ لدى الوكيل لتنفيذ الطلب" (regardless of *which* line or variant was short — no per-variant detail is shown to the agent). **Nothing is transferred at all if any single line fails** (whole transaction rolls back).
  - On full success: decrements the agent's `stockAvailable` by the requested quantity per variant, increments (or creates) the distributor's `PartnerInventory.stockAvailable` by the same amount, writes three `InventoryLedger` rows per variant (`TRANSFER_OUT` for the agent; `TRANSFER_IN` **and** `RESTOCK_REQUEST_FULFILL` both for the distributor — see Notes on this being two ledger entries for what is conceptually one inbound movement), sets `status: FULFILLED`, `fulfilledAt: now`.
- [ ] Each action button is disabled while `updatingId === request.id` (only one request's action in flight at a time is tracked, though nothing prevents starting an action on a *different* card concurrently); the fulfill button additionally shows an inline spinner while in flight.
- [ ] On any successful action: generic success toast ("تم تحديث طلب الموزع") + full list reload (`load()`), not an optimistic local update — the card's new state comes from a fresh GET, not a locally patched object.

## States
- [ ] Empty state — agent has zero inbound requests (from any distributor, any status): `EmptyState` "لا توجد طلبات موزعين".
- [ ] Loading state — centered spinner + "جاري التحميل" for the initial load; the whole card list is gated behind this (no per-card skeleton).
- [ ] Error state — list load failure: destructive toast ("فشل تحميل طلبات الموزعين" + message). Action failure (approve/reject/fulfill): destructive toast with the server's message when present (e.g. the fixed insufficient-stock message above) or a generic "فشل تحديث الطلب" fallback; the card is **not** reverted to any prior visual state because nothing was optimistically changed to begin with — it simply stays as it was pre-click.
- [ ] Permission-restricted state — a DISTRIBUTOR (or non-AGENT) loading this URL directly: no client-side guard; the shared GET endpoint still returns *something* (their own `destinationPartnerId`-scoped requests, per the API's partnerType branch — i.e. they'd see their **own outgoing** requests here, mislabeled as if they were "من: `{distributor}`" incoming ones, which would actually read as **from themselves**), and the action buttons would render for PENDING/APPROVED items but fail with a 403 ("غير مصرح بتعديل هذا الطلب") on click since the PATCH endpoint separately checks `request.sourcePartnerId !== user.partnerId`. This is a real, reachable point-of-confusion for a distributor who guesses this URL, not just a theoretical edge case — see Edge cases.

## Edge cases
- [ ] **No confirmation dialog before "تنفيذ التحويل"** — a single click immediately performs the stock transfer server-side; there is no "are you sure?" step, undo, or grace period anywhere in this flow. `[NEEDS PM INPUT: is a confirmation step intentionally omitted for speed, or a gap worth closing in the redesign?]`
- [ ] Fulfilling a multi-line request where only one variant is short on stock — the entire fulfill fails (transaction rollback), with a generic message that doesn't name which variant was insufficient, forcing the agent to go check `/partner/products` themselves to figure out which line to fix or wait on.
- [ ] Approving a request, then later fulfilling it — both actions can carry *different* response notes (the textarea's draft is re-read at whichever action's click time), so the final saved `responseNotes` reflects only the last action taken, not a running log of the agent's replies across approve → fulfill.
- [ ] A DISTRIBUTOR directly navigating here (see States above) sees their own requests mislabeled as if from themselves, and any attempted action 403s with a message that doesn't explain *why* ("غير مصرح بتعديل هذا الطلب" — not authorized to edit this request — with no hint that the real issue is being on the wrong role's screen).
- [ ] Rejecting a request the distributor already expected to be fulfilled — no notification/email system is visible in this flow; the distributor only learns of the rejection by revisiting `/partner/restock-requests` themselves and seeing the status/response-notes change.

## Notes
- This screen and `restock-requests.md` share one GET endpoint and nearly identical card/row rendering (status badges, item-line formatting) but diverge entirely on mutating actions — approve/reject/fulfill exist only here, gated by `request.sourcePartnerId === user.partnerId` (i.e. "am I the agent this request is asking stock from") at the API layer, independent of whatever the UI happens to show. Preserve that ownership check exactly; it's the real security boundary, not the nav-item visibility.
- Fulfilling writes **three** `InventoryLedger` rows per variant per fulfillment (`TRANSFER_OUT` for the source agent, plus both `TRANSFER_IN` and `RESTOCK_REQUEST_FULFILL` for the destination distributor) — two ledger entries for what is, from the distributor's point of view, a single inbound stock event. This looks like it could be an intentional "movement record" + "request-linkage record" split (both reference `restockRequestId`), but is worth flagging to the PM/data-audit owner as a possible duplication rather than assuming it's deliberate: `[NEEDS PM INPUT: confirm the double ledger entry for the destination partner on fulfill is intentional]`.
- Approve is **not a required gate** before fulfill — an agent can fulfill a still-PENDING request directly. If the business process actually expects "approve, then separately fulfill later" as two distinct human steps, the current UI doesn't enforce that ordering; it's a soft convention only.
