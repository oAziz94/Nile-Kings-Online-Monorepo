# Partner — Orders (detail view only)

Route(s): `app/(partner)/partner/orders/[id]/page.tsx` (client component). **There is no `app/(partner)/partner/orders/page.tsx` list route** — see Notes; the order *list* UI partners actually use lives at `/partner/routed-orders` (documented in `routed-orders.md`).
Key files: `app/api/partner/orders/[id]/route.ts` (GET/PATCH, `requireAgentPartner`), `app/api/partner/inventory/route.ts` (GET, used for the "add item" variant search), `lib/inventory/partner-inventory.ts` (`commitPartnerReservation`, `reconcilePartnerStockForAdminOrderItemEdit`, `releasePartnerReservation`, `restorePartnerCommittedStock`, `InsufficientPartnerStockError`), `lib/audit/order-audit.ts`, `lib/services/pricing.ts`, `lib/services/shipping.ts`, `lib/checkout/cod-fee.ts`, `lib/constants/order-status.ts`, `components/dashboard/{page-header,panel-card,empty-state,table-scroll}.tsx`

## Business requirements
- **Goal/KPI**: operational efficiency — lets a regional fulfillment partner (AGENT only, see Notes) correct an order before it ships: fix quantities/variants, change status, leave internal notes — without needing the admin team to intervene. Directly reduces order-processing turnaround and admin support load for the partner's own assigned orders.
- **Trust/credibility signals**: pricing is always shown in EGP (piastres divided by 100, formatted via `.toFixed(0)`, no decimals), with an itemized breakdown (subtotal, discount/coupon, shipping + carrier name, COD fee, total) so the partner can see exactly what the customer is being charged after any edit. Edits to items trigger a live recompute of shipping/coupon/COD ("تم تحديث بنود الطلب وإعادة حساب الإجمالي والشحن") so the partner never silently desyncs the customer-facing total from what's actually being shipped.
- **Friction points**: this screen is reached only via the "فتح" (Open) button on `/partner/routed-orders`, which is only rendered for AGENT partners — a DISTRIBUTOR has no path to this screen from the UI at all (nav or otherwise), and if they guess the URL the API 403s (see States). There's also no order list scoped to `/partner/orders` itself — an agent bookmarking `/partner/orders/<id>` and pressing "back" lands nowhere useful (the back button just does `router.back()`, not a link to a real orders index). Editing items requires typing a raw quantity into a small input per row with no stepper affordance, and variant search/add is a separate, easy-to-miss mini-form below the items table.
- **Compliance/legal**: partner-entered notes are explicitly internal-only ("ملاحظات داخلية للفريق — لا تظهر للعميل ولا تُرسل لشركة الشحن" — internal notes for the team; not shown to the customer or sent to the shipping company) — important to preserve as literal copy since it sets a data-handling expectation.
- **Modern-look rationale**: none specific; this is an internal back-office edit screen, not customer-facing.

## Elements & behavior
- [ ] **Role gate**: every request handler in `app/api/partner/orders/[id]/route.ts` calls `requireAgentPartner()` — `requirePartner()` plus an explicit `Partner.partnerType === "AGENT"` check; DISTRIBUTOR partners get a 403 on both GET and PATCH. **Ownership gate**: both GET and PATCH additionally filter `where: { id, assignedPartnerId: user.partnerId }` — a partner can only view/edit orders assigned to them, not any order in the system.
- [ ] `PageHeader` — title `طلب #{first 8 chars of order id}`; badge = current status pill (`ORDER_STATUS_LABELS`/`ORDER_STATUS_BADGE_CLASSES`, same mapping used across admin/partner); action = "رجوع للطلبات" button calling `router.back()` (browser history, not a fixed link).
- [ ] **Status panel** — a `<Select>` pre-populated with all 7 `ORDER_STATUSES` (`CREATED, CONFIRMED, PROCESSING, READY_TO_SHIP, SHIPPED, DELIVERED, CANCELLED`) each showing its Arabic label; "تحديث الحالة" button, disabled while `updating` or when the selected value equals the order's current status. On save: `PATCH { status }`. Server-side status-change side effects (all inside the same PATCH handler, not visible in the UI beyond a toast):
  - Any status change writes an `OrderAuditLog` entry via `logOrderStatusChange`.
  - Transitioning **to `CANCELLED`** from any non-cancelled status: sets `cancellationReason: "partner_agent"`, and inside a DB transaction either releases the partner's reserved stock (`releasePartnerReservation`, if the order was still using reservation-only stock) or restores previously committed stock (`restorePartnerCommittedStock`) back to the partner's `PartnerInventory`, then logs via `logOrderCancelled`. **Cannot combine with an item edit in the same request** — API returns 400 "لا يمكن تعديل أصناف الطلب مع إلغائه في نفس الطلب" if both `status: "CANCELLED"` and `items` are sent together (the UI never actually does this — status and items are saved via separate buttons/requests — but it's a hard API-level invariant, not just a UI convention).
  - Transitioning **out of `CREATED`** (to anything except `CREATED`/`CANCELLED`) for the first time: commits the partner's stock reservation (`commitPartnerReservation`) against the order's item lines, clears `reservationExpiresAt`, and — if the order's `paymentMethod === "INSTAPAY_PREPAID"` — marks any `PENDING` `PaymentAttempt` rows as `CAPTURED`. If `nextStatus === "CONFIRMED"` specifically, logs via `logOrderConfirmed`; any other non-CREATED/non-CANCELLED status logs a generic status-change entry. If the partner's on-hand stock is insufficient for this commit, the API returns 400 "كمية غير متوفرة في مخزون الشريك لتأكيد الطلب" and the status is **not** changed.
- [ ] **Internal notes panel** — one `<textarea>` (3 rows) bound to `adminNotes`; "حفظ الملاحظات" button disabled while saving or when the draft equals the currently-saved value (empty string saved as `null`). `PATCH { adminNotes }`.
- [ ] **Customer panel** — read-only: customer name (falls back to "عميل بدون اسم" if unset) and phone.
- [ ] **Shipping address panel** — read-only: `governorate, city, area, street` plus building/floor/apartment rendered as "مبنى {x}"/"دور {x}"/"شقة {x}" when present, comma-joined (falls back to "لا يوجد عنوان" if the address has no populated lines); customer's own address notes shown separately, labeled "ملاحظات العميل على العنوان" (distinct from the partner's own internal notes above).
- [ ] **Order items table** — columns: صورة+اسم المنتج/المتغير (image thumbnail or a gray placeholder box + "`{productName}` – `{variantName}`"), الكمية (editable numeric input, min 1, values coerced via `Math.max(1, Math.trunc(...))` on change — non-finite input silently resets to 1), السعر الوحدة (unit price, read-only), الإجمالي (`qty × unit price`, computed client-side, read-only), المقاس (size, parsed from `variantName` via regex/heuristics — see Notes on `getSize`), اللون (color, first Arabic-script segment of `variantName`, else "—" — see `getColor`), إجراء (حذف/remove button, removes the row from the local draft only, no confirmation dialog).
- [ ] **Add item from stock** — free-text search input (300ms debounced) that queries `/api/partner/inventory?q=...&limit=20&offset=0` (i.e. searches the *partner's own* inventory/catalog, not the global admin catalog) and flattens results into a `<Select>` of `"{product} - {variant}[ - {color}]"` options priced at `pricePiastres`; a quantity input (min 1); "إضافة" button (disabled until a variant is selected) that either bumps quantity on an existing draft line for that variant or appends a new one.
- [ ] **Save items** — "حفظ البنود وإعادة الحساب" button, disabled while saving or if the draft has zero items (client blocks with a toast "لا يمكن حفظ طلب بدون بنود" before even calling the API; the API independently rejects an empty `items` array the same way). On save, `PATCH { items: [{variantId, quantity}] }` (quantities for duplicate variantIds are summed client-side before send). Server-side on an items edit:
  - Re-resolves each variant's current name/SKU/price/product weight from the DB (line prices/snapshots are **not** trusted from the client).
  - Rejects (400) if any variant no longer exists, if total weight can't be computed (missing `weightGrams`), or if the shipping address has no `governorate`.
  - Recomputes pricing via `computePricing` (re-applies the order's existing coupon code and the customer's senior-discount eligibility), recomputes shipping via `getPhase1ShippingFee` (weight- and address-based), recomputes COD fee via `computeCodFeePiastres` if `paymentMethod === "COD"`, and overwrites `subtotalPiastres/discountPiastres/seniorFreeValuePiastres/shippingPiastres/carrierShippingPiastres/codFeePiastres/totalPiastres/couponCode` plus **replaces all `OrderItem` rows** (`deleteMany` + `create`).
  - If the new item lines differ from the original ones in a way that changes required stock (`stockLinesEquivalent` check), reconciles the partner's `PartnerInventory` reservation/commitment via `reconcilePartnerStockForAdminOrderItemEdit` inside the same transaction; insufficient stock → 400 "كمية غير متوفرة في مخزون الشريك لتعديل الطلب بهذه الأصناف" and nothing is saved.
  - If the order was still `CREATED` and this items-edit is paired with a status transition out of `CREATED` in the *same* request, both the stock-reconcile-for-edit and the leaving-CREATED commit logic run together in one transaction.
  - On success, both the order summary numbers panel and the items table update from the server's authoritative response (not just echoed back).
- [ ] **Order summary block** (below the items table) — subtotal; discount line (only shown if `discountPiastres + seniorFreeValuePiastres > 0`, appends the coupon code in parens if present); shipping line (amount + shipping provider name, e.g. "Egypt Post"); COD fee line (only shown if `> 0`); bold total line. All figures recompute from whatever the server last returned (i.e. reflects saved state, not unsaved draft edits).

## States
- [ ] Empty state — order not found (deleted, wrong id, or not assigned to this partner): full-page `EmptyState` — "الطلب غير موجود" / "ارجع إلى قائمة الطلبات واختر طلباً آخر."
- [ ] Loading state — full-page centered spinner + "جاري تحميل الطلب" while the initial GET is in flight; no skeleton for individual panels.
- [ ] Error state — no dedicated error UI/boundary; every fetch failure (initial load, status save, notes save, items save) surfaces only as a destructive `toast` (message from the API's `error.message` when present, else a generic Arabic fallback like "خطأ في الاتصال" for network failures or "فشل تحميل الطلب" for the initial load). A failed initial load leaves `order` as `null`, which renders the same "not found" `EmptyState` as a genuinely-missing order — **the UI cannot distinguish "order doesn't exist" from "network/API error fetching it."**
- [ ] Permission-restricted state — DISTRIBUTOR partner hitting this route: the page itself has no client-side role check; it would call the GET API, receive a 403, and — because the fetch's `.then` only handles the success branch and the `.catch` only fires on network-level failures, not on a resolved-but-`!success` JSON response — `order` simply never gets set, `loading` flips to `false` in `finally`, and the user sees the generic "الطلب غير موجود" empty state with **no indication it's actually a permission error**, not a missing-order error.

## Edge cases
- [ ] Saving items with an empty draft (all rows removed via "حذف") — blocked client-side before the request is even sent ("لا يمكن حفظ طلب بدون بنود").
- [ ] Adding a variant already present in the draft — merges by summing quantities rather than creating a duplicate row.
- [ ] Changing an item's quantity input to a non-numeric or negative value — silently clamped to `1` (`Number.isFinite(nextQty) ? Math.max(1, Math.trunc(nextQty)) : 1`), no inline validation message shown.
- [ ] Attempting to change status **and** edit items as a combined save is not possible from this UI (separate buttons/requests) but is explicitly rejected server-side (400) if ever attempted via direct API call — this is a real, tested API invariant worth preserving even though the current UI can't trigger it.
- [ ] Editing items on an order whose status is already `CANCELLED` — API rejects with 400 "لا يمكن تعديل أصناف طلب ملغى"; the UI has no client-side guard for this (a partner could try to add/remove items on a cancelled order and just get a failure toast).
- [ ] Insufficient partner stock when saving item edits, or when transitioning an order out of `CREATED` — both return descriptive 400s and leave the order **unchanged**; the local item draft is *not* rolled back automatically on failure, so the partner's in-progress edit remains on screen for correction.
- [ ] `variantName` parsing for size/color display (`getSize`/`getColor`) is heuristic string-splitting on `-`, matched against a size-pattern regex or "first Arabic-script segment" — a variant name that doesn't follow the expected `{slug}-{size}-{colorArabic}` convention could show a wrong or missing size/color in these two columns without erroring.
- [ ] `groupItemsByCategory` runs automatically on every `editableItems` change and silently re-sorts the items array by a parsed "category" (second `-`-segment when the variant name starts with `nk-`) whenever the sort order differs from current — this is an implicit, non-obvious re-ordering side effect a rebuild could easily drop or accidentally change.

## Notes
- **There is no partner-facing order list at `/partner/orders`.** Only the `[id]` detail route exists under `app/(partner)/partner/orders/`. The functional "orders list" a partner uses day-to-day is `/partner/routed-orders` (see `routed-orders.md`), whose "فتح" (Open) button — shown only for AGENT partners — is the sole in-app entry point into this detail screen. Treat this file as covering the **detail screen only**; do not invent a list view at `/partner/orders` during rebuild unless the PM/redesign explicitly decides to consolidate it.
- This detail API/page and the *separate* `/partner/routed-orders/[id]` API (`app/api/partner/routed-orders/[id]/route.ts`, GET+PATCH on the `RoutedOrder` model with its own status enum `ACCEPTED/OUT_FOR_DELIVERY/DELIVERED/FAILED`) are two different resources that happen to sound similar: this screen edits the `Order` row (items, pricing, `OrderStatus`) directly and is AGENT-only; the `RoutedOrder` API edits the routing/delivery-tracking record and has **no partner-facing UI consumer at all** in the current codebase (no `/partner/routed-orders/[id]` page exists) — it appears to be orphaned/unused by the partner surface today. Don't assume it needs a UI in the rebuild without confirming with the PM; note its existence in case it's meant for a future screen.
- The order-summary numbers panel intentionally reflects the **last-saved server state**, not the unsaved item draft — if a partner adds/removes items but hasn't clicked "حفظ البنود", the totals at the bottom still show the old numbers. This is current behavior, not a bug to "fix" during redesign without PM sign-off.
- Money is displayed with **zero decimal places** here (`.toFixed(0)`) even though internal amounts are piastres (integer, /100 = EGP with cents) — differs from `reports.md`'s revenue figures which use `formatNumberEn`/no fixed decimals via a different helper. Keep this screen's own rounding behavior; don't unify formatting without confirming.
