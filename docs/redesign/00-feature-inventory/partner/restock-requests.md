# Partner — Restock Requests (distributor's "request stock from my agent" screen)

Route(s): `app/(partner)/partner/restock-requests/page.tsx` (client component)
Key files: `app/api/partner/restock-requests/route.ts` (GET list, POST create), `app/api/partner/inventory/route.ts` (GET, variant search for the request form), `lib/inventory/restock-requests.ts` (`createRestockRequest`), `components/dashboard/{page-header,panel-card,empty-state,search-input}.tsx`

## Business requirements
- **Goal/KPI**: lets a DISTRIBUTOR (see Notes — this screen is functionally distributor-only despite no route-level redirect) request stock transfers from their linked AGENT without a phone call/manual process — reduces stockout risk and agent/distributor coordination overhead, directly supporting the distributor-hierarchy fulfillment model.
- **Trust/credibility signals**: every past request shows its live status (قيد المراجعة/مقبول/مرفوض/تم التنفيذ/ملغي) plus the agent's own free-text response, so the distributor always has a record of what was asked for and how the agent responded — important since a rejected or still-pending request means the distributor should not assume that stock is coming.
- **Friction points**: the "طلب جديد" (new request) form has no visibility into the *agent's* current stock levels for the variant being requested — a distributor can submit a request for a quantity the agent can't actually fulfill and will only find out when the agent rejects it or the fulfill action fails server-side with an insufficient-stock error. There's also no way to edit or cancel an already-submitted PENDING request from this screen (no cancel/withdraw action anywhere in the UI, even though the underlying model has a `CANCELLED` status).
- **Compliance/legal**: every fulfilled request writes ledger entries with a `restockRequestId` back-reference — an audit trail, not directly visible here but must not be broken by a UI rebuild.
- **Modern-look rationale**: none specific.

## Elements & behavior
- [ ] **Role gate — GET is shared, POST is not**: `GET /api/partner/restock-requests` requires only `requirePartner()` and branches its `where` clause by the caller's actual `partnerType` (`sourcePartnerId` match for AGENT, `destinationPartnerId` match for DISTRIBUTOR) — so this same endpoint powers *both* this screen and `distributor-requests.md`'s screen, just returning opposite-direction data depending on who's asking. `POST /api/partner/restock-requests` (create) additionally requires `Partner.partnerType === "DISTRIBUTOR"` — an AGENT calling POST gets a 403 ("طلبات إعادة التوريد متاحة للموزعين فقط").
- [ ] `PageHeader` — title "طلب إعادة توريد"; description "اطلب متغيرات من الوكيل المرتبط بحسابك وتابع حالة الطلب."; `StatusBadge` "موزعون فقط" (distributors only — a label, not an enforced client-side redirect, see States); "تحديث" refresh button.
- [ ] **New-request form** (`"طلب جديد"` panel):
  - Product search input (300ms debounced) queries `/api/partner/inventory?q=...&limit=30&offset=0` — i.e. searches the requesting **distributor's own** partner-scoped inventory view of the catalog (same endpoint as `products.md`), flattened into variant options labeled `"{product} - {variant}[ - {color}] - {sku}"`.
  - Variant `<Select>` + quantity `<Input>` (min 1) + "إضافة" (add line) button, disabled until a variant is selected.
  - Draft lines table: adding an already-present variant sums its quantity into the existing line rather than duplicating; each line has a trash-icon remove button.
  - Notes `<textarea>` (free text, optional).
  - "إرسال الطلب" (submit) button, disabled while submitting or when the draft has zero lines (client-side guard mirrors a server-side "at least one item" check). On success: clears the draft form (lines + notes + product search), reloads the requests list below, shows a success toast.
  - `POST` body: `{ notes, items: [{ variantId, quantity }] }`. **`sourceAgentPartnerId` is never sent by this UI** — server resolves it from `destination.linkedAgentId` (the distributor's own `Partner.linkedAgentId`) automatically; the API does technically accept an explicit `sourceAgentPartnerId` override but this form has no field for it (see Notes).
  - Server-side validation (`createRestockRequest`): destination partner must exist and be `partnerType: "DISTRIBUTOR"`; resolved source partner must exist and be `partnerType: "AGENT"`; a distributor with no `linkedAgentId` set gets a generic 400 ("Distributor has no linked source agent") surfaced via `apiBadRequest`, i.e. shown as whatever raw message the thrown `Error` carries (not a friendlier Arabic message — see Edge cases).
- [ ] **Past requests table** (`"طلبات سابقة"` panel): columns الحالة (status badge — colors: FULFILLED/APPROVED→default, REJECTED/CANCELLED→destructive, PENDING→secondary), الوكيل (`sourcePartner.name` — the agent), الأصناف (each line as `"{product} · {sku} × {qty}"`, stacked), ملاحظاتك (`notes`, the distributor's own submitted notes), رد الوكيل (`responseNotes`, the agent's reply — "—" if none yet), التاريخ (`formatDateEn(createdAt)`). **Read-only** — no action buttons on this screen (approve/reject/fulfill only exist on the agent-facing `distributor-requests.md` screen).

## States
- [ ] Empty state — no past requests yet: `EmptyState` "لا توجد طلبات إعادة توريد".
- [ ] Loading state — past-requests panel shows a centered spinner + "جاري التحميل" while the initial GET is in flight; the new-request form renders immediately regardless (not gated on the list load).
- [ ] Error state — list-load failure: destructive toast ("فشل تحميل طلبات إعادة التوريد" + server message if present); table area is left empty/stale, no inline retry beyond the page's "تحديث" button. Submit failure: no explicit toast title differing from generic — errors bubble as `json?.error?.message ?? "فشل إرسال الطلب"`.
- [ ] Permission-restricted state — **an AGENT visiting this URL directly is not blocked by any client-side check.** They see the exact same page (form + "موزعون فقط" badge + their own list of *incoming* requests via the shared GET, i.e. this becomes a read-only mirror of `distributor-requests.md`'s data but without any approve/reject/fulfill buttons). If an agent fills out and submits the "new request" form anyway, the POST 403s and they get a destructive toast with the raw Arabic message "طلبات إعادة التوريد متاحة للموزعين فقط" — the only signal that this screen isn't meant for them.

## Edge cases
- [ ] Distributor with no linked agent (`Partner.linkedAgentId` is null and no override is passed) — submit fails with an **untranslated English error string** ("Distributor has no linked source agent") surfaced via the generic `apiBadRequest(error.message)` catch-all in the route handler, breaking the otherwise all-Arabic error messaging on this screen. `[NEEDS PM INPUT: is this a known gap, or should it be caught and given a proper Arabic message before/during redesign?]`
- [ ] Submitting a request for a quantity the agent doesn't currently have in stock — the request is still created successfully (no stock check happens at *creation* time, only at *fulfillment* time on the agent's side); the distributor has no way to know from this screen whether the request is fulfillable until the agent acts on it.
- [ ] Rapid duplicate submissions (double-click "إرسال الطلب") — no explicit debounce/idempotency guard visible beyond the button's own `disabled={submitting || ...}` state, which should prevent a true double-submit as long as the button disables synchronously.
- [ ] A request the agent has already `APPROVED` but not yet `FULFILLED` — still shows in this list with no distributor-side way to remind/nudge, cancel, or otherwise act on it; it simply sits as "مقبول" until the agent independently fulfills or the distributor manually follows up out-of-band.

## Notes
- **This screen has no server-enforced role redirect** — unlike some other partner surfaces, an AGENT can load `/partner/restock-requests` and see a functional-looking (if action-less) page. The "موزعون فقط" badge is purely a label, not a gate. It is, however, absent from the AGENT nav entirely (`PartnerShell`'s `AGENT_NAV_ITEMS` has no entry for it) — so in normal use an agent would never land here except by guessing the URL or an old bookmark.
- The create-request API technically supports an explicit `sourceAgentPartnerId` (letting a distributor request from an agent other than their linked one), but **this UI never exposes that field** — every request created from this screen goes to the distributor's single `linkedAgentId`. If the business model allows a distributor to have relationships with multiple agents, that capability exists at the API layer but is currently invisible in the UI — flag for PM: `[NEEDS PM INPUT: is multi-agent sourcing per distributor a real scenario, or is the single-linked-agent model intentional and final?]`
- This screen and `distributor-requests.md` are two faces of the exact same `RestockRequest` resource and the exact same GET endpoint — build them as a shared component/view model where practical in the rebuild (list rendering, status badge logic, and item-line rendering are already byte-for-byte duplicated between the two page files today), but keep the action buttons (approve/reject/fulfill) strictly on the agent-facing view per the ownership check in the PATCH endpoint (`request.sourcePartnerId !== user.partnerId` → 403).
