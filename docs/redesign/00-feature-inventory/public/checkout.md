# Public — Checkout

Route(s): `app/(public)/checkout/page.tsx`
Key files: `lib/checkout/types.ts`, `lib/checkout/summary.ts`, `lib/checkout/place-order.ts`, `lib/checkout/cod-fee.ts`, `lib/checkout/instapay.ts`, `lib/services/pricing.ts` (coupon + senior discount), `lib/services/shipping.ts`, `lib/shipping/egypt-post-phase1/*` (zone/weight rate calculator), `lib/inventory/partner-inventory.ts` (partner stock reservation/fulfillment), `lib/rerouting/assign.ts` (post-order courier/partner assignment), `lib/addresses/completeness.ts`, `lib/phone.ts` (Egypt mobile validation), `lib/settings.ts` (senior-promo toggle, COD-fee percent), `lib/storefront-location.ts` (authoritative delivery-partner resolution), `app/api/checkout/summary/route.ts`, `app/api/checkout/place-order/route.ts`, `app/api/profile/addresses/*` (saved-address read/save/patch, called from this screen)

**This is the highest-risk surface in the redesign per explicit PM decision — every payment branch, validation rule, and failure path below was traced directly from the route handlers and business-logic modules, not inferred from UI text.**

## Business requirements
- **Goal/KPI**: final conversion step — must not silently lose orders. Every failure path below returns a specific, user-facing Arabic error rather than a generic failure, which is a deliberate trust/support-load design choice (fewer "why didn't my order go through" support tickets) that a rebuild must preserve message-for-message where reasonably possible, not just functionally.
- **Trust/credibility signals**: full cost breakdown before commit (subtotal, coupon discount, shipping, COD fee when applicable, grand total) with a live-recalculating summary; explicit payment-method framing ("الدفع عند الاستلام" / Cash on Delivery vs. "الدفع عبر InstaPay" / InstaPay prepaid) including a green "شحن أقل عند الدفع عبر InstaPay" (lower shipping with InstaPay) hint — see Notes for why this claim is really about the COD fee, not the carrier shipping rate; explicit "تأكيد الطلب" (confirm order) button only enabled once a valid summary exists.
- **Friction points**: checkout is **login-gated with no guest checkout** — a shopper with a full cart who is not logged in sees only a "سجّل الدخول أو أنشئ حساباً لإتمام الطلب" prompt (login/register links) with no way to check out as a guest, which is a plausible, measurable source of cart abandonment given the cart itself never required login. Delivery address requires **both** a saved-address system (governorate/city/area/street/phone) **and** a separate site-wide "storefront delivery location" cookie (set via the floating `GovernorateSelector`, not on this page) that is the sole authority for which partner fulfills the order — a shopper can fill in and save a checkout address for a governorate different from their storefront-location cookie's governorate, and the order will still be fulfilled/priced/routed based on the **cookie's** governorate, not the address typed into the checkout form (see Elements — "Authoritative partner resolution"). This is a subtle, high-risk area for the rebuild to get wrong.
- **Compliance/legal**: Egyptian mobile-number format is strictly validated (must be a real `01[0125]xxxxxxxx` number via `libphonenumber-js`) before an order can be placed, both at summary-preview and at place-order time, server-side — this is a hard requirement worth preserving exactly (see Elements/Edge cases).
- **URL/SEO stability**: `/checkout` should not be indexed (transactional page); no special metadata beyond defaults.
- **Business-critical nuance for the rebuild**: this order-placement flow directly reserves real partner inventory inside a database transaction (see Elements — "Stock reservation / commit") — any UI rebuild that changes *when* place-order is called (e.g. optimistic UI, retries, double-submit prevention) must not change the underlying "exactly-once, transactional, partner-authoritative" placement semantics.

## Elements & behavior

### Access gating
- [ ] Auth check on mount — `GET /api/auth/me`; `401` → guest state (see States); success → stores `profilePhone` for prefill. No server-side/middleware redirect exists for `/checkout` (confirmed: `middleware.ts` only matches `/admin/*` and `/partner/*`) — the login gate is entirely client-side JS, meaning a non-JS or slow-JS client briefly sees the checkout shell before the guest prompt swaps in.
- [ ] Guest state — "سجّل الدخول أو أنشئ حساباً لإتمام الطلب" card with "تسجيل الدخول" (`/login?redirect=/checkout`), "إنشاء حساب" (`/register?redirect=/checkout`), and "العودة للسلة" (back to cart) links. Cart is **not** touched/cleared for a guest reaching this screen.
- [ ] Mid-session expiry — if the session cookie expires while the shopper is already on the checkout page (summary fetch or place-order call returns `401`), the page `router.replace`s to `/login?redirect=/checkout` without any toast/explanation of *why* they were bounced.

### Delivery address
- [ ] Saved addresses fetch — `GET /api/profile/addresses` (only when logged in). If any exist: the default address (or first) is pre-selected (`isDefault` flag, else index 0); if none exist: the "new address" form is shown by default.
- [ ] Saved-address picker — each saved address rendered as a selectable card (governorate/city/area/street summary line, phone, optional label, "افتراضي" default badge). Selecting one sets it as the active checkout address.
- [ ] Legacy-incomplete saved address ("يحتاج المدينة" / needs city badge) — addresses created before `city` was a required field are missing it (`isSavedAddressIncomplete`: `!city.trim()`). Selecting one of these shows an inline amber-bordered panel demanding city input (`pendingCity` state) before that address can be used; on order placement, this city is **persisted back onto the saved address** via `PATCH /api/profile/addresses/{id}` (so the shopper only has to complete it once, and future orders reuse the completed address) — this patch happens for *both* the COD/direct path and the InstaPay-confirm path, right before `place-order` is called.
- [ ] "إضافة عنوان جديد" (add new address) — switches to a full new-address form: تسمية (label, optional), المحافظة (governorate, required `<select>` sourced from `GOVERNORATE_OPTIONS` — a fixed list of all 27 Egyptian governorates), المدينة (city, required free text), هاتف التوصيل (delivery phone, required, `dir="ltr"`), المنطقة (area, required free text), العنوان بالتفصيل (street/detailed address, required free text), ملاحظات (notes, optional). Governorate has no cascading "city" dropdown — city is always free text even though a fixed governorate list exists.
- [ ] New-address auto-save — whenever `useNewAddress` is true and the order is placed successfully (either path), the typed address is also `POST`ed to `/api/profile/addresses` as a new saved address **before** `place-order` is called — i.e. the address is persisted even if `place-order` itself then fails, so a failed order attempt still leaves the address saved for next time.
- [ ] Delivery-phone prefill — when showing the new-address form, `address.phone` is prefilled from the logged-in shopper's account phone number if empty (does not override an already-typed value).
- [ ] Address completeness gate — `isCheckoutAddressComplete`: governorate, city, area, street, phone **all** must be non-empty (trimmed); floor/apartment/notes are optional. This exact check gates both the summary fetch (below) and the final place-order submit — an incomplete address never triggers a summary calculation and blocks submission with a toast ("اختر عنوان توصيل أو أكمل البيانات...").

### Payment method
- [ ] Two selectable options only (`CHECKOUT_PAYMENT_OPTIONS`): **الدفع عند الاستلام** (COD, value `"COD"`, default-selected) and **الدفع عبر InstaPay** (`"INSTAPAY_PREPAID"`). A third value, `"PAYMOB"`, exists in the underlying type system (`PAYMENT_METHODS`, order/place-order validation, `PaymentAttempt.provider`) and is fully supported end-to-end by the backend (treated identically to COD as an "immediate confirm" method) but has **no UI affordance anywhere on this page** — it cannot currently be selected by a shopper. Do not remove PAYMOB from backend types/validation in the rebuild without an explicit PM decision; it appears to be an intentionally-dormant future payment integration, not dead code.
- [ ] Radio-style selection; selecting INSTAPAY_PREPAID shows a green hint line directly under that option: "شحن أقل عند الدفع عبر InstaPay" (lower shipping with InstaPay — see Notes for the precise mechanism, which is the COD fee being dropped, not a lower carrier rate).
- [ ] Changing payment method re-triggers the summary calculation (COD fee only applies when `paymentMethod === "COD"`; see Pricing below).

### Coupon
- [ ] Free-text "الرقم التسلسلي للخصم" (discount code) input, always visible in the summary panel regardless of whether a summary has loaded yet.
- [ ] Coupon is **not** applied automatically as the shopper types — a separate "طبق" (apply) button must be clicked, which copies the typed value into `appliedCouponCode` (the value actually sent to the API); typing alone never triggers a recalculation.
- [ ] An "X" clear button appears once either the input has text or a coupon is currently applied; clears both the typed text and the applied code.
- [ ] Invalid/expired/inapplicable code — the summary API silently returns `appliedCouponCode: null` and `couponDiscount: 0` (no error status) rather than rejecting the request; the UI infers invalidity from this ("كود الخصم غير صالح أو منتهي الصلاحية." shown when `couponCode` is non-empty but `summary.appliedCouponCode` is falsy).
- [ ] Server-side coupon validation (`lib/services/pricing.ts`, `getCouponDiscount`) — code matched case-normalized to uppercase; must be `active: true`, within `validFrom`/`validUntil` window, subtotal-after-senior-discount must meet `minOrderPiastres` (default 0), and `usedCount < maxUses` if `maxUses` is set. Three discount shapes: `PERCENT` (1–100%, floored), `FIXED` (flat piastres, capped at the subtotal), `BOGO_QTY` ("buy N get M free" — see Notes for the exact algorithm).
- [ ] **Coupons and the senior "buy-2-get-3rd-free" promo never stack** — if the senior discount applies (see below), any coupon code is silently ignored server-side (`couponCodeWhenSeniorApplies = seniorDiscountPiastres > 0 ? null : couponCode`) with **no UI messaging explaining why** a shopper's coupon appears not to apply if they also qualify for the senior promo.

### Order summary / pricing (`GET-equivalent via POST /api/checkout/summary`, debounced 500ms after address/coupon/payment-method changes)
- [ ] Subtotal — sum of `quantity × unitPricePiastres` across all cart lines (server re-reads the cart fresh each time, not client-trusted).
- [ ] Senior discount — applies **only** if both `SiteSetting.senior_promo_enabled === "true"` (admin-toggleable, cached 60s) **and** the logged-in shopper's `User.seniorVerified === true` (separate national-ID verification flow, not part of this screen). Mechanic: every group of 3 units across the *entire cart* (pooled across all lines, not per-product) makes the single cheapest unit in that group of 3 free (units sorted ascending, grouped in chunks of 3, first of each full chunk is free). Not shown as a distinct line unless non-zero (`seniorFreeValue`).
- [ ] Coupon discount — see Coupon section above; shown as "خصم كود" only when `couponDiscount > 0`.
- [ ] Shipping fee — Phase 1 Egypt Post "Wasalha" carrier only (no carrier choice). Computed from **cart weight** (`sum(quantity × Product.weightGrams)` — if **any** cart line's product has `weightGrams == null`, the whole summary calculation fails, see Edge cases) and the delivery address's **governorate** (mapped to one of 6 shipping zones — CAIRO_METRO/ALEX_DELTA/CANAL/NORTH_UPPER/SOUTH_UPPER_REDSEA/REMOTE — via a hardcoded Arabic-name lookup table; unrecognized governorate text also fails the whole summary, see Edge cases). Customer-facing fee = carrier base rate (by zone, first 2kg flat then +7 EGP/kg) + 14% VAT + 0.50 EGP insurance, **plus** a shop margin (10% of base+extra-weight, floor 5 EGP) **plus** a flat 8 EGP prep-service fee — the margin and prep fee are addded to what the customer pays but are explicitly excluded from the "carrier-facing" shipping amount recorded separately (`carrierShippingPiastres`) for courier/partner export purposes.
- [ ] COD fee — **only** added when `paymentMethod === "COD"`; computed as a percentage (`SiteSetting.cod_fee_percent`, admin-configurable, cached 60s, default 0) of `(subtotal − discounts + shippingFee)`, with a hard floor of 5 EGP (`COD_FEE_MIN_PIASTRES = 500` piastres) whenever the percentage is > 0. If the admin-configured percent is 0, the COD fee is 0 (no floor applied). **This is the entire mechanism behind the "شحن أقل عند الدفع عبر InstaPay" claim** — the carrier/shipping rate itself is identical for both payment methods; only the COD fee (displayed folded into the same "رسوم الشحن" line in the UI: `shippingFee + (paymentMethod === "COD" ? codFee : 0)`) differs. A rebuild should not literally implement "InstaPay gets cheaper shipping" as a separate shipping-rate rule — it must replicate this fold-in-COD-fee-only mechanism or the totals will not match.
- [ ] Final total — `subtotal − seniorDiscount − couponDiscount + shippingFee + codFee` (all in integer piastres server-side; the UI divides by 100 for display, rounding for values ≥ 1 EGP and keeping 2 decimals only for sub-1-EGP amounts via `piastresToEgpDisplay`).
- [ ] Cart line-items snippet — shown in the summary panel regardless of whether a full price summary has resolved yet (first 6 lines, "+N more" not shown — lines beyond 6 are simply omitted with no "and N more" indicator).
- [ ] Pre-address state — before a complete address is selected/entered, the summary panel shows the raw cart subtotal with "الشحن: يُحسب بعد إكمال العنوان" (shipping calculated after address is completed) instead of a real shipping number, and the total shows the same "calculated after address" placeholder rather than a number.

### Place order — COD / PAYMOB path (immediate)
- [ ] Triggered by the form's "تأكيد الطلب" submit button (disabled while `!summary || placeLoading`).
- [ ] Validates address completeness client-side (toast if incomplete) and that a `summary` already resolved (toast "انتظر تحميل الملخص أو تحقق من العنوان" if not) before calling the API.
- [ ] If the currently-selected saved address is legacy-incomplete, persists the just-entered city to it first (`PATCH`), aborting the whole flow silently returning early (no order placed) if that patch fails.
- [ ] If using a new address, `POST`s it to `/api/profile/addresses` first (fire-and-forget relative to success — order placement proceeds even if this save call isn't awaited-checked for success).
- [ ] Calls `POST /api/checkout/place-order`. On success: "تم إنشاء الطلب بنجاح" toast, `refreshCart()` (cart is now empty), navigate to `/profile/orders`, `router.refresh()`.
- [ ] On failure: destructive toast with the server's Arabic error message (see the full error-code table under Edge cases).

### Place order — InstaPay prepaid path (two-step, modal-gated)
- [ ] Selecting "تأكيد الطلب" while `paymentMethod === "INSTAPAY_PREPAID"` does **not** place the order — it opens an instructions modal instead (`instaPayModalOpen`), without calling any API yet.
- [ ] Modal content — a QR image and a tappable InstaPay address (IPA) text. **The IPA/QR shown depends on which partner the order is resolved to fulfill** (`getInstapayDetailsForPartner(summary.partnerName)`): the default account (`gamalelasabdul@instapay` / `instapay-qr.jpeg`) for every partner **except** a partner literally named `"AlJamal Home"` in the database, which gets a distinct account (`elhussein11@instapay` / `instapay-qr-aljamal.jpeg`). This match is by **partner display-name string equality**, not a partner id/flag — see Notes for why this is fragile.
- [ ] Tapping the IPA text — attempts to copy it to the clipboard (best-effort, swallowed on failure) and shows a "تم نسخ عنوان الدفع" toast; on mobile devices (`android|iphone|ipad|ipod` UA sniff) it also attempts to deep-link directly into the InstaPay app (Android: `intent://` scheme with a Play Store fallback URL; iOS/other mobile: `instapay://send?...` custom scheme) pre-filled with the IPA and, when known, the exact order amount. On desktop, the link resolves to `"#"` (no-op) and instead opens the appropriate app-store link (iOS App Store vs. Google Play, UA-sniffed) in a new tab.
- [ ] Modal shows the exact amount to transfer ("المبلغ: {finalTotal} ج.م").
- [ ] "أتممت التحويل" (I've completed the transfer) button — this is what **actually places the order** (same address-completeness re-validation, same legacy-city-patch, same new-address auto-save as the COD path, then the same `POST /api/checkout/place-order` call, this time with `paymentMethod: "INSTAPAY_PREPAID"`).
- [ ] On success: closes the InstaPay modal, opens a **separate** non-dismissible-by-overlay-click success modal ("تم إرسال طلبك بنجاح" / your order was sent successfully, with copy explaining a confirmation call/SMS will follow) — deliberately does **not** call `refreshCart()` at this point, specifically so the cart page doesn't flash to its empty state while this modal is still up (code comment confirms this is intentional). Only clicking "تم" inside the success modal triggers `refreshCart()`, navigation to `/profile/orders`, and `router.refresh()`.
- [ ] Backend order state for this path — order is created with `status: "CREATED"` (not `"CONFIRMED"`), a `PaymentAttempt` row with `status: "PENDING"` is recorded, and **stock is reserved but not committed** (see Stock reservation below) — an admin must manually confirm or cancel the order after verifying the InstaPay transfer arrived; there is no automated payment verification, no timeout/auto-expiry (the `Order.reservationExpiresAt` column exists but is explicitly documented in the schema as legacy/unused — "admin decides, no auto-expiry").
- [ ] Cancelling out of the InstaPay modal ("إلغاء") — no order is placed, no API call made, returns to the checkout form with the selected payment method still set to InstaPay.

### Authoritative partner resolution (applies to both payment paths)
- [ ] The delivery **partner** who will fulfill/ship the order — and therefore whose live inventory gates whether the order can be placed at all — is resolved from the shopper's site-wide **storefront-location cookie's governorate** (set via the floating `GovernorateSelector`, the same mechanism used for browsing/cart stock, documented in `home.md`/`cart.md`), **never** from the governorate typed/selected in this checkout form's delivery address. A shopper who selected "Cairo" in the location picker but is shipping this specific order to a relative in "Giza" (typed into the checkout address form) still gets Cairo's partner and Cairo's resolved stock — this is a deliberate design choice (the code comments confirm: "never re-derive a partner from the delivery address's governorate... would otherwise silently swap to a different partner than the one whose stock the customer saw"), not a bug, but it is very easy for a UI rebuild to get subtly wrong (e.g. by wiring "resolve partner" to the checkout form's own governorate field instead of the global cookie).
- [ ] If no storefront-location governorate is set at all when `place-order` is called — hard-rejected with `apiBadRequest("اختر محافظة التوصيل من أعلى الصفحة أولاً", { code: "GOVERNORATE_NOT_SELECTED" })` ("choose your delivery governorate from the top of the page first") — note this error explicitly references a UI element (the floating location picker) that is **not part of the checkout page itself**, so a shopper hitting this on checkout must go find that separate control elsewhere in the layout.
- [ ] If the resolved partner cannot fully cover every cart line's quantity — the order is rejected outright with a specific, itemized message: "الأصناف التالية غير متوفرة حالياً، برجاء إزالتها من السلة: {variant names}" (the following items are currently unavailable, please remove them from your cart), `code: "INSUFFICIENT_STOCK"`, plus a structured `outOfStockItems` array (variantId/sku/productName/variantName) in the response for programmatic use. **There is no fallback to a different partner** — this is a hard failure naming exact items, by design (per code comments: the customer never saw stock from any other partner, so silently substituting one would be misleading).
- [ ] If literally no partner is configured at all for the resolved governorate — `code: "NO_PARTNER_CAN_FULFILL_CART"`, generic message "الأصناف المطلوبة غير متوفرة لدى شريك واحد في هذه المحافظة".

### Stock reservation / commit (transactional, inside `placeOrder`)
- [ ] All of the following happens inside one Prisma transaction (`maxWait: 15s`, `timeout: 60s`): create the `Order` row, reserve partner stock (`stockReserved += qty` per line, row-locked via `SELECT ... FOR UPDATE`), create `OrderItem` snapshot rows (product/variant name, SKU, price all snapshotted at order time — later catalog edits never retroactively change a placed order's recorded details), write an audit-log "created" event.
- [ ] COD/PAYMOB (immediate-confirm methods) additionally, in the same transaction: set `Order.status = "CONFIRMED"`, commit the reservation (`stockAvailable -= qty, stockReserved -= qty` — i.e. actually decrements real inventory, not just reserves it), write a `PaymentAttempt` with `status: "CAPTURED"`, write a "confirmed" audit event.
- [ ] INSTAPAY_PREPAID: order stays `status: "CREATED"`, stock stays **reserved but not committed** (still shows as unavailable to other shoppers via the same partner, but not yet deducted from real available count), `PaymentAttempt` written as `PENDING`.
- [ ] Coupon usage — if a coupon was applied, a `CouponUsage` row is created and `Coupon.usedCount` incremented, inside the same transaction (so a failed transaction never over-counts usage).
- [ ] Cart clearing — all cart items for that user are deleted inside the same transaction once the order is successfully created (both payment paths) — this happens at the API/DB level regardless of when the client-side `refreshCart()` call happens to run (the InstaPay UI's delayed `refreshCart()` is purely about avoiding a premature empty-cart *flash* in the UI; the cart is already empty server-side as soon as `place-order` returns success).
- [ ] Post-transaction, non-blocking: `assignOrderToGovernorate(orderId)` creates a `RoutedOrder` record assigning the order to the same already-selected partner (or marks it `UNROUTED` if something is inconsistent) for the partner-facing order queue; failures here are caught and logged (`console.error`) but **never surfaced to the shopper or rolled back** — the order itself has already successfully been placed by this point regardless of routing outcome. Analytics cache is also invalidated after this (`invalidateAnalyticsCache()`).

## States
- [ ] Empty state — "السلة فارغة. أضف منتجات ثم عد للدفع." (cart is empty, add products then come back) with a "عرض السلة" button → `/cart`, shown when the cart has zero items **and** the InstaPay success modal is not currently open (a deliberate exception so the success modal stays visible through the moment the cart empties — see InstaPay path above).
- [ ] Loading state — "جاري التحقق…" (checking…) full-page text while the initial auth check is in flight; "جاري تحميل العناوين المحفوظة…" while saved addresses load; "جاري الحساب…" (calculating…) replacing the summary panel while a summary recalculation is in flight (500ms-debounced); submit button label swaps to "جاري إنشاء الطلب…" while `placeLoading`/`instaPayConfirmLoading`.
- [ ] Error state — no page-level error boundary; every failure surfaces as a destructive toast with the specific server message (see the error-code table below) rather than blocking the whole page. A summary-calculation failure clears `summary` to `null`, which re-collapses the panel to the pre-address placeholder state and disables the submit button, but does not show a dedicated inline error unless the response was a genuine non-401 failure (in which case a toast does fire: "تعذر حساب الملخص" or the server's specific message).
- [ ] Permission-restricted state — login-gated (see Access gating above); no role/tier restriction beyond "must be logged in as any role" (`requireCustomer()` — any `UserRole`, not customer-specific in the RBAC sense despite the function name).

## Edge cases (place-order failure codes, verified from `lib/checkout/place-order.ts` and both API routes)
- [ ] `GOVERNORATE_NOT_SELECTED` — "اختر محافظة التوصيل من أعلى الصفحة أولاً" — storefront-location cookie unset.
- [ ] `INVALID_CHECKOUT` — "السلة فارغة، أو وزن منتج ناقص، أو لا يمكن حساب الشحن لهذا العنوان" (cart empty, OR a product's weight is missing, OR shipping can't be computed for this address) — **one message covers three distinct root causes**; the shopper (and a support agent) cannot tell from the message alone which one actually happened. This is the single highest-risk message to get right in a rebuild: at minimum, preserve the same ambiguity rather than inventing a more specific message that isn't backed by more specific server-side diagnostics, since doing so would create a UI/backend mismatch.
- [ ] `EMPTY_CART` — "السلة فارغة" — cart became empty between summary calculation and place-order submission (e.g. two tabs, or an item silently pruned by a governorate change mid-checkout).
- [ ] `INVALID_ITEM` — "صنف غير متاح في الطلب" — a cart line's product was deactivated between summary and place-order.
- [ ] `INSUFFICIENT_STOCK` — itemized message naming exact unavailable variants (see Authoritative partner resolution above); also returned as a thrown-exception path (`InsufficientStockError`/`InsufficientPartnerStockError`) with a less specific generic message ("Insufficient stock for item" — **this fallback message is in English, not Arabic**, an inconsistency worth flagging since every other user-facing string on this page is Arabic) if the race is detected inside the transaction rather than in the pre-transaction fulfillability check.
- [ ] `NO_PARTNER_CAN_FULFILL_CART` — "الأصناف المطلوبة غير متوفرة لدى شريك واحد في هذه المحافظة".
- [ ] `ORDER_TOTAL_TOO_LARGE` / `LINE_AMOUNT_TOO_LARGE` — "قيمة الطلب تتجاوز الحد المسموح. قلّل الكميات أو قسّم الطلب." — guards against any computed total/line amount exceeding Postgres `Int` range (2,147,483,647 piastres ≈ 21.4M EGP); extremely unlikely in practice but present as a real guard.
- [ ] `TRANSACTION_TIMEOUT` (Prisma `P2028`) / `TRANSACTION_CONFLICT` (Prisma `P2034`) — "استغرقت معالجة الطلب وقتاً أطول من المتوقع (سلة كبيرة أو ازدحام). أعد المحاولة بعد لحظات." (processing took longer than expected — large cart or contention; try again shortly) — surfaces real DB contention/lock-timeout scenarios to the shopper as a retry-able message rather than a generic failure.
- [ ] `ORDER_PERSIST_FAILED` — any other Prisma known-error during the transaction — "تعذر إتمام الطلب. إذا تكرر ذلك، تواصل مع الدعم." (couldn't complete the order; contact support if this repeats).
- [ ] Phone validation failure — `EGYPT_MOBILE_ERROR_MESSAGE`: "رقم الجوال يجب أن يكون رقم مصري صحيح يبدأ بـ 010 أو 011 أو 012 أو 015" (must be a valid Egyptian mobile starting with 010/011/012/015) — enforced via `libphonenumber-js`'s `"EG"` mobile parser plus an explicit national-number regex (`^(10|11|12|15)\d{8}$`), both at summary-preview time and place-order time, so a malformed phone is caught before an order is ever attempted, not just at final submit.
- [ ] Missing product weight (`Product.weightGrams == null`) anywhere in the cart — silently folds into the generic `INVALID_CHECKOUT` message above rather than naming which product is missing weight data; this is an admin/catalog-data-quality issue that surfaces as an opaque checkout failure to the shopper with no actionable next step besides contacting support.
- [ ] Unrecognized/unmappable governorate text reaching the shipping calculator — also folds into `INVALID_CHECKOUT`; in practice this shouldn't happen since the checkout form's governorate field is a closed `<select>` sourced from the same `GOVERNORATE_OPTIONS` list the zone-mapping table's keys are built from, but a saved address created via a different code path (e.g. admin-entered, or historical data) with free-text/mistyped governorate spelling could still trigger it.
- [ ] Admin toggles `senior_promo_enabled` or `cod_fee_percent` mid-session — both are cached 60s server-side (`unstable_cache` with `revalidateTag` on admin write, so an admin's own save is instant, but another shopper's in-flight checkout session could see the old value for up to 60s after) — a shopper's summary could show a different total than what actually gets charged if they take longer than that window between summary calculation and final submit, though in practice the 500ms-debounced summary refetch on every keystroke/change makes this a narrow window.

## Notes
- **The "InstaPay = lower shipping" framing is a display artifact, not a real shipping-rate difference.** The carrier/shipping fee (`shippingFee`) is identical for both payment methods; only the COD fee (added only for COD, with a 5 EGP floor) differs, and the UI happens to fold the COD fee into the same "رسوم الشحن" (shipping) line item rather than showing it as its own line. A rebuild that treats this as "InstaPay gets a shipping discount" and tries to model it as a rate adjustment will produce wrong totals — it must replicate the exact fold-in-COD-fee-into-shipping-display mechanism, or split it into an honestly-separate "COD fee" line (a legitimate UX improvement to propose via `02-proposals.md`, but not silently in the parity pass).
- **Partner-name string matching for InstaPay account selection is fragile.** `getInstapayDetailsForPartner` branches on `partnerName === "AlJamal Home"` — an exact string match against the `Partner.name` field, not a stable id/flag. If that partner is ever renamed in the admin, checkout silently reverts every affected shopper to the *default* InstaPay account/QR without any error — payments would go to the wrong account with no system-level warning. This is the single most operationally dangerous piece of logic found in this entire inventory pass; strongly recommend the rebuild (or even a pre-redesign hotfix) replace this with a stable field (e.g. a `Partner.instapayIpa`/`instapayQrImageUrl` column) rather than preserving the string-match as "parity."
- **Address governorate ≠ fulfillment governorate.** This is the single most likely thing a UI-focused rebuild gets wrong: the checkout form's own governorate `<select>` only affects shipping-fee calculation and the shipping-address record; it has **zero effect** on which partner's stock is checked/reserved or which InstaPay account is shown. That's entirely driven by the separate, layout-level storefront-location cookie. A rebuild must keep these two governorate concepts architecturally distinct, not collapse them into "the governorate on the checkout form."
- The InstaPay success modal's deliberate delay of `refreshCart()` until the shopper clicks "تم" is a specific, intentional UX choice (confirmed by an inline code comment) to prevent the empty-cart view from flashing underneath the success modal — a rebuild should preserve this sequencing, not "simplify" it by refreshing immediately on order success.
- `PAYMOB` is a fully-wired-but-UI-dormant third payment method (see Payment method section) — confirm with PM/engineering whether it's planned for imminent launch (in which case the rebuild should leave an obvious extension point) or truly deprecated (in which case removing the dead branches is in scope, but that's a product decision, not something to assume from the code alone).
- Saved-address auto-completion (typing a new address at checkout silently also creates/updates a `SavedAddress` row) means the checkout page has real side effects on the shopper's address book beyond just placing the order — a rebuild's checkout form is not "just a form that posts an order," it's also implicitly an address-book write path, which affects how it should handle partial failures (e.g. address saved but order placement failed — the address save is not rolled back).
