# Public — Profile Senior (senior-citizen discount verification)

Route(s): `app/(public)/profile/senior/page.tsx` (wrapped by the same `app/(public)/profile/layout.tsx` shell as orders/addresses/account — but **not** linked from `app/(public)/profile/profile-nav.tsx`)
Key files: `app/api/profile/senior/route.ts`, `lib/senior/verify.ts` (`verifyAndStoreSeniorId`, `getSeniorStatus`), `lib/senior/egypt-id.ts` (`parseEgyptianNationalId`), `lib/senior/encrypt.ts`, `lib/services/pricing.ts` (`computeSeniorDiscount`), `app/api/settings/senior-promo/route.ts`, `app/(admin)/admin/senior-promo-toggle.tsx`, Prisma models `User.seniorVerified`, `SeniorVerification`, `SiteSetting`

## Business requirements

**Framing correction — read before scoping accessibility work around this screen.** The task brief for this redesign assumes `/profile/senior` is a deliberately simplified, accessibility-oriented UI variant of the profile section for older/less tech-savvy users (larger text, fewer options, alternate navigation, etc.). **That is not what this route is.** Verified against the actual code:

- `/profile/senior` is a single-purpose **senior-citizen (60+) discount eligibility verification page**. A customer submits their 14-digit Egyptian national ID once; the server validates it, confirms the holder is 60+ from the ID's embedded birthdate, and — if valid and not already used on another account — permanently sets `User.seniorVerified = true`. This unlocks a site-wide pricing promotion ("buy 2, get the cheapest of every 3 items free," computed in `lib/services/pricing.ts`) that is separately gated on/off globally by an admin toggle (`app/(admin)/admin/senior-promo-toggle.tsx` → `SiteSetting` row, read via `/api/settings/senior-promo`).
- **Visually and structurally this page is identical to the rest of the profile section** — same `ProfileLayout` chrome/sidebar, same font sizes, same card and form-input styling as account/addresses/orders. There is no larger text, no reduced navigation, no alternate simplified checkout/ordering flow anywhere in the codebase for older users. A repo-wide search for accessibility-mode toggles, "simplified" UI variants, or alternate layouts found nothing beyond this one narrow discount-verification form.
- **If genuine accessibility improvements for older/less tech-savvy users are a goal of this redesign, that is net-new work, not something to reverse-engineer from this route.** Recommend the PM explicitly re-scope this as a fresh accessibility proposal (`02-proposals.md`) rather than treating this file as a parity spec for "the senior variant."
- **Goal/KPI (of the feature as it actually exists)**: a targeted loyalty/discount mechanic for elderly customers, likely a differentiator + AOV driver via the "buy more, save more" structure, gated behind lightweight KYC (national-ID age proof) to prevent abuse.
- **Discoverability gap (real, worth flagging)**: this page is not linked from `ProfileNav` (only طلباتي/عناويني/حسابي appear there), and a search of the entire `app/` and `components/` trees found **no other link to `/profile/senior` anywhere** — no banner, no checkout callout, no account-page mention, no promo popup. A customer can only reach this screen by typing the URL directly. The admin-side promo toggle exists, but nothing in the customer-facing UI currently advertises either the offer or this verification page.
- **Sensitive-data handling**: the national ID is the most sensitive PII this app collects. It is encrypted at rest (`nationalIdEncrypted`, AES-256 per the model's own comment); only a SHA-256 fingerprint and the last 4 digits are otherwise queryable/displayable; the full ID is never returned to the client, even post-verification. The fingerprint is checked for uniqueness across **all** accounts, preventing the same ID from verifying two different users.

## Elements & behavior
- [ ] On mount: `GET /api/profile/senior`; a `401` uses **`router.replace()`** (soft client-side navigation) to `/login?redirect=/profile/senior` — note this differs from the hard `window.location.href` redirect pattern used on the account/addresses/orders pages.
- [ ] Static intro copy is shown **unconditionally**: "إذا كان عمرك 60 عاماً أو أكثر، يمكنك الاستفادة من عرض شراء 2 واحصل على الأرخص مجاناً لكل 3 قطع." This page never checks `/api/settings/senior-promo` — verification eligibility and promo enablement are two independent systems this screen does not reconcile, so the invitation to verify is shown even if an admin has switched the underlying promo off.
- [ ] **Verified state** (`status.seniorVerified === true`): static amber/gold card, `BadgeCheck` icon, "أنت مسجّل كعضو في العرض الخاص", plus "رقم الهوية: ****<last4>" if available. No further action is possible on this screen — verification is effectively permanent, with no "un-verify" or "change ID" control.
- [ ] **Unverified state** — single-field form:
  - رقم الهوية الوطنية (14 رقماً) — text input, `inputMode="numeric"`, `pattern="[0-9]*"`, `maxLength=14`, `dir="ltr"`. `onChange` strips every non-digit character live, so the field can never hold anything but digits regardless of what's typed or pasted.
  - Helper text: "نتحقق من عمرك فقط. لا نُخزّن الرقم كاملاً ولن نشاركه." — **this copy is inaccurate relative to the implementation**: the full ID *is* stored (encrypted), just not in plaintext and never re-displayed in full. Preserve this exact copy for parity unless the PM chooses to correct the wording during the rebuild.
  - Submit "إرسال للتحقق" — disabled unless exactly 14 digits are entered, and disabled while submitting.
  - `POST /api/profile/senior` with `{ nationalId }`. `401` mid-flow redirects the same way as the GET. On success: local state flips to verified, shows the masked last4, toast "تم التحقق بنجاح. يمكنك الاستفادة من العرض الخاص." On failure: toast with the server's specific Arabic error message; the ID field is **not** cleared on failure (only cleared on success), so the user can correct and resubmit without retyping.
- [ ] Server verification (`verifyAndStoreSeniorId`):
  - Normalizes input to exactly 14 digits (`normalizeNationalId` left-pads/truncates rather than rejecting outright — unreachable in practice since the client already blocks submission below 14 digits).
  - Parses the real Egyptian national-ID structure: century digit (`2`→19xx, `3`→20xx), 2-digit year, month, day; rejects invalid century/month/day/date combinations with specific Arabic messages (e.g. "الرقم الأول غير صالح (يجب 2 أو 3)", "شهر غير صالح", "تاريخ ميلاد غير صالح").
  - Computes age precisely as of today (month/day-aware, not just year subtraction) and requires ≥60, else "يجب أن يكون عمرك 60 عاماً على الأقل للاستفادة من العرض الخاص".
  - Checks a SHA-256 fingerprint for uniqueness across the **whole** `SeniorVerification` table (not scoped per-user): same ID already used by *this* account → "تم التحقق من هذا الرقم مسبقاً لهذا الحساب"; used by *another* account → "رقم الهوية مستخدم لحساب آخر" (hard-blocked).
  - On success: encrypts and upserts a `SeniorVerification` row and sets `User.seniorVerified = true` inside a single Prisma `$transaction`.

## States
- [ ] Empty state — not applicable; the page always renders either the verified-confirmation card or the verification form.
- [ ] Loading state — `<h1>العرض الخاص</h1>` + "جاري التحميل…" only, same minimal pattern as the other profile pages.
- [ ] Error state — a load failure shows a destructive toast "خطأ في التحميل"; `status` stays `null`, and since `status?.seniorVerified` is falsy for `null`, the page falls through to render the **unverified form** — indistinguishable from "genuinely not yet verified" to the customer, the same class of gap as the orders screen's error handling. A failed *submit* is toast-only and does not clear the entered ID.
- [ ] Permission-restricted state — both `GET` and `POST` `401`s redirect via `router.replace("/login?redirect=/profile/senior")` (soft navigation, unlike the hard-redirect pattern used elsewhere in `/profile`).

## Edge cases
- [ ] Age exactly 60 with today as the birthday — handled correctly via explicit month/day comparison, not calendar-year subtraction alone.
- [ ] Re-submitting an ID already verified on the same account — treated as a soft/duplicate condition with its own message, not a generic error and not silently re-accepted as a fresh success.
- [ ] Re-submitting an ID already verified on a *different* account — hard-blocked, preventing shared/duplicate senior identities across accounts.
- [ ] Invalid century digit, or an impossible month/day — explicit, specific Arabic rejection messages rather than a silently miscomputed birthdate/age.
- [ ] The global senior-promo toggle is **off** while a customer verifies here — verification still succeeds and `seniorVerified` is still set; only the discount itself won't apply at checkout (that gate lives entirely in `lib/services/pricing.ts`, decoupled from this page) — this screen gives no indication either way of whether the promo is currently active.
- [ ] `SeniorVerification` table missing (pre-migration environment) — `getSeniorStatus` specifically catches Prisma error `P2021` and falls back to `{ seniorVerified: false, nationalIdLast4: null }` instead of throwing; the `POST` path (`verifyAndStoreSeniorId`) has no equivalent guard, so a submit attempt before migration would likely 500 uncaught.

## Notes
- **This is the key finding for the redesign's accessibility scoping**: no simplified/large-text/reduced-navigation UI variant for older users exists anywhere in the current codebase. Anything the redesign wants to do for accessibility here is new product work, not a parity requirement extractable from this route.
- The route's name ("senior") collides with the demographic term "senior" used in the redesign brief's accessibility framing — almost certainly the source of the mismatch; recommend the team consistently call this feature "senior discount verification" in downstream docs to avoid the confusion recurring.
- Because this page is currently unreachable through any in-app navigation, the rebuild should treat surfacing it (a link from the account page, a homepage banner, etc.) as a deliberate, PM-approved product change — not something to silently add as "obviously implied" by its existence.
- 401-handling technique (`router.replace`) differs from the `window.location.href` hard-redirect used on account/addresses/orders — worth normalizing site-wide in the rebuild regardless of the accessibility question.
