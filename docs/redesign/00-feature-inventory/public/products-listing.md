# Public — Products listing

Route(s): `app/(public)/products/page.tsx`
Key files: `app/(public)/products/products-content.tsx`, `components/shared/catalog-filter-bar.tsx`, `components/shared/sort-dropdown.tsx`, `components/shared/product-card.tsx`, `components/shared/quick-shop-modal.tsx`, `components/shared/empty-state.tsx`, `components/shared/loading-dots.tsx`, `hooks/use-navigate-back-restore.ts`, `app/api/products/route.ts`, `app/api/products/filters/route.ts`, `lib/catalog.ts`, `lib/storefront-location.ts`

See also `docs/redesign/00-feature-inventory/public/categories.md` — the single-category screen (`CategoryContent`) is a near-duplicate of this screen (`ProductsContent`) scoped to one category, sharing the same filter/sort/infinite-scroll/scroll-restore mechanics.

## Business requirements
- **Goal/KPI**: primary catalog-browsing conversion surface for shoppers who don't land via a category or the home page — full unfiltered product search/browse with filter+sort controls. Also the de-facto "search results" experience (see `search.md`: there is no dedicated search page; `?q=` on this route is where product-name/description/tag search actually lives).
- **Trust/credibility signals**: live result count ("X نتيجة" in the filter bar header, "X منتج" above the grid), honest out-of-stock badging, EGP pricing with discount badges.
- **Friction points**: search box and sort/filter live inside one card-styled `CatalogFilterBar`, but there's no way to filter by price range or "in stock only" from the UI despite the API supporting both (`minPrice`/`maxPrice`/`inStock` query params exist in `lib/catalog.ts` `ProductsQuery` but have no corresponding control here) — a shopper cannot narrow to "only what I can actually buy" without scrolling past every out-of-stock card. Infinite scroll with no visible pagination affordance can make it hard to gauge catalog size at a glance (mitigated somewhat by the live "X منتج" count).
- **Compliance/legal**: none specific.
- **URL/SEO stability**: `/products` must be preserved; metadata is static (title "المنتجات", description, canonical path `products`) — does not vary by filter/sort/search query (query-string variants are not distinctly indexed/described).
- **Modern-look rationale**: sticky filter card + infinite scroll + hover quick-view/quick-shop is standard modern PLP (product listing page) pattern; matches competitor catalog browsing UX.

## Elements & behavior
- [ ] Page header — static "كل المنتجات" `<h1>`.
- [ ] `CatalogFilterBar` — gradient header row showing a live result count ("{total} نتيجة" or "جاري التحميل" while loading) plus:
  - Search input (`ابحث باسم المنتج...`) — debounced 250ms before triggering a re-fetch; syncs to `?q=` in the URL (`router.replace`, `scroll: false`, so the URL updates without a page jump).
  - Category `<Select>` — "كل التصنيفات" + every category (options from `GET /api/products/filters`, revalidated whenever the selected category changes); syncs to `?category=`.
  - Size `<Select>` — "كل المقاسات" + every distinct variant size present in the current category scope (auto-clears if the selected size becomes invalid for a new category); syncs to `?size=`.
  - "مسح" (clear) button — resets search+category+size together; disabled when no filter is active.
- [ ] `SortDropdown` — custom dropdown (not a native `<select>`), 8 options: فيتشر (featured — default: `sortOrder desc, createdAt desc`), أفضل مبيعات (best_sales — ranked via `getProductIdsRankedByRecentSales`, see Notes), ابجديا الف→ياء (name_ar), أبجديا Z→A (name_za), السعر الارخص→الاعلى (price_asc), السعر الاعلى→الادنى (price_desc), التاريخ قديم→جديد (date_asc), التاريخ جديد→قديم (date_desc). Only non-default sorts are added to the URL (`?sort=`).
- [ ] Product grid — 2 cols (mobile) → 3 (md/lg); `ProductCard` per product: hover overlay (نظرة سريعة / quick-view link to PDP, متجر سريع / quick-shop opens `QuickShopModal` without navigating), amber discount badge, "نفذ" out-of-stock badge, color swatches (hover swaps card image, click navigates to that color variant's slug).
- [ ] `QuickShopModal` (triggered from any `ProductCard`'s cart icon) — fetches the full product detail (`GET /api/products/{slug}`) on open, lets the shopper pick size then color (color required only if the selected size has >1 color), a quantity stepper (min 1, no visible max cap in the UI itself — server still enforces `maxQty` on add), then either "أضف إلى السلة" (add to cart, stays on page, opens the cart drawer) or "اشتر الآن" (buy now — adds to cart then hard-navigates to `/cart`). Validates size/color selection and in-stock status client-side before calling the API; shows the same Arabic validation toasts as the PDP (يرجى اختيار المقاس / يجب اختيار اللون / هذا المقاس غير متوفر حالياً).
- [ ] Pagination — infinite scroll via `IntersectionObserver`, page size 9 (`PAGE_SIZE`), fetches `offset = products.length` on intersect; guarded against double-fetching while `loading`/`loadingMore` or once `products.length >= total`.
- [ ] Scroll/position restore on browser Back — `useNavigateBackRestore("storefront-products-scroll")`: remembers the clicked product's id + loaded count in `sessionStorage`; on return, re-fetches at least that many items and scrolls the original card (`data-row-id`) back into view, then clears the stash.
- [ ] Data source — `GET /api/products?q=&category=&sizes=&sort=&limit=&offset=`. Server logic (`app/api/products/route.ts`): `active: true` always; text search (`q`) matches `OR` across product name/slug/description (case-insensitive `contains`), exact tag match (`tags: { has: q }`), and category name (case-insensitive `contains`) — i.e. searching a category's Arabic name surfaces its products even without selecting the category filter. `price_asc`/`price_desc` sorts and any `minPrice`/`maxPrice` filter force a full up-to-500-row fetch (`FULL_FETCH_CAP`) that is sorted/filtered/paginated in application code rather than the database, because price is a derived/computed field (variant price or explicit discount price), not a raw sortable column.

## States
- [ ] Empty state — "لا توجد منتجات" / "جرّب تغيير البحث أو الفلاتر المختارة." with a "العودة للرئيسية" button, shown when the filtered result set is empty (whether from search, category, or size filter).
- [ ] Loading state — page wrapped in a server-side `<Suspense>` with `LoadingDots` fallback for first paint; client-side `loading` state additionally shows a large centered `LoadingDots` for the first filtered fetch, and a smaller one below the grid while `loadingMore` (infinite-scroll fetch in flight).
- [ ] Error state — no explicit error UI. A failed `/api/products` or `/api/products/filters` fetch is caught silently and renders as an empty product list / empty filter options — indistinguishable from "no results" to the shopper.
- [ ] Permission-restricted state — not applicable; fully public.

## Edge cases
- [ ] Governorate/partner not resolved — every product's `inStock` becomes `false` regardless of real inventory (shared storefront-wide behavior; see `home.md`).
- [ ] `best_sales` sort — computed via `getProductIdsRankedByRecentSales(where)` (a separate ranking query applied as a post-hoc `Array.sort` over the already-fetched page) rather than a true DB-level ORDER BY; this is a per-product metric, so it composes correctly with the current filters but not with `price_asc`/`price_desc`'s full-fetch code path (mutually exclusive sort choices in the UI, so this doesn't collide in practice today, but a rebuild adding combinable sort/filter should note the two sorting strategies are structurally different).
- [ ] Selected size becomes invalid after switching category — silently cleared (`if (size && !nextSizes.includes(size)) setSize("")`), no toast/explanation shown to the shopper for why their size filter disappeared.
- [ ] Very large `q` search matching zero products but a valid category tag substring — search also matches category **name**, so an ambiguous query can return products from a category whose name happens to contain the search text, which may surprise a shopper expecting literal product-name-only matching.
- [ ] `minPrice`/`maxPrice`/`inStock` query params are honored server-side but have no UI control — reachable only via a hand-built URL; any implementer replicating "what filters exist" purely from the visible UI would miss these.

## Notes
- This route is the *actual* search experience today — see `search.md` for the full explanation of why `/search` and `/api/products/search` exist as directories in the repo but are completely empty (no `page.tsx`, no `route.ts`). Do not build a separate "search results" screen in the redesign without an explicit PM decision on whether to keep search folded into `/products` (current behavior) or split it into its own screen.
- `ProductsContent` and `CategoryContent` (`categories.md`) are near-duplicate client components; consider unifying in the rebuild, but see that file's Notes for the caveats (independent scroll-restore keys, independent-but-currently-identical page sizes).
- The `/api/products` cache (`unstable_cache`, 60s, keyed by serialized `where`/`orderBy`/`skip`/`take`) caches the *catalog* query only — partner stock overrides are always applied fresh per request after the cache read, so stock numbers are never stale even though the underlying product/price data can be up to 60s old.
