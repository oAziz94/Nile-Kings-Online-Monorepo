# Public — Cart

Route(s): `app/(public)/cart/page.tsx`
Key files: `contexts/cart-context.tsx`, `components/cart/cart-drawer.tsx` (mini-cart, layout-level — same cart data, appears on every public page), `components/shared/price.tsx`, `components/shared/product-card.tsx` (recommendations rail), `lib/cart/cart.ts`, `lib/storefront-location.ts`, `app/api/cart/route.ts`, `app/api/cart/items/route.ts`, `app/api/cart/items/[id]/route.ts`, `app/api/products/recommendations/route.ts`

## Business requirements
- **Goal/KPI**: pre-checkout review/edit surface — confirm items, quantities, and running subtotal before committing to the checkout flow; secondary cross-sell via a "قد يعجبك ايضا" (you might also like) recommendations rail to lift AOV.
- **Trust/credibility signals**: per-line and running-subtotal pricing in EGP; explicit quantity stepper bounded by real-time sellable stock (`maxQty`) rather than letting a shopper request more than can be fulfilled; line-item images/names/variant descriptors so nothing is ambiguous before checkout.
- **Friction points**: the cart is **not** authentication-gated (guest-token based via a cookie — see Elements), but checkout immediately behind it *is* login-gated, so a guest who fills a cart and clicks "متابعة للدفع" (proceed to payment) only discovers they must log in on the next screen, not here — a plausible late-funnel drop-off point worth flagging to PM even though it's out of scope for this file (see `checkout.md`). Cart contents can silently shrink (items removed) when a shopper changes their delivery governorate elsewhere in the site, with the explanation only surfacing as a toast on whatever page they land on next, not on the cart page itself in the moment it happens.
- **Compliance/legal**: none specific to this screen.
- **URL/SEO stability**: `/cart` must be preserved; not typically an indexed/marketing page, no special metadata beyond default site metadata (no `pageMetadata()` call in `cart/page.tsx`).
- **Modern-look rationale**: no cart-specific "modern look" business rationale beyond general redesign consistency — this is a functional utility screen.

## Elements & behavior
- [ ] Cart resolution/identity — no login required. `getOrCreateCart()` (`lib/cart/cart.ts`) resolves by signed-in `userId` if logged in, otherwise by a `guestToken` cookie (created on first cart interaction if absent); a cart row always has exactly one of `userId`/`guestToken` set. Guest carts merge into the user's cart on login (`mergeGuestCartIntoUser`, summing quantities per variant, capped at each variant's current `maxQty`) — this merge is **not** triggered from this page; it's part of the login flow elsewhere.
- [ ] Line items list — each row: product image (links to `/products/{variantSlug ?? productSlug}`, i.e. deep-links to the exact color/size if the variant has its own slug), product name (link, same href), variant descriptor text (`{productSlug}-{size}[-{colorName}]` format, e.g. "cotton-tshirt-M-أسود" — note this is a slug-derived technical string, not a friendly "Size: M, Color: Black" label — see Notes), unit price, quantity stepper, remove button, and a right-aligned line total (`priceEgp * quantity`).
- [ ] Quantity stepper — `−`/`+` buttons around a numeral. Decrement disabled at quantity 1 (no direct "set to 0" via the stepper — removal is a separate explicit action). Increment disabled once `quantity >= item.maxQty` (`maxQty` = live sellable stock for that variant under the shopper's currently-resolved partner, recomputed server-side on every cart fetch — not a snapshot from when the item was added). Both buttons disabled while that specific line is mid-update (`updatingId === item.id`), so a shopper can't double-fire the same line's request, but can still interact with other lines concurrently.
- [ ] Remove button ("حذف" with a trash icon) — `DELETE /api/cart/items/{id}`, shows a "تم حذف المنتج من السلة" success toast on completion.
- [ ] Order summary card — "المجموع ({itemCount} منتج)" and the subtotal price; "متابعة للدفع" (proceed to payment) primary button → `/checkout`; "متابعة التسوق" (continue shopping) secondary button → `/categories`. **No shipping estimate, coupon field, or final total appears on this page** — those only appear once the shopper reaches checkout and provides a delivery address (shipping is governorate/weight-dependent and cannot be computed without one).
- [ ] Recommendations rail ("قد يعجبك ايضا") — up to 4 products from `GET /api/products/recommendations` (same trending/add-to-cart-log-driven ranking as the home page's best-sellers, see `home.md`), rendered as standard `ProductCard`s, with a "عرض الكل" button linking to `/categories`. Shown only if at least 1 recommendation exists; not personalized to the current cart's contents (no "frequently bought with X" logic — it's the same global ranking used elsewhere).
- [ ] Mini-cart drawer (`CartDrawer`, layout-level, opens from the header cart icon or after any add-to-cart action anywhere on the site) — a slide-in panel showing the same line items/stepper/remove/subtotal pattern as the full cart page (smaller images, no recommendations rail), with a single "عرض السلة" (view cart) button linking to `/cart`. Both surfaces read/write the exact same cart via `useCart()` context, so changes in one are reflected in the other once either re-fetches.
- [ ] Data refresh — the full cart page calls `refreshCart()` on mount (always re-fetches from `GET /api/cart` even if `CartProvider`'s initial mount fetch already populated it), so stock/price numbers shown here are always current as of page load, not stale from an earlier page.

## States
- [ ] Empty state — shopping-bag icon, "سلة التسوق فارغة" (cart is empty), "تسوق الآن" (shop now) button → `/categories`. Identical empty-state pattern (smaller) in the mini-cart drawer.
- [ ] Loading state — no dedicated skeleton/spinner for the cart page itself; `cart` starts `null` in context and the page treats `null` the same as "empty" until the fetch resolves (i.e. **a slow cart fetch is visually indistinguishable from a genuinely empty cart** for however long the request takes — there is no separate "loading…" state between "unknown" and "confirmed empty").
- [ ] Error state — no explicit error UI on this page. A failed quantity-update or remove call shows a destructive toast with the server's Arabic message (or a generic "حدث خطأ" on parse failure / network error) but does not roll back or re-fetch the row — the line item's displayed quantity may become out of sync with the server until the next full `refreshCart()`.
- [ ] Permission-restricted state — not applicable; cart is fully guest-accessible, no login required to view/edit it.

## Edge cases
- [ ] Attempting to increase quantity beyond current sellable stock — API (`PATCH /api/cart/items/{id}`) returns `422` with "الكمية المتاحة لهذا المقاس: {maxQty} فقط" (only {maxQty} available for this size) if a request somehow exceeds `maxQty` server-side (the `+` button is pre-disabled at that boundary client-side, so this mainly guards against stale client state, e.g. two tabs open).
- [ ] A cart item's underlying product becomes inactive (`Product.active = false`) after being added — silently deleted from the cart on the next `getCartPayload()` read (`inactiveItemIds` cleanup in `lib/cart/cart.ts`), with **no toast or notice to the shopper** that anything was removed — the item just disappears the next time the cart is fetched.
- [ ] Shopper changes delivery governorate (via the site-wide `GovernorateSelector`, not from this page) to one where the newly-resolved partner has zero stock for some cart items — those lines are deleted server-side (`pruneCartItemsForGovernorate`, triggered by the governorate-save endpoint, not by this page) and a "تم حذف بعض الأصناف من السلة" toast fires, but only because the governorate-change flow does a **hard page reload** and stashes the removed-item list in `sessionStorage` for the next page to read — if a shopper is not on `/cart` when this happens, they only learn about it wherever they land next (which could be several pages later if `sessionStorage` isn't consumed immediately — in practice it's read once on the very next mount of `GovernorateSelector`, which is layout-level and mounts on every page, so this fires promptly, but the mechanism is indirect and worth an implementer's attention).
- [ ] Two browser tabs open, one updates a line's quantity — the other tab's displayed quantity/subtotal is stale until it independently calls `refreshCart()` (no cross-tab sync, no polling).
- [ ] Variant display name relies on `productSlug` + raw variant `name` (size) + `colorName` — for the "kids" category where size *labels* are remapped for display elsewhere (PDP, quick-shop — see `products-pdp.md`), the cart's line-item text uses the **unmapped** underlying size code (e.g. shows "M" even though the PDP displayed "4" for a kids product), which is an inconsistency a shopper could notice between screens.

## Notes
- `maxQty` per line is recomputed live on every cart fetch from the shopper's currently-resolved partner (governorate-dependent) — it is not fixed at add-time. This means a cart item added while stock was plentiful can show a lower (or zero, forcing removal) `maxQty` later purely because the shopper's selected delivery location changed, with no direct causal link visible on the cart screen itself.
- The line-item "variant name" shown to shoppers (`{productSlug}-{size}-{colorName}`) is a technical/slug-style string reused verbatim from internal code (also used in order snapshots and admin displays) rather than a shopper-friendly label — a rebuild should consider whether to keep this exact string for downstream consistency (order history, admin support lookups all use the same format) or introduce a friendlier *display-only* variant, being careful not to change what's actually stored on `OrderItem.variantName` since that's a historical snapshot field.
- Cart and the mini-cart drawer are two independent renderings of the same `CartContext` state — there is no cart-specific business logic duplicated between them (unlike the PDP/QuickShopModal duplication noted in `products-pdp.md`), so this is a lower-risk area for the rebuild as long as both keep reading/writing through the shared context.
