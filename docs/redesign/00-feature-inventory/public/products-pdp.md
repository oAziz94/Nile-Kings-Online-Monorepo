# Public — Product detail page (PDP)

Route(s): `app/(public)/products/[slug]/page.tsx`
Key files: `app/(public)/products/[slug]/product-page-content.tsx`, `components/shared/size-chips.tsx`, `components/shared/color-swatches.tsx`, `components/shared/price.tsx`, `components/shared/product-card.tsx` (related products), `lib/size-display.ts`, `lib/catalog.ts`, `lib/storefront-location.ts`, `app/api/products/[slug]/route.ts` (used by `QuickShopModal`, not by this page directly — see Notes), `app/api/analytics/view`, `app/api/analytics/add-to-cart`, `app/api/cart/items`

## Business requirements
- **Goal/KPI**: primary conversion moment — variant (size/color) selection, stock confirmation, add-to-cart. Also feeds cross-sell via a "منتجات ذات صلة" (related products) rail at the bottom.
- **Trust/credibility signals**: price with strikethrough original price + discount % when discounted (`Price` component); explicit "متوفر"/"غير متوفر" (in stock / not in stock) text status; per-size stock reflected via disabled size chips.
- **Friction points**: single static product image with no gallery/zoom (`galleryImages` array always has exactly one URL — the selected variant's image or the product's fallback image; there is no multi-image carousel or zoom-on-hover despite `galleryImages` being named as if it supported multiple). Size must be picked before color options become selectable/validated in some flows, which is a two-step tap sequence that could cost conversions on mobile. No "notify me when back in stock" for out-of-stock variants — a shopper hits a dead end (disabled chip only).
- **Compliance/legal**: none specific.
- **URL/SEO stability**: canonical path `products/{slug}`; `generateMetadata` reads the *product* record (title = product name, description = truncated product description, OG image = product image) even when the page was reached via a **variant** slug (see Elements — variant-slug resolution) — metadata does not vary per-variant/per-color.
- **Competitive/market framing**: PDP gallery/zoom is a standard competitor expectation for apparel ecommerce that this implementation currently does **not** meet (single static image, no zoom) — flag to PM as a plausible redesign upgrade opportunity, not just a parity target, since competitors in this category typically show a multi-image gallery per color variant.

## Elements & behavior
- [ ] Slug resolution (server, `app/(public)/products/[slug]/page.tsx`) — the `[slug]` param is resolved two ways: first as a **variant** slug (`productSlug_size_colorHexCode` format, e.g. `cotton-tshirt_m_000000`) via `prisma.variant.findFirst({ where: { slug } })`; if no variant matches, falls back to a **product** slug (`prisma.product.findFirst({ where: { slug, active: true } })`). This means the same PDP route serves both a generic product URL and color/size-specific deep links (e.g. from a `ProductCard`'s `variantSlug` or a color swatch), and when reached via a variant slug the page opens with that exact size+color pre-selected (`initialVariantId`).
- [ ] Breadcrumb — الرئيسية (home) → category name (links to `/categories/{categorySlug}`) → product name (current, not a link).
- [ ] Main image — single image, `object-cover`, swaps when the selected color/variant changes (image `key` prop forces remount so Next `<Image>` reliably updates); falls back through variant image → product image → hardcoded Unsplash placeholder.
- [ ] Size selection — `SizeChips`, options built via `getVariantSizeOptions` (`lib/size-display.ts`): sizes are deduplicated/normalized (e.g. "3XL" normalizes to "XXXL"), sorted by a fixed order (S, M, L, XL, XXL, XXXL, 4XL) then alphabetically as a tiebreaker, and **relabeled for the "kids" category** via `KIDS_SIZE_LABEL_MAP` (e.g. adult-style "S"/"M"/"L" labels are displayed as kids' age-based sizes "2"/"4"/"6"/"8"/"10"/"12"/"14" when `categorySlug === "kids"`) — the underlying variant `name` values are unchanged, only the *displayed* label differs. A chip is disabled when no in-stock variant exists for that size (across any color). Deselecting a size clears the color selection.
- [ ] Color selection — `ColorSwatches` (square shape on PDP), built from **all** variants regardless of selected size (colors are always visible, not gated behind picking a size first) with hex resolved from `colorHex`, falling back to a hardcoded Arabic/English color-name→hex map (`variantColorHex`) if `colorHex` is null, defaulting to gray (`#9e9e9e`) if the name isn't recognized either. A swatch is disabled if no in-stock variant exists for that color within the current size context (or across all sizes if no size is selected yet).
- [ ] Color requirement logic — color is only **required** (validated) when the selected size has more than one color option; if a size has exactly one color, that variant is auto-selected without requiring an explicit color click.
- [ ] Price display — shows the *selected variant's* price/original-price/discount if a variant is selected, else falls back to the product-level price/discount (`product.priceEgp`, computed server-side as `discountPricePiastres ?? min(variant prices)`).
- [ ] Stock status line — "متوفر" (green text) / "غير متوفر" (destructive/red text), driven by `product.inStock` (true if **any** variant has stock > 0), not by the currently-selected variant's stock specifically.
- [ ] "أضف إلى السلة" (Add to Cart) button — disabled when `!product.inStock || adding`. On click, validation order: (1) size not selected → toast "يرجى اختيار المقاس"; (2) size selected, multiple colors available, none chosen → toast "يجب اختيار اللون"; (3) no resolved variant → toast "يرجى اختيار المقاس" again; (4) resolved variant but its stock is 0 → toast "هذا المقاس غير متوفر حالياً". On success: `POST /api/cart/items` with `{ variantId, quantity: 1 }` (**quantity is always exactly 1** — there is no quantity stepper on the PDP itself, unlike the cart page and `QuickShopModal`), updates cart context, opens the cart drawer, and shows a success toast **only on desktop** (`window.innerWidth >= 768`) — mobile shoppers get no toast, just the drawer opening.
- [ ] Product tags — rendered as pill links below the Add to Cart button, but **every tag link points to the same static `/products` URL** regardless of the tag's text (`href="/products"`, not `?section={tag}` or similar) — i.e. clicking any tag currently does not filter by that tag despite visually looking like a filter chip. Compare to `categories.md`'s note that `?section=` *is* a real server-side filter param elsewhere; this PDP tag link does not wire into it.
- [ ] View-count analytics — `POST /api/analytics/view` fired once on mount (and again if the resolved variant changes) with `productId`, optional `variantId`, and a session id generated fresh per call (`"session-" + Date.now()`, not a stable session identifier — see Notes).
- [ ] Add-to-cart analytics — `POST /api/analytics/add-to-cart` fired (fire-and-forget, errors swallowed) alongside every successful add-to-cart, feeding the "recommended" signal used on the home page and cart-page recommendations.
- [ ] Related products — up to 4 products from the same category (excluding the current product), server-computed (`sortOrder desc`), rendered as a standard `ProductCard` grid ("منتجات ذات صلة" heading) — only shown when at least 1 related product exists.

## States
- [ ] Empty state — not applicable to the PDP itself (a product either exists or 404s); the related-products rail is simply omitted (`related.length > 0` guard) if there are no other active products in the category.
- [ ] Loading state — server-rendered (`export const dynamic = "force-dynamic"` on the page, though the underlying product/variant query is `unstable_cache`'d 60s); no client-side loading spinner for the page itself. `logView()` and the add-to-cart flow show no dedicated per-action loading state beyond the Add to Cart button's `disabled={adding}` (no spinner/label change while `adding` is true — button text stays "أضف إلى السلة").
- [ ] Error state — no product/variant found for the slug → server-side `notFound()` → generic Next.js not-found page (no custom "product not found" messaging). Add-to-cart API failures show a destructive toast with the server's Arabic error message, or a generic "حدث خطأ" if the response can't be parsed.
- [ ] Permission-restricted state — not applicable; fully public (no login required to view or add to cart — cart is guest-token-based until checkout).

## Edge cases
- [ ] Governorate/partner not resolved — `product.inStock` is `false` for every variant (see `home.md`); every size chip renders disabled, Add to Cart is disabled, and the "غير متوفر" status shows even for objectively in-stock products.
- [ ] Reached via a variant slug whose product is inactive (`active: false`) — the variant-slug lookup path does **not** filter by `product.active` (only the fallback product-slug lookup does: `where: { slug, active: true }`), so a direct link to a variant of a deactivated product may still render instead of 404ing. Flag this inconsistency to engineering/PM — it's a real discoverable gap, not a redesign guess.
- [ ] A size has only one variant/color but that variant is out of stock — the size chip is still shown (not hidden) but disabled, consistent with "always show all sizes, disable unavailable ones" rather than hiding out-of-stock options entirely.
- [ ] Selecting a color before a size — the main image updates to that color's variant image (`displayVariantForImage` logic falls back to color-only match), but Add to Cart still requires a size pick.
- [ ] Product has zero variants entirely (data integrity edge case, not expected in normal operation) — size/color sections render "لا توجد ألوان" / empty size chip row; Add to Cart would fail validation at the "no resolved variant" step.

## Notes
- `QuickShopModal` (triggered from `ProductCard`s on listing/category/home/cart screens, not from this PDP itself) duplicates almost all of this page's size/color selection and validation logic independently, including the same hardcoded Arabic color-name→hex fallback map (`variantColorHex`) — the two are not sharing a component today. A rebuild should strongly consider extracting this into one shared hook/component (`useVariantSelection` or similar) since the two implementations must stay behaviorally identical (same validation order, same messages) and currently only stay in sync by hand.
- The PDP's own page/route never calls `GET /api/products/{slug}` — it fetches the product server-side directly via Prisma. That API endpoint exists solely for `QuickShopModal`'s client-side fetch and admin/other tooling; don't assume the PDP is a consumer of it when tracing data flow.
- `GET /api/products/{slug}/related` also exists as a separate endpoint but is **not called by this page** — the PDP computes its own related-products list server-side inline (`getRelated` in `page.tsx`) with slightly different selection logic (`sortOrder desc`, take 4, no dependency on the `/related` route). Confirm before assuming that endpoint has a live consumer anywhere.
- Kids' size relabeling (`KIDS_SIZE_LABEL_MAP`) is purely a *display* transformation — cart line items, order records, and the admin catalog all continue to reference the underlying adult-style size codes (S/M/L/etc.). A rebuild must not "fix" this by renaming the underlying data, or it will break every downstream consumer (cart, checkout, admin, partner) that expects the original codes.
- The analytics session id (`"session-" + Date.now()`) is regenerated on every single view/add-to-cart call — it is **not** a stable per-visit or per-session identifier despite the name, so any analytics relying on `sessionId` to group events from one visit will not actually be able to do so today.
