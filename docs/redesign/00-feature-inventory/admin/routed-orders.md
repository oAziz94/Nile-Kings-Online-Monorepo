# Admin — Routed Orders (list, detail/status/proof/reassign)

Route(s): `app/(admin)/admin/routed-orders/page.tsx` (list), `app/(admin)/admin/routed-orders/[id]/page.tsx` (detail: routing status, delivery-proof upload, manual reassignment)
Key files: `lib/rerouting/assign.ts` (`assignOrderToGovernorate` — the auto-routing engine that feeds this screen), `lib/inventory/partner-inventory.ts` (`reassignReservedPartnerStock`), `app/api/admin/routed-orders/route.ts`, `app/api/admin/routed-orders/[id]/route.ts`, `app/api/admin/routed-orders/[id]/reassign/route.ts`, `app/api/admin/upload/route.ts` (proof-photo upload, `folder: "routed-proofs"`). Covered as one file (list + detail) — the detail page has real complexity (status, proof upload, reassignment dialog with stock movement) but shares the same `RoutedOrder` record and status vocabulary throughout, so splitting would fragment one continuous story.

## Business requirements
- **Goal/KPI**: operational visibility into the regional-partner fulfillment network — this is the screen that answers "which partner is delivering this order, what's its delivery status, and is there proof of delivery" separately from the order's own commercial status (tracked on `/admin/orders`). Directly serves fulfillment reliability/ops-efficiency and is the escalation tool when a partner isn't delivering (manual reassignment).
- **Trust/credibility signals**: delivery-proof photo capture (JPG/PNG/WebP upload, stored via Cloudinary) exists specifically to resolve delivery disputes ("courier says delivered, customer says not received") — this is a real operational/trust mechanism, not decorative, and must be preserved with the same file-type acceptance and clear did-it-save feedback.
- **Friction points**:
  - `RoutedOrder.status` (ASSIGNED/NOTIFIED/ACCEPTED/OUT_FOR_DELIVERY/DELIVERED/FAILED/CANCELLED/UNROUTED) is a **separate state machine from `Order.status`** (CREATED/CONFIRMED/.../DELIVERED/CANCELLED on `/admin/orders`), and this screen has no visible sync/warning when the two diverge (e.g. a routed-order marked DELIVERED here doesn't itself update the commercial order's status, and vice versa) — an admin working only from one of the two screens could get an incomplete picture. Worth flagging to PM as a potential source of confusion, not something to silently "fix" by merging the models without a product decision.
  - List has no pagination/search parity with Orders — default page size here is **50** (vs. 20 elsewhere), and list/filter state is **not persisted to the URL** (uses plain `useState`, unlike the `useListUrlState` hook used on Products/Orders) — so browser-back from a detail page always resets filters/search/page here, unlike the other two list screens. This is a real, easily-missed inconsistency for the rebuild to either preserve knowingly or fix as a deliberate improvement.
  - Search only matches order id / customer name / customer phone — does not search by partner name or governorate.
- **Compliance/legal**: none beyond the general order-audit-trail expectations already covered in `orders.md`.
- **Modern-look rationale**: none beyond consistency with other admin table/detail patterns.

## Elements & behavior

### List (`/admin/routed-orders`)
- [ ] `PageHeader` — title "الطلبات الموجهة", description "متابعة التوجيه للشركاء، الحالة، وإثبات التسليم." (tracking routing to partners, status, and delivery proof). **No "create" action** — `RoutedOrder` rows are only ever created by the auto-routing engine (`assignOrderToGovernorate`, invoked after order placement — customer checkout or admin manual order) or, per-order, once (unique on `orderId`); there is no manual "create a routed-order" flow anywhere in the admin UI.
- [ ] Toolbar: `SearchInput` (placeholder "بحث برقم الطلب…" — order-number only per placeholder, though the query actually also matches customer name/phone server-side, so the placeholder undersells the real search scope), status `<select>` (كل الحالات + all 8 `RoutedOrderStatus` values with Arabic labels).
- [ ] Table columns: رقم الطلب (`#` + last-8-chars of the underlying `Order.id`, monospace), العميل (name or "—"), المحافظة (`governorate`, raw text — this is the routing-decision governorate, taken from the shipping address at assignment time, not necessarily re-synced if the address changes later), الشريك (assigned partner name, or "—" if `UNROUTED`), النوع (partner type: "وكيل" for AGENT / "موزع" for DISTRIBUTOR), طريقة التعيين ("تلقائي" AUTO / "يدوي" MANUAL), تاريخ التعيين (`assignedAt`), الحالة (plain outline `Badge`, no status-specific color-coding unlike the Orders list), إثبات (✓ if a proof image URL is set, else "—" — no thumbnail preview in the list, just presence/absence), إجراءات ("تفاصيل" link → `/admin/routed-orders/{id}`).
- [ ] Debounced 400ms search; page auto-resets to 0 whenever search/status filter change; page auto-clamps into range once `total` is known (no `loading`-guard on this clamp effect, unlike Products/Orders — could theoretically clamp against a stale `total=0` on the very first render before data arrives, though in practice `total` starts at `0` and `page` starts at `0` so this is unlikely to visibly misbehave).
- [ ] Sort: `createdAt desc` only (of the `RoutedOrder` record, not the underlying order) — no column sorting.
- [ ] No bulk actions/selection on this list at all (no checkboxes, no export) — a notable contrast with the Orders list's bulk courier/CSV export.

### Detail (`/admin/routed-orders/[id]`)
- [ ] Header: "طلب موجه #{last-8-chars of orderId}", back link to the list.
- [ ] **الحالة والملاحظات (status & notes) card** — `<select>` over all 8 `RoutedOrderStatus` values (again, no transition constraints — any status reachable from any other), "حفظ الحالة" button (disabled if unchanged/saving), current status also shown as a badge next to the control. Separately, a single-line ملاحظات (notes) `<Input>` with its own independent "حفظ الملاحظات" save button (saved via a separate PATCH call from the status save — the two are not submitted together). Server-side: setting status to `ACCEPTED` auto-stamps `acceptedAt = now()`; setting to `DELIVERED` auto-stamps `deliveredAt = now()` (both are set once on that specific transition, not corrected if you toggle away and back — re-selecting DELIVERED a second time would re-stamp `deliveredAt` to the new "now", since the server doesn't check `data.deliveredAt` is already set).
- [ ] **إثبات التسليم (delivery proof) card** — shows the current proof image (`<img>`, max-height 48 (12rem), object-contain) if one exists; upload button (hidden native file input restricted to `.jpg,.jpeg,.png,.webp` / `image/jpeg,image/png,image/webp`, both by extension and MIME) that immediately uploads to `POST /api/admin/upload` with `folder: "routed-proofs"` (routed to a distinct Cloudinary folder, `nile-kings/routed-proofs`, from product images) and populates the URL field on success — **the uploaded image is not yet persisted to the `RoutedOrder` record at this point**; a separate manual "حفظ صورة الإثبات" (save proof image) click is required to PATCH `{ proofImageUrl, proofImagePublicId }` onto the record, with an explicit toast after upload reminding the admin: "تم رفع الصورة. احفظ لتسجيلها في السجل." (image uploaded — save it to record it). A raw URL can also be pasted directly into the same field instead of uploading a file (both paths converge on the same "حفظ صورة الإثبات" button).
- [ ] **التعيين (assignment) card** — read-only summary: المحافظة (routing governorate), الشريك (assigned partner name + phone, or "—"), نوع الشريك (Arabic partner-type label), طريقة التعيين (Auto/Manual), تاريخ التعيين, and — only if set — تاريخ الإشعار (`notifiedAt`, when the partner was notified of the assignment; no UI control to trigger a (re-)notification manually — notification appears to be a side effect of the auto-routing/order-placement flow only, not an admin action available here). "إعادة تعيين يدوي" (manual reassign) button opens a dialog.
- [ ] **تفاصيل الطلب (order details) card** — customer name+phone, order total (EGP), full line-item table (product/variant, quantity, line total — no images, no size/color parsing unlike the Orders detail page), and a "فتح الطلب الأصلي" (open the original order) link to `/admin/orders/{orderId}` — this is the explicit bridge between the two parallel screens/state-machines.
- [ ] **إعادة تعيين الشريك (reassign partner) dialog** — on open, fetches **both** AGENT and DISTRIBUTOR partners (two parallel `GET /api/admin/partners?partnerType=…&limit=100` calls, concatenated) into one `<select>` — i.e. reassignment is not governorate-filtered or partner-type-filtered in the UI; an admin can manually reassign to *any* active-or-inactive partner of either type regardless of whether they actually serve the order's governorate (no client-side validation against `governorate` at all). Auto-preselects the first partner in the merged list if none chosen yet (not necessarily a sensible default — it's whichever partner query happens to return first, i.e. effectively arbitrary/alphabetical-ish, not "closest" or "current"). Optional free-text ملاحظة (reassignment reason note). Submits `POST /api/admin/routed-orders/{id}/reassign` with `{ partnerId, notes }`.
  - Server-side reassignment (`reassignReservedPartnerStock`, transactional, 15s/60s tx limits): moves the order's **reserved/committed stock** from the old partner's `PartnerInventory` to the new partner's (fails with 400 "الشريك الجديد لا يملك مخزوناً كافياً لهذا الطلب" if the new partner can't cover the order's line items — reassignment is blocked outright on insufficient stock, not partially applied), updates the parent `Order.assignedPartnerId` and `Order.shippingOriginGovernorate` to the new partner's own governorate (**not** necessarily the customer's delivery governorate — these can differ), and updates the `RoutedOrder` itself: `partnerId` → new partner, `assignmentMode` forced to `"MANUAL"` (even if it was originally `AUTO`), `status` reset to `"ASSIGNED"` (regardless of what status it was in before — e.g. reassigning a `FAILED` or `OUT_FOR_DELIVERY` routed order silently resets it back to the start of the routing lifecycle), `notifiedAt`/`notificationError` cleared, and an audit note (`"إعادة تعيين يدوي إلى شريك {partnerId}. {admin's note}"`) appended to the existing `notes` field (newline-joined, not replacing prior notes).

## States
- [ ] Empty state (list) — `EmptyState`, `Truck` icon, title "لا توجد نتائج للبحث" (search active) or "لا توجد طلبات موجهة" (none) — no description text, matching the Orders list pattern.
- [ ] Loading state (list) — full-card skeleton on first load; subsequent refetches show inline "جاري التحديث…" spinner over a dimmed table (same pattern as Orders/Products).
- [ ] Loading state (detail) — single full-page skeleton until the routed-order record resolves; reassign-dialog's partner list has no explicit loading indicator of its own (dialog just opens with an empty `<select>` until the two partner fetches resolve).
- [ ] Error state (list) — destructive toast "فشل تحميل الطلبات الموجهة" on fetch failure.
- [ ] Error state (detail) — destructive toast "فشل تحميل السجل" (failed to load the record) on initial fetch failure; every mutating action (status save, notes save, proof save, proof upload, reassign) has its own destructive toast with server message or generic fallback.
- [ ] Permission-restricted state — enforced at `app/(admin)/layout.tsx` + `requireAdmin()` per route; no finer-grained tiers (consistent with every other screen).

## Edge cases
- [ ] `UNROUTED` routed orders (no rerouting rule exists for the governorate, or the rule has zero active partners) — still appear in this list/detail with a null `partner`/`ruleId`; the only recovery path visible in this UI is the manual "إعادة تعيين يدوي" dialog (there's no "auto-retry routing" button here — that would require either fixing the underlying rule on `/admin/rerouting-rules` (outside this inventory batch) or reassigning manually here).
- [ ] Re-selecting `DELIVERED` on an already-`DELIVERED` routed order — re-stamps `deliveredAt` to the current time with no guard, silently overwriting the original delivery timestamp.
- [ ] Reassigning a routed order that's already `DELIVERED`/`FAILED`/`CANCELLED` — fully permitted by the UI and API (no status-based guard on eligibility for reassignment), and unconditionally resets status back to `ASSIGNED`, which is almost certainly not intended for a genuinely completed/failed/cancelled delivery — worth flagging. `[NEEDS PM INPUT: should reassignment be blocked or require confirmation for routed orders already in a terminal status (DELIVERED/FAILED/CANCELLED)?]`
- [ ] Reassigning to a partner with insufficient stock — the whole reassignment is rejected (400), original assignment untouched; no partial/"reassign anyway and let stock go negative" override exists.
- [ ] The reassignment partner picker offers partners of **either** type with no governorate filter — an admin could reassign an order to a partner far from the delivery address with no warning; `shippingOriginGovernorate` on the parent order simply gets set to whatever that partner's own `governorate` is, which could now visibly mismatch the customer's actual delivery governorate shown elsewhere.
- [ ] Order/RoutedOrder status divergence — nothing in this UI surfaces or reconciles the case where, e.g., `Order.status = CANCELLED` but `RoutedOrder.status` is still `ASSIGNED`/`OUT_FOR_DELIVERY` (or vice versa); each screen only shows/edits its own status field.
- [ ] Proof image uploaded but the admin navigates away before clicking "حفظ صورة الإثبات" — the upload to Cloudinary already happened (an orphaned asset now exists there) but nothing is persisted to the `RoutedOrder` record; refreshing the page loses the unsaved URL from local state.

## Notes
- **`RoutedOrder.status` and `Order.status` are two independent state machines** tracked on two separate admin screens (`routed-orders.md` here vs. `orders.md`) with only a one-way "open the original order" link bridging them — this is the single most important structural fact for the redesign to preserve or deliberately reconcile. Do not assume updating one updates the other; the current code does not do so anywhere in either PATCH handler.
- No admin/superadmin distinction — consistent with every other screen in this batch.
- This list's default page size (50) and lack of URL-persisted filter state are both inconsistent with Products/Orders (page size 20, URL-persisted via `useListUrlState`) — call out to PM/implementer whether to standardize during the rebuild or preserve as-is; either is a legitimate parity choice but it should be a deliberate one, not an oversight.
- `assignOrderToGovernorate` (the auto-routing engine that creates every `RoutedOrder` row in normal operation) prefers an order's already-locked-in `assignedPartnerId` (set at checkout/admin-order-creation time when stock was reserved from a specific partner) over re-deriving a partner from the delivery address's governorate rule — i.e. **routing follows where the stock actually came from, not necessarily the customer's shipping governorate**. This explains why `RoutedOrder.governorate` and the order's actual shipping-address governorate can legitimately differ, and why the manual reassignment dialog's lack of governorate filtering is arguably consistent with how auto-routing already works (stock/partner-driven, not strictly geography-driven) — flagging this so the redesign doesn't "fix" the reassign picker into a governorate-only filter without realizing normal auto-routing itself doesn't strictly enforce that either.
- Round-robin auto-assignment (`ReroutingRule.lastAssignedPartnerId`, cycling through `ReroutingRulePartner`s ordered by `priority` then `createdAt`) is configured on `/admin/rerouting-rules`, outside this inventory batch — this screen only consumes its output, it does not configure it.
