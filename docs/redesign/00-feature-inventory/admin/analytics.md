# Admin — Analytics (التقارير / Reports)

Route(s): `app/(admin)/admin/analytics/page.tsx` (single page, client component; no sub-routes).
Key files: `app/api/admin/analytics/route.ts` (GET, `section=kpis|revenue|products|all`), `app/api/admin/analytics/export/route.ts` (GET, CSV download, `report=summary|revenue|products`), `lib/analytics/queries.ts` (`getKpis`, `getRevenueOverTime`, `getProductVariantReport`), `lib/analytics/types.ts` (`REPORT_ORDER_STATUS = "DELIVERED"`), `lib/analytics/date-range.ts` (preset/clamping helpers), `lib/cache/analytics.ts` (Redis cache, 5-min TTL, version-keyed invalidation), `components/dashboard/kpi-card.tsx`.

## Business requirements
- **Goal/KPI**: the business's primary revenue/sales reporting tool for admins — gives date-ranged revenue, net-merchandise, and order-count KPIs, a revenue-over-time chart+table, and a searchable per-product-variant sales/stock breakdown, each independently exportable to CSV. Serves ops/finance visibility (which products sell, how revenue trends, current stock health) rather than customer-facing conversion.
- **Trust/credibility signals**: none customer-facing (internal tool). Internally, the screen is careful to label its scope precisely — "تم التسليم فقط" (delivered only) badge in the header and per-KPI hint text ("محصل من طلبات مُسلَّمة" / "بدون شحن ورسوم COD") — so a finance-literate admin doesn't misread "total revenue" as all-orders gross value.
- **Friction points**: (1) **all figures are DELIVERED-orders-only, unconditionally** — an admin cannot toggle to see all orders regardless of status, or exclude cancelled/returned separately, from this screen; if "revenue including pending orders" or "cancellation rate" is ever wanted, that's new scope. (2) The revenue chart is a plain CSS-bar visualization (no axis labels, no hover tooltip beyond the `title` attribute, no zero-data distinction from a rendering glitch) — fine for a quick glance, weak for serious analysis. (3) Product-variant table caps effectively at whatever `variant.findMany` returns for *all active products* (no pagination, just a `max-h-[32rem]` scrolling container) — could get slow/unwieldy with a large catalog since it loads every active variant's full sales-in-range data on every fetch. (4) No comparison-to-previous-period (e.g. "+12% vs last week") anywhere.
- **Compliance/legal**: none specific found; CSV exports contain only aggregate business data (revenue, product/SKU sales, stock), no customer PII.
- **Modern-look rationale**: KPI-cards + chart + searchable table is standard admin-reporting convention; no other business-driven layout constraint.

## Elements & behavior
- [ ] Header — gradient card with title "التقارير", static "تم التسليم فقط" success badge, description "ملخص الإيرادات والمبيعات للطلبات المُسلَّمة في الفترة المحددة.", and once loaded, the actually-applied period restated as text ("الفترة المعروضة: {from} – {to}").
- [ ] **Date-range filter card** — "من"/"إلى" native `<input type="date">` pickers (`clampStartDate`/`clampEndDate`/`resolveEndWhenStartChanges` from `lib/analytics/date-range.ts` keep `from ≤ to ≤ today`, and moving `from` forward past the current `to` pulls `to` along with it), a "التجميع" (granularity) `<select>` (يومي/أسبوعي/شهري = day/week/month, affects only the revenue-over-time bucketing), and four preset pill-buttons (آخر 7 أيام / آخر 30 يوم / هذا الشهر / من البداية) that snap `from`/`to` to `rangeForPreset()`'s computed range and visually highlight as active when the current `from`/`to` exactly match that preset's computed range.
- [ ] **KPI row** (3 `KpiCard`s, `md:grid-cols-3`):
  - "إجمالي الإيراد" — `SUM(Order.totalPiastres)` for delivered orders in range; hint "إجمالي محصل (شامل الشحن ورسوم COD)"; burgundy accent; has its own "تصدير الملخص" (export summary) link button beneath it.
  - "صافي المنتجات" — `SUM(subtotalPiastres - discountPiastres - seniorFreeValuePiastres)` computed in application code over the fetched order rows (not a DB-side aggregate); hint "بعد الخصومات، بدون الشحن ورسوم COD"; gold accent.
  - "طلبات مُسلَّمة" — delivered order count in range; emerald accent.
- [ ] **Revenue-over-time card** — CSS bar chart (bar height ∝ `totalRevenuePiastres / max(bucket revenue)`, min 8px, `title` attribute shows exact EGP value on hover) followed by a full data table (الفترة / إجمالي الإيراد / صافي المنتجات / الطلبات per bucket) — bucket key format depends on granularity (`YYYY-MM-DD` day, week-start `YYYY-MM-DD` [Sunday-based, `start.getDate() - start.getDay()`], or `YYYY-MM` month). Card header has its own "تصدير CSV" export button.
- [ ] **Products & variants card** — header shows live counts ("{N} متغير · {M} بمبيعات في الفترة"), a client-side `SearchInput` (filters already-fetched rows by product name / variant name / SKU / color name, case-insensitive, no debounce needed since it's client-side), and its own "تصدير CSV" export button. Table columns: المنتج, المقاس (variant name), اللون (colorName or "—"), SKU (monospace), السعر (current variant price, not historical), مباع (`quantitySold` in range — green badge if >0, plain "0" if not), إيراد البنود (line revenue in range, or "—" if zero), متبقي (`stockAvailable` — destructive-red badge if exactly 0), محجوز (`stockReserved`). Rows with `quantitySold > 0` get a subtle green row tint. Table header is sticky within its scroll container.
- [ ] **CSV exports** — three independent endpoints (`report=summary|revenue|products`), each opened via `window.open(url, "_blank")` (new tab, not a programmatic download-triggering fetch), each honoring the currently-selected `from`/`to` (and `granularity` for the revenue report only); files are UTF-8 with BOM (`﻿` prefix, for Excel Arabic/number compatibility) and use English column headers even though the rest of the UI is Arabic.
- [ ] **Caching** — `GET /api/admin/analytics` caches `kpis` and `revenue` sections in Redis for 5 minutes, keyed by `from/to/granularity`, **but only when no explicit `from`/`to` is passed** (`useCache = ...&& !from && !to`); since this page always passes explicit dates (even for presets), **this screen's requests never hit the cache** in practice — caching only benefits some other caller passing no date params (e.g. the admin dashboard's KPI-only call, see `admin/dashboard.md`). Cache invalidation is version-key-based (`invalidateAnalyticsCache()`, presumably called after order-state changes elsewhere — not read as part of this screen).
- [ ] Stock figures (`stockAvailable`/`stockReserved`) reflect **current** inventory at fetch time, not a historical snapshot as of the selected date range — they're read live from `Variant`/`PartnerInventory`, unrelated to the date filter.

## States
- [ ] Empty state (revenue) — BarChart3 icon + "لا توجد بيانات في الفترة المحددة." when zero buckets returned for the range.
- [ ] Empty state (products) — Package icon + either "لا توجد نتائج للبحث." (search active, zero matches) or "لا توجد منتجات نشطة." (genuinely zero active products).
- [ ] Loading state — first load: full-page `ReportsSkeleton` (header bar + 3 KPI-card skeletons + chart skeleton + table skeleton, stacked). Subsequent refetches (date/granularity change): the entire content area drops to 70% opacity (`loading && data && "opacity-70"`) while keeping the previous data visible, rather than re-showing skeletons.
- [ ] Error state — **no explicit error UI.** If the fetch fails (`!res.ok`) or returns `success: false`, `data` is set to `null` and `loading` flips false — every KPI/table/chart then renders its own "no data" empty state (visually indistinguishable from a genuinely empty date range). No toast, no banner, no retry button anywhere on this screen.
- [ ] Permission-restricted state — enforced at `app/(admin)/layout.tsx` only; nothing analytics-specific.

## Edge cases
- [ ] `from` > `to` — prevented entirely by the date-input clamping helpers (`min`/`max` attrs plus the `clampStartDate`/`clampEndDate`/`resolveEndWhenStartChanges` logic keeps the pair always valid); not reachable as a bad-state through this UI.
- [ ] "من البداية" (all-time) preset combined with a large order history — no client-side pagination/virtualization on the products table beyond a fixed-height scroll container; performance at scale is untested from code alone (flagging, not asserting a bug).
- [ ] A variant with sales in-range but that has since been deactivated (`product.active: false`) — **excluded entirely** from the products table (`where: { product: { active: true } }` on the variants query), even though its historical `quantitySold`/`lineRevenuePiastres` technically exist in `OrderItem` data — so the revenue KPI totals and the product-table's sum of line revenues are not guaranteed to reconcile once a product is deactivated after having sold.
- [ ] Exporting CSV for an empty range — still returns a valid CSV with header row(s) only (no special "no data" handling in the export route), so the download isn't blocked, just minimal.
- [ ] Multi-select/partner-scoped analytics — `lib/analytics/queries.ts`'s functions all accept an optional `scope: { partnerId }` parameter, but this admin screen never passes one (full-store view only) — that scoping exists for the *partner-facing* analytics screen (`partner/reports`, out of scope here), not this one.

## Notes
- **"صافي المنتجات" (net merchandise) is computed in application code, not a database aggregate** — the API fetches every matching order's `subtotalPiastres`/`discountPiastres`/`seniorFreeValuePiastres` and sums the derived value in JS (`netMerchandisePiastres()` in `lib/analytics/queries.ts`). A rebuild reimplementing this as a raw SQL `SUM()` should replicate the exact formula: `subtotalPiastres - discountPiastres - seniorFreeValuePiastres`.
- All figures on this screen are scoped to `Order.status === "DELIVERED"` only (`REPORT_ORDER_STATUS` constant) — this is a hardcoded, non-optional filter, not a default that can be widened from the UI.
- This is the only one of the 7 screens in this batch with genuine chart/visualization surface — worth extra design attention in the rebuild (per the `dataviz` design guidance, if the redesign session uses it) given the current implementation is a minimal hand-rolled CSS bar chart with no library.
- The Redis caching layer (`lib/cache/analytics.ts`) is effectively dead weight *for this specific screen* today, per the "never hits cache" finding above — worth flagging to the PM/implementer so nobody assumes this screen is cache-accelerated when profiling performance.
