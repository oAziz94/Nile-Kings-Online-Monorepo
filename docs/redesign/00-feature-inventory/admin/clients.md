# Admin — Clients

Route(s): `app/(admin)/admin/clients/page.tsx` (list), `app/(admin)/admin/clients/new/page.tsx` (create), `app/(admin)/admin/clients/[id]/page.tsx` (profile/detail — **shared with the Admins screen**, see Notes) — all client components.
Key files: `app/api/admin/clients/route.ts` (GET list w/ role filter+search+pagination, POST create), `app/api/admin/clients/[id]/route.ts` (GET profile only — no PATCH/DELETE), `app/api/admin/clients/[id]/grant-admin/route.ts` (POST — promotes a `CUSTOMER` to `ADMIN`), `app/api/admin/clients/[id]/addresses/[addressId]/route.ts` (PATCH one saved address), `lib/admin/address.ts` (`parseCreateAddressInput`), `lib/auth/password.ts` (`hashPassword`), `lib/phone.ts` (`normalizeEgyptMobilePhone`), `lib/services/shipping.ts` (`GOVERNORATE_OPTIONS`), `prisma/schema.prisma` (`User`, `SavedAddress`, `Order` — profile shows a slice of each).

## Business requirements
- **Goal/KPI**: ops-efficiency (support/CS tooling) — lets an admin look up a customer by phone/name, see their saved addresses and order history in one place, fix an address on a customer's behalf (support request), or manually create an account for a customer who's ordering over phone/WhatsApp rather than self-registering. The "جعل مسؤولاً" (grant admin) action is the *only* way to promote a trusted staff member to admin access — no separate admin-invite flow exists.
- **Trust/credibility signals**: none directly customer-facing (internal tool), but data integrity matters — this screen can silently grant full, ungated admin access to any customer account (see role-model note below), so its "grant admin" affordance is a real security control point, not just data entry.
- **Friction points**: (1) **an admin cannot edit a client's own name/phone/email from this UI** — `GET /api/admin/clients/[id]` has no corresponding PATCH; only saved *addresses* are editable. A support agent fixing a typo'd name or phone has no in-app way to do it. (2) No way to deactivate, suspend, or delete a client account from this UI (no DELETE route for `User` at all). (3) No password-reset-on-behalf-of-customer tool visible here (out of scope check — not found in this screen or its API routes). (4) The address-edit dialog silently omits `building`/`floor`/`apartment` fields (present in the data model and shown read-only in the address list) — see Edge cases.
- **Compliance/legal**: `password` is required (min 8 chars) and hashed (`hashPassword`) when admin-creating a client — reasonable. Phone numbers are normalized via `normalizeEgyptMobilePhone` and must be unique. No visible PII-handling beyond what's already required by the data model.
- **Modern-look rationale**: none beyond standard list/detail/create admin conventions.

## Elements & behavior

### List (`/admin/clients`)
- [ ] `PageHeader` — title "العملاء", description "حسابات العملاء فقط، مع العناوين والطلبات المرتبطة بكل عميل.", action "عميل جديد" → `/admin/clients/new`.
- [ ] Table, **filtered server-side to `role=CUSTOMER` only** (`ADMIN`-role users never appear here, even though the underlying `GET /api/admin/clients` endpoint is role-parameterized and shared with the Admins screen). Columns: الهاتف (monospace), الاسم (or "—"; a "كبار سن" secondary badge appended if `seniorVerified`), البريد (or "—"), العناوين (`_count.savedAddresses`), الطلبات (`_count.orders`), التسجيل (`formatDateEn(createdAt)`), إجراءات ("عرض الملف" → `/admin/clients/[id]`).
- [ ] Search — `SearchInput`, 400ms debounce, matches `phone` OR `name` OR `email` (case-insensitive `contains`), resets to page 0 on change.
- [ ] Pagination — `PaginationBar`, default 20/page, server-paginated.

### New (`/admin/clients/new`)
- [ ] Two-card form: "بيانات الحساب" (phone [required, LTR/monospace input, placeholder "+2010..."], name [required, min 2 chars], email [optional], password [required, min 8 chars]) and "عنوان التوصيل الافتراضي" (label defaulting to "المنزل", governorate `Select` from `GOVERNORATE_OPTIONS` [required], city [required], area [required], street [required], delivery phone [required, separate from account phone], notes [optional]) — the created address is always `isDefault: true`.
- [ ] Client-side validation before submit: phone+name required, name ≥2 chars, password ≥8 chars, all address fields required (governorate/city/area/street/addressPhone) — all as a single combined toast per failed group, not per-field inline errors.
- [ ] Submit → `POST /api/admin/clients` with the full payload in one transaction (`prisma.$transaction`: creates `User` with `role: "CUSTOMER"`, then the `SavedAddress`). Duplicate phone → 400 "هذا الرقم مسجّل مسبقاً". On success, redirects to the new client's profile page.

### Profile/detail (`/admin/clients/[id]`) — shared page for both Clients and Admins
- [ ] Header title switches based on the viewed user's role: "ملف العميل" for `CUSTOMER`, "ملف المسؤول" for `ADMIN`; back-link target switches accordingly (`/admin/clients` vs `/admin/admins`).
- [ ] "البيانات الأساسية" card — read-only display of phone (monospace), name (or phone if no name), "كبار سن" badge if `seniorVerified`, "مسؤول" badge if `role === "ADMIN"`, email if set, registration date. **No edit affordance for any of these fields.**
- [ ] "جعل مسؤولاً" (grant admin) button — **only rendered when `role === "CUSTOMER"`** (a `CUSTOMER`-role client viewing their own admin-granted profile would no longer see it, since the button's visibility is keyed off the freshly-fetched role, not a static list membership). Opens a confirm dialog ("سيتمكن هذا المستخدم من الدخول إلى لوحة التحكم بنفس رقم الهاتف بعد تسجيل الدخول مرة أخرى") → `POST /api/admin/clients/[id]/grant-admin`. On success: if the user was already admin, shows "المستخدم مسؤول بالفعل" toast and just closes the dialog; if newly granted, shows a success toast and **hard-navigates to `/admin/admins`** (`window.location.href`, full page reload, not a router push).
- [ ] "العناوين المحفوظة" card — count in the title; lists every `SavedAddress` with label, "افتراضي" (default) badge, full formatted address (governorate/city/area/street/building/floor/apartment as available), delivery phone, notes; each has a "تعديل العنوان" (edit) button opening an edit dialog.
- [ ] Address edit dialog fields: وصف العنوان (label), المحافظة (`Select`, required), المدينة (required), المنطقة (required), العنوان بالتفصيل/street (required), هاتف التوصيل (required, LTR), ملاحظات (optional), "اجعل هذا العنوان افتراضي" checkbox. **Does not include building/floor/apartment inputs** even though they're part of the data model and shown in the read-only list above (see Edge cases).
- [ ] Setting an address as default via this dialog unsets `isDefault` on all the client's other addresses server-side (`updateMany` before the target update) — standard single-default-address invariant.
- [ ] "الطلبات" card — count in title; table of up to the 50 most-recent orders (رقم [8-char id prefix], الحالة [status label via shared `ORDER_STATUS_LABELS`], الإجمالي [EGP], التاريخ, "عرض الطلب" link → `/admin/orders/[id]`); a footer note "عرض آخر {N} طلب من إجمالي {total}" appears if the true order count exceeds the 50 shown.
- [ ] No address-deletion, no order-cancellation, and (as noted above) no name/phone/email edit anywhere on this screen.

## States
- [ ] Empty state (list) — `EmptyState`, Users icon; "لا توجد نتائج للبحث" if searching, else "لا يوجد عملاء".
- [ ] Empty state (profile) — "لا توجد عناوين محفوظة." / "لا توجد طلبات." as plain `<p>` text (not the shared `EmptyState` component) inside each respective card.
- [ ] Loading state — list: full-width `Skeleton` while `loading && clients.length === 0`; subsequent refetches show an inline "جاري التحديث…" spinner + 70%-opacity stale table (same pattern as Coupons). Profile: single full-width `Skeleton` (`h-96`) until the client fetch resolves. New-client form has no loading state pre-submit.
- [ ] Error state — toast-only everywhere (list fetch failure, profile fetch failure, address-save failure, grant-admin failure, create-client failure) — no inline banners or retries.
- [ ] Permission-restricted state — enforced at `app/(admin)/layout.tsx` only; nothing client-list-specific. Note there is also no *per-client* restriction — any admin can view/edit any client or grant admin to any customer, with no additional confirmation tier (see role-model note below and in `admins.md`).

## Edge cases
- [ ] Grant-admin on an already-admin user — API returns `{ alreadyAdmin: true }` (200, not an error) and the UI shows "المستخدم مسؤول بالفعل" without navigating away — idempotent by design.
- [ ] Editing a saved address's building/floor/apartment — **not possible through this UI.** The edit dialog's `AddressForm` type only carries `label, governorate, city, area, street, notes, phone, isDefault`; the PATCH API supports `building`/`floor`/`apartment` (and correctly no-ops on omitted fields, so existing values aren't wiped), but this admin UI never sends them, so they can only be set via the original customer-facing checkout flow, never fixed here.
- [ ] Admin phone reused as an "AGENT"/partner phone, or vice versa — not checked here; `User.phone` is globally unique across all roles (`@unique` on `User.phone`), so a phone already used by any account (customer, admin, or partner-linked user) blocks new-client creation with the generic "هذا الرقم مسجّل مسبقاً" message, without clarifying which role currently holds it.
- [ ] Viewing a client with zero orders/addresses — both cards render their empty-text variants independently; no combined "new client, nothing here yet" messaging.
- [ ] `_count.orders` in the list can exceed the 50-row cap shown on the profile page — list and profile both surface the true total (`_count.orders`) even when the profile's own order table is truncated to 50.

## Notes
- **`app/(admin)/admin/clients/[id]/page.tsx` is the same page component the Admins screen (`admins.md`) links to** — there is no separate admin-account detail page. A rebuild should treat client-profile and admin-profile as one shared detail view with role-conditional copy/actions, not two screens, or explicitly decide to split them (a real design choice, not a bug to "fix").
- **Role model, confirmed from `prisma/schema.prisma` (`enum UserRole { CUSTOMER ADMIN PARTNER }`) and `lib/auth/session.ts`**: this screen only ever deals with `CUSTOMER` and `ADMIN`. There is no granular permission system — `grant-admin` sets `User.role = "ADMIN"` outright, which (per `resolveAdminUser()`) grants unrestricted access to every `/admin/*` screen with no scoping, no "read-only admin," no per-section permission. See `admins.md` for the full role-model writeup (same finding, documented once per screen since both need it for their own rebuild).
- There is **no impersonation / "log in as this customer" tooling anywhere in the codebase** (searched for `impersonat*`, `login-as`, etc. — no matches). Any customer-support debugging is done by admins directly viewing this profile page's data, not by assuming the customer's session.
- `seniorVerified` badge here is read-only display; the actual senior-citizen verification flow (national ID upload/check) lives in the customer-facing `(public)/profile/senior` screen and its own admin-adjacent settings toggle (see `settings.md` re: the orphaned `SeniorPromoToggle`), not here.
