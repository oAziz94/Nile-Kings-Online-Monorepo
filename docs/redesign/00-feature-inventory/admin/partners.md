# Admin — Partners (requests, agents, distributors, manual entry)

Route(s): `app/(admin)/admin/partners/page.tsx` (single page, 4 tabs: طلبات شراكة / وكلاء / موزعين / إدخال شريك جديد — no `[id]`/`new` sub-routes)
Key files: `lib/services/shipping.ts` (`GOVERNORATE_OPTIONS`), `lib/phone.ts` (`normalizeEgyptMobilePhone`), `app/api/admin/partner-requests/route.ts`, `app/api/admin/partner-requests/[id]/route.ts`, `app/api/admin/partner-requests/[id]/convert/route.ts`, `app/api/admin/partners/route.ts`, `app/api/admin/partners/[id]/route.ts`. Covered as one file — all four tabs live in one page component and share the `Partner`/`PartnerRequest` data model.

## Business requirements
- **Goal/KPI**: this screen is the admin's control point for growing and vetting the regional-partner network (agents = governorate-level, distributors = linked sub-partners under an agent) that `routed-orders.md` and `partner-inventory.md` depend on — it's the onboarding funnel (public "become a partner" request form → admin triage → converted into a live `Partner` record that can then hold inventory and receive routed orders). Directly serves fulfillment-network growth/operational scaling, not customer-facing conversion.
- **Trust/credibility signals**: none customer-facing (internal tool); the public-facing partner-request form referenced here (`(public)` surface, out of this inventory batch) is where trust signals toward prospective partners would live, not here.
- **Friction points**:
  - **Existing agents/distributors are view-only from this screen** — the detail dialogs on both the "وكلاء" and "موزعين" tabs render static read-only fields with no edit form, despite `PATCH /api/admin/partners/{id}` fully supporting edits to name/governorate/phone/social links/`linkedAgentId`/`isActive`/notes. There is no way to deactivate, edit, or re-link an existing partner anywhere in this admin UI — only to view them. This looks like a real gap, not an intentional read-only design (the "إدخال شريك جديد" tab exists specifically to *create* partners, implying partner management was meant to be editable) — flag to PM/eng as likely unfinished, not a deliberate constraint to preserve as-is. `[NEEDS PM INPUT: confirm whether partner edit/deactivate UI is simply missing (bug/gap) or intentionally out of scope for this screen, e.g. handled elsewhere.]`
  - The partner-request "status" control and the "قبول وتحويل" (accept & convert) action are two independent paths to superficially the same outcome, but only one of them actually creates a `Partner` record — see Notes for the resulting stuck-state risk.
  - No delete for partners or partner-requests anywhere (consistent with the rest of the admin app's general no-hard-delete posture, though here it may simply be because there's no edit UI to build a delete affordance next to).
- **Compliance/legal**: phone numbers are normalized/validated to Egyptian mobile format (`normalizeEgyptMobilePhone`) on both partner-request submission (upstream, public form) and manual partner creation/edit here — consistent phone validation matters for actually being able to reach partners operationally.
- **Modern-look rationale**: tabbed single-page layout (rather than separate routes) keeps the four related partner-management concerns in one place; no other layout-driven business rationale.

## Elements & behavior

### Shared page shell
- [ ] `PageHeader` — title "شركاؤنا", description "طلبات الشراكة، الوكلاء، الموزعون، وإدخال شركاء جدد."
- [ ] Four tabs as plain client-state (`activeTab`, not URL-persisted — switching tabs and refreshing the page always returns to "طلبات شراكة"): طلبات شراكة (requests), وكلاء (agents), موزعين (distributors), إدخال شريك جديد (new partner entry). Each tab is its own independently-fetching component (no shared loading/search state across tabs).
- [ ] Cross-tab sync: converting a request to a partner dispatches a `window` `CustomEvent("partners-list-updated", { detail: { type } })`; the Agents/Distributors tabs each listen for this and reload their list only if `type` matches their own tab — so accepting a distributor request while sitting on the Agents tab does not refresh what the admin is currently looking at (it silently updates in the background only if they later switch to Distributors, at which point it re-fetches from scratch anyway on mount — so in practice this listener mostly matters for a tab that's already mounted and visible).

### طلبات شراكة (Partner Requests) tab
- [ ] Search (plain `Input`, not the shared `SearchInput`/`useListUrlState` pattern used elsewhere — this whole page uses hand-rolled debounce/pagination state per tab instead of the shared hooks), debounced 400ms, matches request `name`/`phone`/`governorate` (all contains/insensitive) — **the API also accepts a `status`/`requestType` filter query param but this tab's UI never sends one**, so requests of every status/type are always shown together, distinguished only by the الحالة column. Page size 20, default page 0 — pagination via the same `PaginationBar` component as elsewhere.
- [ ] Table columns: النوع (وكيل/موزع), الاسم, المحافظة, رقم التليفون, تاريخ الطلب, الحالة (`Badge`: default/"APPROVED"→green-ish default variant, destructive/"REJECTED"→red, secondary otherwise for PENDING/CONTACTED), الإجراءات.
- [ ] Row actions:
  - "عرض" (view) — opens a read-only detail dialog: type, name, governorate, phone, request date, status, notes (if any), and a bullet list of any social/website links provided (Facebook/Instagram/TikTok/YouTube/Website/Other — only the ones actually filled in are shown).
  - "حالة" (status) — opens an edit dialog with a status `<select>` (all 4 `PartnerRequestStatus` values freely selectable, no transition constraints) and a notes `<textarea>`; "حفظ" PATCHes `{ status, notes }` together in one call. **This is a distinct, independent path from "قبول وتحويل" below — using it to set status to APPROVED does NOT create a `Partner` record** (see Notes for the resulting gap).
  - "قبول وتحويل" (accept & convert) and "رفض" (reject) — **only rendered when `status` is not already `APPROVED` or `REJECTED`** (i.e. these disappear once a request reaches either terminal status, including if it was set to APPROVED via the plain "حالة" dialog without ever being converted).
    - "رفض" — one-click `PATCH { status: "REJECTED" }`, no confirmation dialog, no reason/notes prompt.
    - "قبول وتحويل" — opens a dialog; for AGENT requests, informational text only ("سيتم إنشاء وكيل جديد" — a new agent will be created), no further input; for DISTRIBUTOR requests, an optional "الوكيل" (linked agent) `<select>` populated from all existing AGENT-type partners (fetched fresh on dialog open, limit 200, **no search/filter on this dropdown** — could be unwieldy with many agents), defaulting to "— لا وكيل —" (no agent) if left unselected. Confirms via `POST /api/admin/partner-requests/{id}/convert[?linkedAgentId=...]`.
    - Server-side convert: creates a new `Partner` row copying name/governorate/phone (re-normalized)/all social-link fields/notes from the request, forces `isActive: true`, sets `linkedAgentId` only for DISTRIBUTOR type (validated to reference an existing **active** AGENT — 400 "الوكيل المحدد غير موجود أو غير نشط" if not; explicitly rejects attempting to link an AGENT request to another agent — 400 "وكيل لا يمكن ربطه بوكيل آخر"), and atomically sets the source `PartnerRequest.status = "APPROVED"` in the same transaction. This is the **only** code path that both creates a `Partner` from a request and is guaranteed to mark it `APPROVED` consistently with that creation.
- [ ] No bulk actions on this tab (no multi-select).

### وكلاء (Agents) tab
- [ ] Search (name/phone), debounced 400ms, page size 20; fetches `GET /api/admin/partners?partnerType=AGENT` with explicit `cache: "no-store"` / `Cache-Control: no-cache` headers (deliberately bypassing any HTTP caching layer, unlike other list fetches in the admin app which don't set these — likely because this list needs to reflect just-converted partners immediately).
- [ ] Table columns: الاسم, المحافظة, رقم التليفون, عدد الموزعين المرتبطين (`_count.distributors` — how many distributors link to this agent), الحالة (`Badge`: default/"نشط" if active, secondary/"غير نشط" if not), الإجراءات ("عرض التفاصيل" only).
- [ ] Detail dialog (`GET /api/admin/partners/{id}`, includes `linkedAgent` + `distributors`) — **read-only**: name, governorate, phone, active/inactive status, and a bulleted list of every linked distributor (name + phone). No edit fields, no save button, no way to toggle `isActive` or edit any field from this dialog (see Business requirements gap).
- [ ] Sort: `createdAt desc` only, no column sort.

### موزعين (Distributors) tab
- [ ] Identical structure/behavior to the Agents tab (`partnerType=DISTRIBUTOR`), except the table's fourth column is الوكيل المرتبط (linked agent's name, or "—" if none) instead of a distributor count, and the detail dialog shows الوكيل المرتبط instead of a distributors list. Same "view-only, no edit" limitation.

### إدخال شريك جديد (New Partner Entry) tab
- [ ] Manual partner-creation form (bypasses the request/convert flow entirely — for partners onboarded outside the public request form, e.g. by phone/in-person). Fields: نوع الشريك (`<select>` وكيل/موزع, default AGENT), الاسم (required), المحافظة (required `<select>` populated from `GOVERNORATE_OPTIONS` — the same canonical governorate list used by shipping-rule/address logic elsewhere in the app), رقم التليفون (required, validated/normalized server-side to Egyptian mobile format — 400 with a specific error message if invalid), الوكيل المرتبط (اختياري) (only shown when partnerType = DISTRIBUTOR; `<select>` of existing agents, same un-searchable up-to-200 list as the convert dialog), نشط (checkbox, default checked), ملاحظات (free `<textarea>`).
- [ ] Client validation: only name/governorate/phone required (toast "الاسم والمحافظة ورقم التليفون مطلوبة" if any missing) — no client-side phone-format check, relies entirely on the server's `normalizeEgyptMobilePhone`.
- [ ] On success: toast "تم إضافة الشريك بنجاح", form fully resets to defaults, and `onSuccess()` **switches the active tab to "وكلاء" (Agents) regardless of whether a DISTRIBUTOR was just created** — a genuine bug/inconsistency: creating a new distributor lands the admin on the Agents tab, not Distributors, where they won't see what they just created without manually switching tabs.

## States
- [ ] Empty state (each tab) — dashed-border placeholder box (not the shared `EmptyState` component used elsewhere — this page hand-rolls its own empty-state markup), icon + Arabic message: requests → "لا توجد نتائج للبحث"/"لا توجد طلبات شراكة"; agents → "لا توجد نتائج للبحث"/"لا يوجد وكلاء"; distributors → "لا توجد نتائج للبحث"/"لا يوجد موزعين".
- [ ] Loading state — each tab shows its own full-card skeleton on first load only; subsequent refetches show the shared inline "جاري التحديث…" spinner + dimmed table pattern.
- [ ] Error state — each tab's list fetch has its own `.catch` → destructive toast ("فشل تحميل الطلبات" / "فشل تحميل الوكلاء" / "فشل تحميل الموزعين"); mutating actions (status update, reject, convert, create) surface server error messages via toast or a generic fallback, with no dedicated inline error banner.
- [ ] Permission-restricted state — enforced at `app/(admin)/layout.tsx` + `requireAdmin()` per route; no finer-grained tiers.

## Edge cases
- [ ] Setting a partner request's status to `APPROVED` via the "حالة" (status) dialog instead of "قبول وتحويل" (convert) — **creates no `Partner` record**, yet the row immediately loses its convert/reject action buttons (they're hidden whenever `status` is APPROVED or REJECTED) — the request is now stuck in an approved-but-never-converted state with no UI path back to converting it short of manually re-opening the status dialog, setting it back to PENDING/CONTACTED, and then using "قبول وتحويل". `[NEEDS PM INPUT: is this a known/acceptable quirk, or should "قبول وتحويل" be the only way to reach APPROVED, i.e. should the status dropdown exclude APPROVED?]`
- [ ] Creating a distributor from either the convert dialog or the manual-entry tab without selecting a linked agent — allowed (`linkedAgentId` stays `null`); such distributors show "—" for الوكيل المرتبط everywhere.
- [ ] Manual entry of a new DISTRIBUTOR partner — succeeds but silently lands the admin on the Agents tab afterward (see Elements & behavior); the newly created distributor is not visibly confirmed beyond the toast unless the admin manually clicks the Distributors tab.
- [ ] Agent/distributor linked-agent dropdowns (in both convert and manual-entry flows) load up to 200 agents with no search — a partner network beyond ~200 agents would silently truncate this list with no "load more"/search affordance.
- [ ] Rejecting a partner request — completely irreversible from this UI (no "un-reject"/reopen action; only the generic "حالة" dialog could manually set it back to PENDING, which is not an obvious recovery path to a typical admin).
- [ ] Phone number entered in a locally-formatted-but-non-Egyptian-mobile shape — rejected server-side with `EGYPT_MOBILE_ERROR_MESSAGE` on both create and edit; no client-side format hint/mask shown before submit.

## Notes
- **No admin/superadmin distinction** — consistent with every other screen in this batch.
- **This is the one screen in the batch with a real, likely-unintentional functional gap**: existing partners (both agents and distributors) cannot be edited, deactivated, or re-linked from this UI at all — only viewed and newly created. The backend (`PATCH /api/admin/partners/[id]`) is fully built for this (supports every field including `isActive` and `linkedAgentId`); only the frontend affordance is missing. This is the single most important "add, don't just preserve" candidate to raise with the PM before/during the rebuild, since faithfully reproducing "view-only" would just carry the gap forward.
- The partner-request → partner conversion flow is the only place in this screen where a `Partner` record is reliably created in a way that also correctly updates the source request's status in the same transaction; the plain status-dialog "APPROVED" path is a trap that looks like the same outcome but isn't (see Edge cases).
- Unlike Products/Orders/Categories, this page does not use the shared `useListUrlState`/`SearchInput`/`EmptyState` components — each of the three list tabs hand-rolls its own search/pagination/empty-state code with parallel but not-identical implementations (page size 20 here vs. list screens elsewhere; `GET /api/admin/partners` itself defaults to page size 50 when called without an explicit `limit`, e.g. from the convert/manual-entry dropdown's `limit=200` override — the *page's* own list tabs explicitly pass `limit=20`). Worth normalizing during the rebuild, but flagging so the rebuild doesn't assume this page already follows the same list-pattern conventions as Products/Orders.
- `GOVERNORATE_OPTIONS` (from `lib/services/shipping.ts`) is the canonical governorate list reused across this form, shipping-rule configuration, and address entry elsewhere in the app — the manual-partner-entry governorate dropdown should stay wired to that single source, not a locally hardcoded list.
