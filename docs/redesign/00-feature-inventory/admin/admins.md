# Admin — Admins (admin-account management)

Route(s): `app/(admin)/admin/admins/page.tsx` (list only — client component). There is **no** `/admin/admins/[id]` or `/admin/admins/new` route; profile viewing reuses `/admin/clients/[id]` (see `clients.md`), and there is no dedicated admin-creation flow (see Notes).
Key files: `app/api/admin/clients/route.ts` (same endpoint as the Clients screen, called here with `role=ADMIN`), `app/api/admin/clients/[id]/grant-admin/route.ts` (the only way an admin account is ever created — via promotion, not direct creation), `lib/auth/session.ts` (`requireAdmin`, `resolveAdminUser`, `userHasAdminAccess` — the entire permission model), `prisma/schema.prisma` (`enum UserRole`, `model User`).

## Business requirements
- **Goal/KPI**: ops/security visibility — lets an admin see who else currently has admin panel access (a short, presumably small list for a business this size) and reach their profile. This is the closest thing this app has to a "team management" screen.
- **Trust/credibility signals**: none customer-facing. Internally, this screen is a security-relevant control point: it's the only way to audit who can log into `/admin/*`, so its accuracy matters even though it's read-mostly.
- **Friction points**: (1) **This screen cannot create an admin account directly** — there's no "new admin" button/form anywhere on this page. The only path to a new admin is: go to Clients, find (or first create) a `CUSTOMER` account, open their profile, click "جعل مسؤولاً". This is a real, non-obvious multi-screen flow the redesign must preserve (or deliberately improve, as a proposal). (2) **There is no way to revoke admin access from this UI** — no "demote to customer" button anywhere, on this screen or the shared profile page. Once granted, admin access can only be removed by directly editing the database. (3) No way to remove/deactivate/delete an admin account at all. (4) No last-login or "last active" column, so staleness of admin accounts (e.g., an ex-employee) isn't visible without cross-referencing other data.
- **Compliance/legal**: this is the screen where the gap matters most — there is no confirmation step, no audit trail, and no reversibility for granting full administrative access to any customer account (see Notes — this directly touches the audit-log context called out in `docs/redesign/07-analytics-and-audit-plan.md`: admin-account changes are explicitly listed there as *not yet* covered by any audit log, and this inventory confirms that firsthand — no audit trail is written or displayed anywhere around grant-admin).
- **Modern-look rationale**: none — this is a short, simple internal roster table.

## Elements & behavior
- [ ] `PageHeader` — title "المسؤولون", description "حسابات الفريق التي لديها صلاحية دخول لوحة الإدارة." **No action button** (unlike every other list screen in this batch, which has a "new" CTA — there genuinely isn't one here, see Friction points).
- [ ] Table — fetches `GET /api/admin/clients?role=ADMIN&...` (same endpoint/component shape as the Clients list, just a different `role` filter baked into the request). Columns: الهاتف (monospace), الاسم (or "—"), الصلاحية (**static** "مسؤول" badge on every row — there is only one admin tier, so this column carries no information beyond confirming the row is in fact an admin), البريد, الطلبات كعميل (`_count.orders` — notably labeled "orders *as a customer*", acknowledging an admin account can also have placed orders as a regular customer before/after promotion), تاريخ الإنشاء, إجراءات ("عرض الملف" → `/admin/clients/[id]`, same shared profile page as Clients).
- [ ] Search — `SearchInput`, 400ms debounce, same `phone`/`name`/`email` contains-match as Clients, scoped to `role=ADMIN` rows only.
- [ ] Pagination — `PaginationBar`, default 20/page, server-paginated.
- [ ] Clicking "عرض الملف" lands on the same detail page documented in `clients.md`, which for an `ADMIN`-role user shows "ملف المسؤول" as its title, a "مسؤول" badge, and (critically) **no "جعل مسؤولاً" button** since that's conditionally rendered only for `role === "CUSTOMER"` — so once on this screen, there is no visible action button of any kind for managing that admin's access from the profile either.

## States
- [ ] Empty state — `EmptyState`, ShieldCheck icon; "لا توجد نتائج للبحث" if searching, else "لا يوجد مسؤولون" (would only realistically show on a fresh/misconfigured deployment, since at least one admin must exist to be viewing this screen at all).
- [ ] Loading state — full-width `Skeleton` (`h-64`) on initial load; inline "جاري التحديث…" spinner + 70%-opacity stale table on refetch (identical pattern to Clients/Coupons).
- [ ] Error state — toast-only ("فشل تحميل المسؤولين"), no inline banner or retry.
- [ ] Permission-restricted state — enforced at `app/(admin)/layout.tsx` only. Notably: **this screen itself applies no additional restriction beyond generic admin access** — any admin can view the full admin roster and, by navigating to Clients, grant admin to anyone. There is no "who can grant admin" sub-permission.

## Edge cases
- [ ] An admin account with zero orders as a customer — "الطلبات كعميل" column simply shows `0`, no special-casing.
- [ ] Self-view — an admin viewing their own row/profile sees the exact same read-only layout as viewing any other admin; no "(you)" marker, no self-demote or self-edit affordance (there being none for anyone regardless).
- [ ] Only one admin exists (the deploying developer's own account, typically) — nothing in the UI signals this is a fragile single-point-of-failure state (e.g., no warning "this is the last admin").

## Notes
- **The permission model, stated plainly for the rebuild's role-model design (this is the single most important finding across all 7 screens in this batch):** `prisma/schema.prisma` defines `enum UserRole { CUSTOMER ADMIN PARTNER }` — three flat, mutually-exclusive roles on `User.role`. There is **no sub-tiering within ADMIN** (no "superadmin," "read-only admin," "support admin," etc.) anywhere in the codebase. `lib/auth/session.ts`'s `resolveAdminUser()` is literally `if (dbUser.role !== "ADMIN") return null` — binary, all-or-nothing. Every admin can reach every screen in the entire `/admin/*` surface (confirmed by `AdminShell`'s nav, which renders the same links for every admin identity with no conditional filtering) and perform every action documented across this inventory batch, including granting admin to arbitrary customers. **Do not design a granular RBAC/permissions UI for the redesign's admins screen unless the PM explicitly scopes that as new work** — building one would silently exceed current parity and could actively mislead admins into thinking access is scoped when it isn't.
- **Admin creation is a one-way promotion, not a distinct "create admin" flow.** There is no form anywhere to create a brand-new admin account with its own phone/password directly as an admin — you must go through Clients → (optionally create) → profile → "جعل مسؤولاً". If the redesign wants a direct "invite/create admin" flow on this screen, flag it in `02-proposals.md` — it would be new functionality, not a UI-only parity change, since no backing API for direct-admin-creation exists (`POST /api/admin/clients` hardcodes `role: "CUSTOMER"`).
- **No demotion/revocation path exists anywhere** — confirmed by reading every route under `app/api/admin/clients/` and `app/api/admin/admins*` (no such directory exists; `admins.md`'s screen is purely a filtered view of the same clients endpoint). Once `role = ADMIN`, it stays `ADMIN` until changed directly in the database.
- **No audit trail for grant-admin.** `lib/audit/order-audit.ts` and the `OtpAuditLog`/`OrderAuditLog` models cover order lifecycle and OTP events only (confirmed by grep across the whole `prisma/schema.prisma` and `lib/audit/`) — granting admin access, arguably the single highest-privilege action in the entire app, is logged nowhere. This directly matches the gap already identified in `docs/redesign/07-analytics-and-audit-plan.md` (which proposes a general `AdminActionLog` covering exactly this kind of action) — that plan is prospective/future work, not implemented, but this screen is the clearest concrete example of why it's needed.
- This screen shares literally all of its list-rendering code shape with `clients.md`'s list (same component pattern, same API endpoint, differing only by the `role` query param and the missing "new" CTA) — a rebuild could reasonably implement both as one parameterized component, which is how the current code is already structured (independently, not shared literally, but structurally identical).
