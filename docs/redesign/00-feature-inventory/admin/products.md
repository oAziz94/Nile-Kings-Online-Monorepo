# Admin — Products (list, detail/edit, create)

Route(s): `app/(admin)/admin/products/page.tsx` (list), `app/(admin)/admin/products/[id]/page.tsx` (edit + variant management), `app/(admin)/admin/products/new/page.tsx` (create)
Key files: `components/admin/image-upload.tsx`, `components/shared/product-image-preview.tsx`, `components/dashboard/{pagination,empty-state,page-header,panel-card,search-input,table-scroll}.tsx`, `hooks/use-list-url-state.ts`, `hooks/use-row-scroll-restore.ts`, `lib/admin/slug.ts`, `lib/admin/variant-sort.ts`, `lib/size-display.ts`, `lib/api/response.ts`, `app/api/admin/products/route.ts`, `app/api/admin/products/[id]/route.ts`, `app/api/admin/products/[id]/variants/route.ts`, `app/api/admin/variants/[id]/route.ts`, `app/api/admin/products/export-excel/route.ts`, `app/api/admin/upload/route.ts`, `lib/catalog-export.ts`. All three pages/screens are covered in this one file (list + detail-edit + create) since none is complex enough on its own to warrant splitting, and they share the same `Product`/`Variant` data model and API surface.

## Business requirements
- **Goal/KPI**: this is the catalog system-of-record editor — its job is operational efficiency for the admin maintaining SKUs, pricing, and imagery, and indirectly conversion/AOV on the storefront (accurate stock, pricing, and product photography downstream of what's entered here). The Excel export exists to hand the catalog to non-technical stakeholders (e.g. courier/partner coordination, marketing) without giving them admin access.
- **Trust/credibility signals**: prices are entered and displayed in EGP (ج.م) with piastres as the storage unit (`price/100`), consistent with the storefront's EGP-only framing. `active` toggle controls storefront visibility so admins can stage a product before launch without deleting it.
- **Friction points**:
  - No inline stock/quantity fields anywhere in this screen — stock (`stockAvailable`/`stockReserved`) is intentionally NOT editable here (see Notes); an admin who expects to set stock on the product page will hit a wall and needs to know to go to `/admin/partner-inventory` instead. The variants card explicitly links there ("إدارة المخزون").
  - Variant "delete" and product "delete" (delete has no UI trigger at all, see Notes) are blocked server-side when `stockReserved > 0`, but the block reason surfaces only via a disabled trash icon (no tooltip other than a bare `title="حذف"`) or a toast on failed API call — an admin could be confused why delete silently fails to do anything if they don't notice the button is disabled.
  - Manual slug editing on both create and edit is a raw text input with no live availability check — the admin only learns of a slug conflict after submitting (409 toast).
  - Excel export button has no visible size/row-count constraint messaging even though it always exports the entire catalog (no filter applied), which could be slow at scale with no progress indicator beyond the button's `disabled` spinner-less state.
- **Compliance/legal**: none specific; no PII in this screen.
- **Modern-look rationale**: table + skeleton loading + debounced search + `PanelCard` is the standard list-page pattern across the admin area (shared with other admin list screens); no unique layout justification here beyond consistency.

## Elements & behavior

### List (`/admin/products`)
- [ ] Wrapped in `<React.Suspense fallback={null}>` because `useListUrlState` reads `useSearchParams()` (a client hook requiring Suspense boundary in the App Router).
- [ ] `PageHeader` — title "المنتجات", description "إدارة الكتالوج، المتغيرات، الأسعار، والتصدير إلى Excel.", actions: "تصدير Excel" (outline button, `FileDown` icon, disabled while `exporting`) and "إضافة منتج" (primary button linking to `/admin/products/new`, `Plus` icon).
- [ ] Search box (`SearchInput`, placeholder "بحث بالاسم أو slug…") — debounced 400ms (`useListUrlState`), matches product `name` OR `slug` case-insensitively (`contains`, `mode: insensitive`) server-side. Search text, page, and page size are persisted to the URL query string (`q`, `page`, `pageSize`) so browser-back from a detail page restores exact list state; changing the query resets to page 0.
- [ ] Table columns: الصورة (thumbnail via `ProductImagePreview`, or a placeholder `Package` icon box if no image), الاسم, الفئة (`category.name`), الوزن (غ) (or "—" if null), الأولوية (`sortOrder` raw number), السعر (shows `discountPricePiastres` if set, else `basePricePiastres`, else "—"; formatted `(piastres/100).toFixed(0)` + " ج.م" — no decimals shown even though stored with cent precision), المتغيرات (`variants.length` + " متغير"), الحالة (`Badge`: "نشط"/success if `active`, "معطّل"/secondary if not), إجراءات (single "تعديل" ghost button linking to `/admin/products/{id}`, which also calls `rememberRow(p.id)` for scroll restore on back-navigation).
- [ ] Default sort: `sortOrder desc, createdAt desc` — **not** best-sales/recent-sales ranked (that ranking, `getProductIdsRankedByRecentSales` in `lib/products/ranked-listing.ts`, is used only by the public storefront product listing API and the standalone inventory dashboard tool's "Priority Analytics" tab — it is not wired into this admin list at all). No column-header sort-by-click; "الأولوية" is a raw display of `sortOrder`, not a clickable sort control.
- [ ] No status/category/active filter controls on this list — only free-text search and pagination.
- [ ] Pagination via `PaginationBar` — page-size selector (10/20/50, default 20), prev/next buttons, "عرض X–Y من Z" count text; hidden entirely when `total === 0`.
- [ ] "تصدير Excel" — `GET /api/admin/products/export-excel`; requires admin; exports the **entire** catalog (ignores current search/filter/page) as `.xlsx` via `lib/catalog-export.ts` `buildCatalogXlsx`, including per-variant SKU/name/color/price/stock/image and a link built from `NEXT_PUBLIC_APP_URL` (falls back to `https://nilekingscotton.com`) and `NEXT_PUBLIC_BRAND_NAME` (falls back to "Nile Kings"); filename taken from `Content-Disposition` header or falls back to `"catalog_products.xlsx"`; downloaded via a synthetic `<a download>` click + `URL.createObjectURL`.
- [ ] Row click target is only the "تعديل" button/link — rows themselves are not clickable.

### Create (`/admin/products/new`)
- [ ] Fields: الاسم (`name`, required, trimmed), الرابط/slug (optional text input — if blank, server derives from name via `slugify()`; final slug always lowercased and stripped to `[a-z0-9-]`, falling back to `"product"` if that yields empty), الفئة (`categoryId`, required `<select>` populated from `GET /api/admin/categories`), الوصف (`description`, optional `<textarea>`), صورة المنتج (`ImageUpload` component — see shared behavior below) plus a manual "أو رابط الصورة يدوياً" text fallback bound to the same `imageUrl` state, الوزن (غرام) (`weightGrams`, optional integer, used for shipping calc), أولوية العرض (`sortOrder`, integer, default `"0"`, helper text "الرقم الأعلى يظهر أولاً في المتجر" — i.e. higher number = shown first), الوسوم (`tagsInput`, free text split on `\s*-\s*` into a tags array — hyphen-delimited, values may contain spaces), السعر الأساسي / سعر التخفيض (ج.م) (both optional numeric EGP inputs converted to piastres via `Math.round(parseFloat(v) * 100)`), المنتج نشط (checkbox, default checked — maps to `active`).
- [ ] Client-side validation: only checks `name.trim()` and `categoryId` are non-empty before submit (toast "الاسم والفئة مطلوبان" if missing); no client-side numeric validation beyond `type=number`/`min=0` HTML attributes.
- [ ] Submit → `POST /api/admin/products`; server validates `name` and `categoryId` required, checks slug uniqueness (409 "الرابط (slug) مستخدم مسبقاً" if taken), checks category exists (400 "الفئة غير موجودة" if not); on success redirects to `/admin/products/{new id}` (the edit page) and shows toast "تم إنشاء المنتج". No variants are created at this step — variant creation happens only on the edit page after the product exists.
- [ ] "إلغاء" button links back to `/admin/products` (list) without confirmation.
- [ ] Categories fetch failure is not surfaced (no `.catch` — a rejected fetch would leave `categories` empty and `loading` stuck via `.finally`, so the `<select>` would render with just the placeholder "اختر الفئة" option forever if the categories call truly throws instead of resolving).

### Detail/Edit (`/admin/products/[id]`)
- [ ] Two independent server round-trips on load in parallel: `GET /api/admin/products/{id}` and `GET /api/admin/categories`; both wrapped in one `.catch` → toast "فشل التحميل" (destructive) on either failing; page renders a full-page skeleton until both resolve or the request errors (loading state has no distinct error UI — see States).
- [ ] Product edit form — same field set as create (name, slug, category select, `ImageUpload` + manual URL fallback, weight, sortOrder with same "higher = shown first" helper text, tags, base/discount EGP prices, active checkbox) but pre-filled; PATCH-based partial update (`PATCH /api/admin/products/{id}`) sends the full current form state each save. Slug re-validated for uniqueness against other products on save (409 on conflict); category re-validated to exist (400 if not). Save button label toggles "حفظ المنتج" / "جاري الحفظ…".
- [ ] **No delete-product control anywhere in the UI** — `DELETE /api/admin/products/{id}` exists server-side (blocks deletion with 400 "لا يمكن حذف منتج له كميات محجوزة" if any variant has `stockReserved > 0`) but nothing in `products/[id]/page.tsx` calls it. Product deletion is effectively API-only/undiscoverable from the current UI (see Notes).
- [ ] Variants card ("المتغيرات (المقاس + اللون)") — description text explicitly tells the admin "أسعار المنتج تُنسخ تلقائياً؛ يمكنك تعديل أسعار كل متغير. المخزون يُدار من صفحة مخزون الشركاء لكل شريك على حدة" (prices are copied automatically from the product; you can edit each variant's price; stock is managed per-partner from the partner-inventory page — i.e. this page has zero stock fields by design).
  - "إدارة المخزون" outline button → `/admin/partner-inventory?q={product.slug}` (deep-links into the partner-inventory screen pre-filtered by this product's slug).
  - "إضافة متغير" opens an Add-Variant dialog.
  - Variant table columns: المقاس (via `getDisplaySizeLabel` — remapped to numeric kids sizing labels, e.g. "S"→"2", only when `category.slug === "kids"`; otherwise shown as-is), اللون (swatch dot colored via `colorHex`, falling back to a hardcoded Arabic/English color-name→hex map, else grey `#9e9e9e`, plus `colorName` text or "—"), السعر الأساسي (ج.م) (or "—"), سعر التخفيض (ج.م), إجراءات (Edit pencil button opening an Edit-Variant dialog; Delete trash button — **disabled** when `stockReserved > 0**, destructive-colored icon).
  - Variant sort order (`sortVariants`, shared with the list's per-row variant... actually applied product-detail-side): primarily by color-hex sort key (falls back to the same name→hex map when `colorHex` is unset), then by a fixed size order `S, M, L, XL, XXL, XXXL, 4XL` (unrecognized sizes sort last), then alphanumeric name as final tiebreaker. `"3XL"`→normalized to `"XXXL"`, `"4X"`→normalized to `"4XL"` for sort purposes only (display unaffected here).
  - Add-Variant dialog fields: المقاس (`<select>` S/M/L/XL/XXL plus "آخر (أدخل يدوياً)" custom free-text option), اسم اللون (required text), كود اللون (optional hex text, free text — no format validation/color-picker in the UI despite being a hex value), صورة اللون (optional, `ImageUpload` + manual URL fallback — shown as "تظهر على صفحة المنتج عند اختيار هذا اللون"), السعر الأساسي (ج.م) (optional, placeholder shows product's default if set), سعر التخفيض (ج.م) (**required**, must be ≥ 0). Client validation: size required (toast if neither dropdown nor custom text set), color name required (toast), discount price required and non-negative (toast "سعر التخفيض مطلوب ويجب أن يكون غير سالب"). Submits `POST /api/admin/products/{id}/variants`.
    - Server-side SKU generation: `{productSlug}-{size}-{colorPart}` uppercased, non-alnum→`_`; `colorPart` derived from `colorName` (preferred) or `colorHex`, or literal `"NOC"` (no color) if neither given; if the cleaned color string is under 2 chars it's hashed into an 8-char base36 token prefixed `C` instead (so very short color names/hexes don't collide or produce unreadable SKUs). Slug format: `{productSlug}_{size}_{colorHexCode}` (hex normalized to 6-digit lowercase without `#`, 3-digit hex expanded, or `"noc"` if absent/invalid). Duplicate SKU → 409 "متغير بنفس المقاس واللون موجود مسبقاً"; duplicate slug → 409 "متغير بنفس الرابط (slug) موجود مسبقاً". New variants always start `stockAvailable: 0, stockReserved: 0` (stock must be added afterward via partner-inventory).
    - There's also an **API-only, no-UI-trigger** bulk path: `POST` with `{ generateSizes: true }` creates one variant per any of `S/M/L/XL/XXL` not already present on the product (colorless, `NOC` SKU suffix), returns 409 "جميع المقاسات موجودة مسبقاً" if all five already exist. Nothing in `products/[id]/page.tsx` calls this — dead/unused from the UI (see Notes).
  - Edit-Variant dialog: same field set minus size-dropdown convenience (plain text المقاس input) and color image via `ImageUpload`; SKU shown read-only as caption text; on save (`PATCH /api/admin/variants/{id}`) recomputes SKU/slug only if name/colorName/colorHex changed, re-checking uniqueness the same way as create (409 on conflict). Discount price required/non-negative validated client-side; base price, if provided, must be non-negative.
  - Delete-Variant confirmation dialog: simple "هل أنت متأكد؟ لا يمكن التراجع." (are you sure, cannot be undone) with Cancel/Delete buttons; server blocks with 400 "لا يمكن حذف متغير له كمية محجوزة" if `stockReserved > 0` (though the trigger button is already disabled in that case, so this server check is effectively a second line of defense, e.g. against a stale/racing UI state).
- [ ] `ImageUpload` shared component (used on create, edit, add-variant, edit-variant): file `<input type=file accept=image/*>` → client validates MIME starts with `image/` (toast if not) → reads to base64 → `POST /api/admin/upload` as JSON `{ image: dataURL, contentType }` → server requires admin, requires `CLOUDINARY_CLOUD_NAME`/`API_KEY`/`API_SECRET` env vars (returns 501 "Cloudinary غير مضبوط" if unset, surfaced in the UI with a specific toast pointing at the missing env vars) → server signs and uploads directly to Cloudinary (`folder=nile-kings/products`, SHA-1 signature) → returns `{ url, publicId }`. No client-side image resize/compression, no file-size limit enforced client-side (Cloudinary/Next.js body-size limits would be the only backstop). Uploaded image can be "removed" (clears to `""`) via a button overlaid on the thumbnail. A manual URL text field is always offered as a fallback/alternative next to every `ImageUpload` instance, letting admins paste an already-hosted image URL instead of uploading.

## States
- [ ] Empty state (list) — `EmptyState` component, `Package` icon, title "لا توجد نتائج للبحث" when a search query is active, else "لا توجد منتجات بعد"; description "ابدأ بإضافة أول منتج إلى الكتالوج." in both cases (slightly misleading copy when the empty state is due to a search with zero matches, not truly zero products).
- [ ] Loading state (list) — full-page two-skeleton block (title bar + one large card skeleton) shown only on the very first load (`loading && products.length === 0`); subsequent debounced-search/page-change fetches instead show an inline "جاري التحديث…" spinner row above a dimmed (`opacity-70`) table, keeping old rows visible during refetch (no flash-to-skeleton on every keystroke).
- [ ] Loading state (detail/edit, create) — full-page skeleton (title + one large card) until product+categories (or just categories, on create) resolve.
- [ ] Error state (list) — fetch failure/non-success response shows destructive toast "فشل تحميل المنتجات"; table falls back to whatever `products` last held (empty on first load, so effectively shows the empty state, not a distinct error UI/banner). Uses an `AbortController` per fetch to cancel stale in-flight requests when filters/page change.
- [ ] Error state (create/edit forms) — every mutation (`saveProduct`, `addVariant`, `saveEditVariant`, `deleteVariant`) shows a destructive toast with the server's `error.message` when available, else a generic Arabic fallback ("فشل الحفظ" / "فشل الإضافة" / "فشل الحذف" / "خطأ في الاتصال"); forms are not reset/cleared on error, letting the admin retry without re-entering data.
- [ ] Permission-restricted state — enforced entirely at `app/(admin)/layout.tsx` (see dashboard.md for the shared mechanism); none of these three pages re-check role themselves beyond the API routes' own `requireAdmin()` calls, which return 401/403 (mapped to Arabic messages) if session/role checks fail mid-session (e.g., role downgraded between page load and a mutating request).

## Edge cases
- [ ] Deleting a variant/product with `stockReserved > 0` — blocked server-side (400) regardless of UI state; UI additionally pre-disables the variant delete button in this case, but the product-level delete has no UI path at all to hit this in the first place (see Notes).
- [ ] Submitting a slug that collides with another product/variant — 409 Conflict, Arabic message surfaced verbatim in a toast; form data is preserved so the admin can just edit the slug field and resubmit.
- [ ] Pagination page number becomes stale after data shrinks (e.g., last item on last page deleted elsewhere, or a search narrows results) — a `useEffect` clamps `page` back into range once `total`/`pageSize` are known, but explicitly skips clamping while `loading` is true to avoid clamping against a stale `total = 0` before the first response lands.
- [ ] Cloudinary not configured in the environment — every image upload attempt across all four `ImageUpload` usages fails with a clear, actionable toast (not a silent failure), and the manual-URL fallback field remains fully usable as a workaround.
- [ ] Non-numeric or negative price/weight input — HTML `type=number`/`min=0` provides only soft client guidance (still bypassable via paste or browser quirks); actual guards are `Math.round(parseFloat(...) * 100)` (which can yield `NaN` if the string is unparsable) and server-side `typeof x === "number" && x >= 0` checks that silently ignore (fall through to `undefined`, i.e. no-op on PATCH, or `null` on POST) any invalid numeric value rather than returning a validation error — a `NaN` weight/price would likely persist as `null` rather than erroring loudly.
- [ ] Very long product/variant lists on Excel export — no pagination or row cap on `export-excel`; whole catalog exported every time regardless of list search/filter state.
- [ ] Race between two admins editing the same product concurrently — no optimistic-concurrency/version check; last PATCH to land wins silently, no conflict warning to either admin.

## Notes
- **Product-level delete has no discoverable UI path.** The `DELETE /api/admin/products/[id]` route exists and is fully implemented (including the reserved-stock guard), but `app/(admin)/admin/products/page.tsx` and `app/(admin)/admin/products/[id]/page.tsx` never call it — there is no delete button for a product anywhere in the current UI. This is either an intentional "products are archived via `active: false`, never hard-deleted" policy, or a genuine gap. `[NEEDS PM INPUT: confirm whether product hard-delete should be added to the redesign, or whether "معطّل" (inactive) is the intended-only removal mechanism]`.
- **`generateSizes` bulk-variant-creation API is unused by the UI.** `POST /api/admin/products/[id]/variants` supports `{ generateSizes: true }` to stamp out S/M/L/XL/XXL variants in one call, but no button in the admin UI triggers it — admins currently add variants one at a time via the Add-Variant dialog. Worth flagging to the PM as either a UI feature to surface (it would clearly save time) or intentionally-retired legacy code.
- Stock is **never** editable from the Products screens — by design, per the explicit in-UI copy on the variants card. All stock lives per-partner in `PartnerInventory` and is managed exclusively on `/admin/partner-inventory` (see `partner-inventory.md`). A rebuild must not add a stock field here without a product decision, since it would contradict the existing partner-inventory-owns-stock model.
- "Best-selling"/ranked-by-recent-sales product ordering (`lib/products/ranked-listing.ts`) is real and used elsewhere (public storefront product API, standalone inventory dashboard's Priority Analytics tab) but is **not** used by this admin product list, which sorts by `sortOrder desc, createdAt desc` only. Don't conflate the two when rebuilding — the admin list's "الأولوية" column is a manually-set integer, not a computed sales rank.
- No admin/superadmin distinction anywhere in this surface — see `dashboard.md` Notes; all product/variant CRUD is available to any `User.role === "ADMIN"`.
- Prices are stored as integer piastres (1/100 EGP) throughout; the admin UI always converts to/from EGP for display and input (`/100` and `*100` respectively, with `Math.round` on the way in).
- The kids-size display remap (`getDisplaySizeLabel`) only affects the *label shown* in the variant table on the edit page (and presumably the storefront) — it does not change the underlying `Variant.name` value ("S"/"M"/etc. is still what's stored and used for SKU/slug generation and sorting).
