# Admin — Settings

Route(s): `app/(admin)/admin/settings/page.tsx` (single page, client component; no sub-routes).
Key files: `app/api/admin/settings/cod-fee/route.ts` (GET/PATCH), `app/api/admin/settings/otp-rules/route.ts` (GET/PATCH), `app/api/admin/settings/senior-promo/route.ts` (GET/PATCH — **backend exists, not surfaced on this page**, see Notes), `lib/settings.ts` (`SITE_SETTING_KEYS`, all getter/setter functions, `unstable_cache`/`revalidateTag` wiring), `app/(admin)/admin/senior-promo-toggle.tsx` (**orphaned component — see Notes**), `prisma/schema.prisma` (`SiteSetting` — generic key/value table).

## Business requirements
- **Goal/KPI**: operational/financial control over two checkout-affecting global rules — the COD (cash-on-delivery) surcharge percentage, and OTP (one-time-password, phone-verification) security parameters. These directly affect checkout economics (COD fee) and account-security/friction tradeoffs (OTP timing/lockout).
- **Trust/credibility signals**: the COD fee directly affects the price a customer sees at checkout — getting this wrong (too high, or silently changed) is a real trust risk; the UI at least labels the formula clearly ("نسبة مئوية من (مجموع المنتجات + التوصيل − الخصم إن وُجد)"). OTP lockout parameters affect legitimate customers' ability to complete registration/login if set too aggressively (e.g. `maxVerifyAttempts` too low, `lockMinutes` too high) — a support-load / conversion-friction risk if misconfigured, not just a security knob.
- **Friction points**: (1) both save actions are independent forms with no combined "save all" — an admin editing both COD and OTP settings must submit twice. (2) No confirmation dialog on either save despite both affecting live checkout economics/security — a typo (e.g. COD fee 20 instead of 2) goes live immediately with just a toast, no "are you sure" gate. (3) No history/audit of previous values — if a setting is misconfigured, there's no in-app way to see what it used to be. (4) The senior-citizen promo toggle (`senior_promo_enabled`) has a fully working API and even a pre-built UI component, but **is not rendered anywhere in the running app** — meaning today, toggling that promo on/off can only be done by hitting the API directly (e.g. via a script or manual request), not through any admin screen. This is very likely an unintentional gap (dead code left behind), not a deliberate design choice — flag prominently to the PM.
- **Compliance/legal**: OTP `expiryMinutes`/`cooldownSeconds`/`maxVerifyAttempts`/`lockMinutes` all have hardcoded sane bounds enforced both client- and server-side (see Elements & behavior) — presumably to prevent an admin from accidentally disabling OTP protections entirely (e.g. cooldown of 0 is allowed, but `maxVerifyAttempts` can't go below 1).
- **Modern-look rationale**: none — this is a small, purely functional settings form screen.

## Elements & behavior
- [ ] `PageHeader` — title "الإعدادات", description "رسوم COD وقواعد OTP.", badge "إعدادات النظام" (Settings icon, decorative, non-interactive). Note the description itself only mentions the two setting groups actually present — it does not mention a senior-promo setting, consistent with that toggle not being on this page.
- [ ] **"رسوم الدفع عند الاستلام (COD)" card** — single field, "النسبة (٪)" number input (min 0, max 100, step 0.1, placeholder "0"), description states the formula precisely: "نسبة مئوية من (مجموع المنتجات + التوصيل − الخصم إن وُجد). مثال: 2 = 2٪ من هذا المجموع." Own "حفظ" submit button, independent form.
  - Loads current value from `GET /api/admin/settings/cod-fee` on mount (`codFeePercent` field; note the API also tracks a separate `codFeePiastres` flat-fee field in the underlying settings store, but **this form only reads/writes the percent field** — always sends `codFeePiastres: 0` on save, meaning **the flat-piastres COD fee path can never be set to a nonzero value through this UI**, only through direct API/DB access).
  - Submit → `PATCH /api/admin/settings/cod-fee` `{ codFeePiastres: 0, codFeePercent }`. Client-side validates 0–100 range before submit (toast "النسبة يجب أن تكون بين 0 و 100" if out of range); server re-validates the same bound.
- [ ] **"قواعد OTP" card** — four number-input fields, each with a specific server-enforced min/max clamp (both client-side `min`/`max` attrs and re-clamped again via `Math.min(...,Math.max(...))` right before submit, so an out-of-range typed value is silently clamped rather than rejected with an error):
  - "مدة صلاحية الكود (دقيقة)" (`expiryMinutes`) — 1 to 60.
  - "المهلة بين طلبات الإرسال (ثانية)" (`cooldownSeconds`, resend cooldown) — 0 to 300.
  - "الحد الأقصى لمحاولات التحقق قبل القفل" (`maxVerifyAttempts`) — 1 to 10.
  - "مدة القفل (دقيقة)" (`lockMinutes`) — 1 to 60.
  - Loads current values from `GET /api/admin/settings/otp-rules` on mount. Submit → `PATCH /api/admin/settings/otp-rules` with all four values (always sends all four, not a partial diff, even though the API supports partial updates). Client-side blocks submission if any field is non-finite or negative (toast "قيم صحيحة مطلوبة") before the clamp step even runs.
  - Own independent "حفظ إعدادات OTP" submit button, separate form from the COD card.
- [ ] Both forms load in parallel on mount (`Promise.all` of the two GET requests) and share one page-level `loading` flag — the whole page shows one skeleton until *both* have resolved, even though the two forms are otherwise fully independent afterward.

## States
- [ ] Empty state — not applicable (both are single-value/fixed-field forms, not lists; there's always a value, defaulted server-side if the `SiteSetting` row doesn't exist yet — see Notes).
- [ ] Loading state — single full-width `Skeleton` (`h-96`) replaces the entire page content until both initial GETs resolve; no per-card/per-field skeleton, no partial render if one loads faster than the other.
- [ ] Error state — toast-only for both save actions (destructive toast with the API's Arabic message, or generic "خطأ في الاتصال" on network failure); **the initial load GETs have no error toast at all** — if either `GET` fails, its `.then()` chain simply never sets state (values stay at their initial empty/`null` state), and the page silently proceeds to show empty/default-looking fields with no indication that the load failed versus the setting genuinely being unset.
- [ ] Permission-restricted state — enforced at `app/(admin)/layout.tsx` only; nothing settings-specific.

## Edge cases
- [ ] COD percent entered as a non-numeric or empty string — client coerces via `parseFloat(...) || 0` on change, so an invalid keystroke silently becomes `0` in state rather than showing a validation error inline.
- [ ] OTP field submitted empty — `parseInt("", 10)` yields `NaN`, caught by the `!Number.isFinite(n)` guard → blocked with "قيم صحيحة مطلوبة" toast before any clamping/submit happens.
- [ ] `SiteSetting` row doesn't exist yet for a given key (fresh deployment, migration just run) — `lib/settings.ts`'s getters all fall back to sensible defaults (COD fee 0/0; OTP defaults `{expiryMinutes:10, cooldownSeconds:60, maxVerifyAttempts:5, lockMinutes:15}`) rather than erroring, and `getSiteSetting()` additionally catches Prisma's "table does not exist" error code (`P2021`) and returns `null` instead of throwing — so this screen is resilient to a not-yet-migrated `SiteSetting` table, which is a deliberate defensive design choice worth preserving.
- [ ] Rapid double-submit on either form — both save handlers guard via their own `saving`/`savingCod`/`savingOtp` boolean disabling the submit button mid-request, preventing duplicate submissions.
- [ ] COD fee change takes effect immediately for in-progress checkouts — `setCodFeePercent()`/`setSeniorPromoEnabled()` both call `revalidateTag("checkout-settings")`, so the 60-second `unstable_cache` on the checkout-facing reads is force-invalidated right when an admin saves, not just left to expire naturally. (`otp-rules` has no such cache/revalidate wiring — it's read fresh on every call, no caching layer at all for OTP settings.)

## Notes
- **The senior-citizen promo toggle is dead/orphaned code as far as the admin UI is concerned.** `app/(admin)/admin/senior-promo-toggle.tsx` exports a fully working `SeniorPromoToggle` component (reads/writes `GET`/`PATCH /api/admin/settings/senior-promo`, has its own loading/updating states, a proper switch UI) — but a repo-wide search found **zero imports of it anywhere** (not on this settings page, not on the admin dashboard, not anywhere else). The backing `lib/settings.ts` functions (`isSeniorPromoEnabled`/`setSeniorPromoEnabled`) and API route are live and presumably still read by the storefront/checkout logic (the promo itself may still be effectively "on" or "off" at whatever value was last set, possibly only ever set via seed data or a one-off script) — but there is currently **no admin-facing way to toggle it**. This is almost certainly an unintentional gap left over from development, not a deliberate removal — strongly recommend flagging to the PM as a likely "restore to settings page" item (place the existing `SeniorPromoToggle` component into this screen) rather than treating its absence as intentional current-state to preserve as-is. Whether to treat this as a parity bug-fix (put it back) or an explicit product decision is the PM's call — noting it here per instructions rather than silently fixing or silently ignoring it.
- **`SiteSetting` is a fully generic key-value table** (`key` unique, `value` string) — `SITE_SETTING_KEYS` currently defines 7 keys total (`senior_promo_enabled`, `cod_fee_piastres`, `cod_fee_percent`, and the four `otp_*` keys). This settings screen exposes 6 of those 7 through its UI (all except `senior_promo_enabled`), plus a `codFeePiastres` field that's technically writable via the API but effectively unreachable through this UI (always sent as `0`).
- **No audit trail for settings changes** — same gap pattern as `admins.md`'s grant-admin finding: `lib/settings.ts`'s setters just upsert the `SiteSetting` row directly, with no logging of who changed what/when. Matches the general admin-action-audit gap already called out in `docs/redesign/07-analytics-and-audit-plan.md` (prospective `AdminActionLog`, not yet implemented) — settings changes would be a natural first candidate for that log given how consequential (and currently silent/unconfirmed) they are.
- This screen has no relationship to the (non-existent) shipping-rate configuration described in `shipping.md` — shipping rates are hardcoded constants, not `SiteSetting` rows, and are not editable from here or anywhere else in the current UI.
