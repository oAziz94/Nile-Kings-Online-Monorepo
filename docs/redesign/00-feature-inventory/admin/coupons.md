# Admin — Coupons

Route(s): `app/(admin)/admin/coupons/page.tsx` (single page — list + create/edit dialog + delete-confirm dialog, all client component; no separate `[id]`/`new` routes exist for this screen).
Key files: `app/api/admin/coupons/route.ts` (GET list w/ search+pagination, POST create), `app/api/admin/coupons/[id]/route.ts` (GET one, PATCH, DELETE), `app/api/promotions/coupon-popup-messages/route.ts` (public-facing consumer of `showPromotionPopup`/`promotionPopupMessage`, out of scope but explains the field's purpose), `prisma/schema.prisma` (`Coupon`, `CouponUsage`).

## Business requirements
- **Goal/KPI**: conversion and AOV — coupons are the site's discount/promo mechanism (percentage off, fixed EGP off, or a buy-X-get-Y-free quantity deal), and the "promotional popup" toggle turns a coupon into an active on-site marketing message shown to visitors. `minOrderPiastres` protects margin on small orders; `maxUses`/`usedCount` caps promo cost exposure.
- **Trust/credibility signals**: coupon codes and discount amounts must be unambiguous — the list shows exact discount framing per type (e.g. "20%", "50.00 ج.م", "اشترِ 2 واحصل على 1 مجاناً (نفس المتغير)") so an admin can sanity-check a live promo without opening it. The promotional popup message is free-text (up to 8000 chars) — no content moderation beyond a required-when-enabled check, so accuracy is entirely on the admin.
- **Friction points**: (1) **validity window (`validFrom`/`validUntil`) is not exposed in this UI at all** — see Notes; every coupon effectively starts "now" and never expires unless someone edits it directly via API/DB, meaning short-lived flash-sale coupons cannot be time-boxed from this screen today. (2) No usage-analytics link from a coupon row to *which* orders used it (`usedCount` is a bare number, not a drill-down). (3) Search is code-only (`q` matches `code` `contains`, case-insensitive) — cannot search/filter by discount type, active status, or popup-enabled state.
- **Compliance/legal**: Egyptian ecommerce norms around clear, non-misleading pricing apply to the promotional popup message since it's customer-facing; nothing else coupon-specific flagged in code (no found VAT/tax interaction beyond checkout-side application, out of this screen's scope).
- **Modern-look rationale**: none beyond a standard filterable/paginated admin table + modal-form pattern.

## Elements & behavior
- [ ] `PageHeader` — title "الكوبونات", description "إنشاء وتعديل أكواد الخصم والعروض الترويجية.", action button "إضافة كوبون" opens the create dialog.
- [ ] List table columns: الكود (`code`, monospace), الخصم (`formatCouponDiscount()` — type-specific formatting, see below), نافذة الموقع (badge "نعم"/"لا" for `showPromotionPopup`), الحد الأدنى للطلب (`minOrderPiastres/100` + "ج.م", or "—"), المستخدم / الأقصى (`usedCount` + `/ maxUses` if capped, else just the used count), الحالة (badge "نشط"/success or "معطّل"/secondary), إجراءات (pencil-icon edit button, trash-icon delete button — icon-only, `title` tooltip attrs).
- [ ] Search — `SearchInput`, 400ms debounce, resets to page 0 on change, matches coupon `code` only (case-insensitive `contains`).
- [ ] Pagination — `PaginationBar`, page size selectable, default 20/page; server-paginated via `limit`/`offset` query params.
- [ ] **Discount type** (`discountType`, radio-equivalent `Select`, 3 options):
  - `PERCENT` — single "النسبة (1–100)" number input, integer, validated 1–100 both client-side and API-side.
  - `FIXED` — single "القيمة (ج.م)" number input (decimal, step 0.01), stored as piastres (`Math.round(value * 100)`); validated non-negative.
  - `BOGO_QTY` ("عرض كمية") — two integer inputs: "عدد القطع المدفوعة في الدورة" (`bogoPayQuantity`) and "عدد القطع المجانية في الدورة" (`bogoFreeQuantity`), each 1–999; plus a checkbox "يطبق على نفس المنتج والمتغير فقط" (`bogoSameVariantOnly`, default checked) with explanatory helper text for both the checked state (groups per-variant) and unchecked state (pools all cart lines, cheapest items in each group discounted). `discountValue` is forced to `0`/unused for this type.
  - Switching `discountType` on an existing coupon (edit) clears the other type's fields server-side: switching to PERCENT/FIXED nulls `bogoPayQuantity`/`bogoFreeQuantity`/resets `bogoSameVariantOnly` to `true`; switching to BOGO_QTY zeroes `discountValue`.
- [ ] **Promotional popup** — checkbox "إظهار الرسالة عند زيارة الموقع" + a required-when-checked `textarea` (max 8000 chars, RTL) for `promotionPopupMessage`. Helper text clarifies dismiss behavior: "تُخفى بعد «إغلاق» حتى إغلاق المتصفح أو التبويب" (hidden after close until the browser tab closes — i.e. session-based dismissal, presumably `sessionStorage` on the storefront side, not this screen).
- [ ] **Minimum order** — "الحد الأدنى للطلب (ج.م)" number input, optional (empty = no minimum), stored as piastres.
- [ ] **Max uses** — "الحد الأقصى لمرات الاستخدام" number input, optional (empty = unlimited/`null`), placeholder "غير محدود". On edit, API rejects lowering `maxUses` below the coupon's current `usedCount`.
- [ ] **Active** — plain checkbox "نشط", defaults checked on create.
- [ ] Create flow — dialog form, submits `POST /api/admin/coupons`; code is uppercased client-side on every keystroke and again before submit; duplicate code → 409 "كود الكوبون مستخدم مسبقاً" (Arabic conflict toast, dialog stays open).
- [ ] Edit flow — same dialog/fields pre-filled from the row (`couponToForm()` — note `FIXED` values are converted back from piastres to EGP for display, `PERCENT` used as-is); submits `PATCH /api/admin/coupons/[id]` with the full form body every time (not a diff).
- [ ] Delete flow — separate confirm dialog naming the coupon's code, explicit warning "سجلات الاستخدام المرتبطة تُحذف معه" (associated `CouponUsage` rows cascade-delete with it — matches `onDelete: Cascade` in schema); "حذف" button is `variant="destructive"`; dialog can't be dismissed mid-delete (`if (deleting) return` guard on close).

## States
- [ ] Empty state — `EmptyState` with Ticket icon; message is "لا توجد نتائج للبحث" when a search query is active and returns nothing, else "لا توجد كوبونات".
- [ ] Loading state — initial load: full-width `Skeleton` (`h-64`) replaces the whole content area while `list.length === 0`. Subsequent refetches (search/page/save/delete) instead show an inline "جاري التحديث…" spinner row above the table while keeping stale rows visible at 70% opacity (`fetching && list.length > 0`).
- [ ] Error state — all failures (list fetch, create, edit, delete) surface only via destructive `toast`; no inline banner, no retry button. A failed create/edit leaves the dialog open with the error toast so the admin can correct and resubmit; a failed delete leaves the confirm dialog open.
- [ ] Permission-restricted state — enforced at `app/(admin)/layout.tsx` only (see `admin/dashboard.md`): non-admins never reach this screen.

## Edge cases
- [ ] `showPromotionPopup` checked with empty message — blocked both client-side (`validateCouponForm`) and server-side (400 "نص الرسالة مطلوب عند تفعيل النافذة المنبثقة للعرض") on both create and edit.
- [ ] `BOGO_QTY` with pay/free quantities outside 1–999, or `<1` — blocked client- and server-side ("أدخل كميات صحيحة (1 على الأقل) للعرض" / "...يجب أن يكون بين 1 و 999").
- [ ] Lowering `maxUses` below current `usedCount` on edit — API rejects with 400; UI has no client-side pre-check for this, so the error only surfaces after submit.
- [ ] Code uniqueness on edit — API excludes the coupon's own `id` from the conflict check (`{ code, id: { not: id } }`), so re-saving a coupon with its own unchanged code does not falsely conflict.
- [ ] Deleting a coupon that has been used (`CouponUsage` rows exist, tied to real `Order`s via `orderId`) — no warning beyond the generic "سجلات الاستخدام المرتبطة تُحذف معه" notice; there is no "usage count > 0, are you sure" extra confirmation step, and historical order records presumably keep their own discount snapshot independent of the now-deleted `Coupon` row (order-level fields like `discountPiastres` are on `Order`, not a live join — verify against the orders screen's inventory file if this matters for a rebuild).
- [ ] `discountValue` for `FIXED` type round-trips through EGP↔piastres conversion (`* 100` on save, `/ 100` on load) — a value with more than 2 decimal places entered in EGP will be rounded (`Math.round`), not rejected.

## Notes
- **`validFrom`/`validUntil` exist on the `Coupon` model and are fully handled by both API routes** (`POST`/`PATCH` accept ISO date strings for both; `POST` defaults `validFrom` to "now" and `validUntil` to `null`/never-expires when omitted) **but there is no form field for either in this admin UI.** Every coupon created through this screen is therefore immediately valid and never expires unless someone hits the API directly. If validity windows are wanted for the rebuild, that's a genuine new UI surface to add (worth a `02-proposals.md` line), not something to silently reconstruct from "what the code already does" — the code supports it, the current UI simply never asks for it.
- Discount amounts are stored as piastres (Int) throughout except `PERCENT`, which stores the raw 1–100 integer in the same `discountValue` field — the UI/API disambiguate purely by `discountType`, so a rebuild must not assume `discountValue` is always a currency amount.
- The promotional popup this toggle powers is rendered somewhere in the public storefront (consumed via `GET /api/promotions/coupon-popup-messages`, likely on `(public)/layout.tsx` or the homepage) — out of scope for this file, but relevant context: this admin screen is the *only* way to author that popup's content, there's no separate "site banners" admin screen.
- `CouponUsage.orderId` is nullable — a usage row can exist before an order is finalized (e.g. reserved-but-not-placed), which is why deleting a coupon cascades usage rows rather than blocking on them.
