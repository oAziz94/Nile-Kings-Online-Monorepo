# Admin — Orders (list, detail/status/edit, manual create)

Route(s): `app/(admin)/admin/orders/page.tsx` (list), `app/(admin)/admin/orders/[id]/page.tsx` (detail: status, notes, linked account, line-item edit), `app/(admin)/admin/orders/new/page.tsx` (manual order creation)
Key files: `lib/constants/order-status.ts`, `lib/admin/order-create.ts`, `lib/admin/address.ts`, `lib/checkout/place-order.ts`, `lib/checkout/summary.ts`, `lib/checkout/cod-fee.ts`, `lib/services/pricing.ts`, `lib/services/shipping.ts`, `lib/services/stock.ts`, `lib/inventory/partner-inventory.ts`, `lib/audit/order-audit.ts`, `lib/rerouting/assign.ts`, `lib/courier-export.ts`, `lib/size-display.ts`, `app/api/admin/orders/route.ts`, `app/api/admin/orders/[id]/route.ts`, `app/api/admin/orders/preview/route.ts`, `app/api/admin/orders/courier-export/route.ts`, `app/api/admin/orders/csv-export/route.ts`. All three screens covered in this one file — the `[id]` detail page is complex (status transitions, item editing with live re-pricing, account re-linking) but shares enough data model and UI conventions with list/create that splitting would fragment the same order-lifecycle story; flagging that call here per the instructions.

## Business requirements
- **Goal/KPI**: this is the core order-ops screen — operational efficiency (fast status triage, bulk courier handoff) directly drives fulfillment speed and reduces support load. The manual-order-creation flow exists so phone/WhatsApp/in-person orders (common in Egypt ecommerce) can be entered without the customer touching the storefront, and — per its own description — explicitly "دون المساس بسلته" (without touching the customer's own cart), i.e. it must not clobber a customer's in-progress storefront cart.
- **Trust/credibility signals**: order totals are broken down transparently (subtotal / discount / shipping / COD fee / total) both in the list and detail views, in EGP; COD fee is shown as its own line item, which matters for COD-heavy Egyptian ecommerce where customers/admins need to see it wasn't silently folded into "shipping." Admin notes are explicitly labeled as internal-only ("لا تظهر للعميل ولا تُرسل لشركة الشحن" — not shown to the customer or sent to the courier), which is an important trust boundary to preserve exactly (a rebuild that accidentally exposed these would be a real incident).
- **Friction points**:
  - The courier-export bulk action silently drops any selected order that isn't `READY_TO_SHIP` with no per-order feedback about which ones were skipped — an admin who selects a mixed-status batch gets a smaller-than-expected export with only a generic "no eligible orders" message if *all* were ineligible, and otherwise no warning at all (see Edge cases).
  - The order-detail page's item editor infers "size" and "color" by parsing dashes and Arabic-character heuristics out of the stored `variantName` string (see Elements & behavior) rather than reading structured variant data — a fragile pattern that could misparse for edge-case naming and is worth flagging to the PM as tech debt, not something to blindly reproduce as "correct" display logic without understanding it might misfire.
  - No confirmation dialog before changing order status (including to CANCELLED) — a misclick on the status dropdown + "تحديث الحالة" immediately cancels/transitions a live order.
- **Compliance/legal**: order audit trail (`OrderAuditLog`) records status changes, confirmations, and cancellations with reasons — relevant for dispute resolution / accounting reconciliation, must survive the rebuild even though it's not directly rendered in this UI.
- **Modern-look rationale**: none beyond consistency with other admin list/detail patterns.

## Elements & behavior

### List (`/admin/orders`)
- [ ] Wrapped in `<React.Suspense>` (uses `useListUrlState`/`useSearchParams`).
- [ ] `PageHeader` — title "الطلبات", description "عرض الطلبات، التصدير، وتحديث الحالة من صفحة التفاصيل." (view orders, export, and update status **from the detail page** — i.e. the list is explicitly not where status changes happen), action: "طلب جديد" → `/admin/orders/new`.
- [ ] Toolbar: `SearchInput` (placeholder "بحث برقم الطلب أو العميل…"), status `<select>` (كل الحالات + one option per `ORDER_STATUS_LABELS` entry), two export buttons (see Bulk actions). Search debounced 400ms, matches order `id` (contains, case-insensitive — so partial/full order ID search), customer `name`, customer `phone`, or any order item's `productName`/`variantName` (all `contains`/insensitive) — i.e. one search box covers order#, customer, and product/variant name simultaneously. Search+status+page+pageSize persisted to URL.
- [ ] Table columns: checkbox (selection), الرقم (`id.slice(0,8)`, monospace), العميل (`phone` + optional `(name)`), الإجمالي (bold total EGP + a stacked mini-breakdown of subtotal/shipping/COD-fee, all in EGP), طريقة الدفع (mapped via `PAYMENT_LABELS`: COD → "الدفع عند الاستلام", INSTAPAY_PREPAID → "الدفع عبر InstaPay", PAYMOB → "بطاقة"; unmapped values shown raw), الحالة (`Badge` colored per `ORDER_STATUS_BADGE_CLASSES`), ملاحظات (`ExpandableAdminNotesCell` — truncates to ~56 chars / 2 lines with a "المزيد"/"أقل" (more/less) toggle when the note is longer or multi-line; shows "—" if empty), التاريخ (`formatDateEn`), إجراءات ("تفاصيل" link → `/admin/orders/{id}`, remembers row for scroll-restore on back-nav).
- [ ] **Bulk actions** (selection is a plain client-side array of order IDs, persists across debounced-search/status/page changes only via an explicit reset effect — selection is cleared whenever `debouncedQ`, `statusFilter`, `page`, or `pageSize` changes, i.e. **not** preserved across pagination or filter changes, only within the same page/filter view):
  - Header checkbox selects/deselects all orders on the *current page only* (not all matching orders across pages).
  - "ملف الشحن (N)" (courier/shipping-file export) — `POST /api/admin/orders/courier-export` with selected IDs; disabled when nothing selected or another export is running. Server re-queries only orders among the selected IDs with `status === READY_TO_SHIP`, stamps `exportedToCourierAt = now()` on each included order (idempotent re-export flag, doesn't block re-export), and returns an `.xlsx` via `buildCourierXlsx` (includes address, payment method, items, per-item weight). 400 "لا توجد طلبات بحالة «جاهز للشحن» ضمن الطلبات المحددة" only if **zero** selected orders qualify — if some qualify and some don't, the ineligible ones are silently excluded from the export with no warning.
  - "CSV (N)" — `POST /api/admin/orders/csv-export`; **no status restriction** (any selected order status is exportable), capped at 200 order IDs per request (400 "الحد الأقصى للتصدير هو 200 طلبًا" beyond that), de-duplicates IDs, outputs UTF-8 BOM-prefixed CSV (Arabic-safe in Excel) with columns: معرف الطلب (full id), الرقم المختصر (8-char id), هاتف العميل, اسم العميل, المجموع الفرعي, الشحن, رسوم الدفع عند الاستلام, الإجمالي, طريقة الدفع, الحالة (Arabic label), التاريخ, ملاحظات الإدارة, المنتجات (pipe-delimited `name (variant) ×qty` summary).
  - Both exports download via synthetic `<a download>` + blob URL, filename from `Content-Disposition` header (fallbacks: `shipments.xlsx`, `orders-export.csv`), and clear the selection on success.
- [ ] Default/only sort: `createdAt desc` — no column-sort UI, no other sort option.
- [ ] No delete action anywhere on this list (orders are never hard-deleted from the UI; only status transitions, including CANCELLED, exist).

### Manual create (`/admin/orders/new`)
- [ ] **Client search & select** (existing customers only — filters to `role === "CUSTOMER"`, so an ADMIN account can never be selected as the order's customer): debounced 350ms search by phone/name against `GET /api/admin/clients`; selecting a client fetches their full record + saved addresses (`GET /api/admin/clients/{id}`), auto-preselecting their default (`isDefault`) address or the first one if any exist.
- [ ] If the selected client has **zero saved addresses**, an inline amber warning appears: "لا يوجد عنوان محفوظ لهذا العميل. أضف عنواناً من ملف العميل أولاً." with a link to `/admin/clients/{id}` — **there is no way to type a one-off address inline on this screen**; the admin must leave this page, add a saved address on the client's profile, then come back. This is a real workflow gap for phone orders from new/addressless customers.
- [ ] **Item picker**: debounced 300ms free-text search against `GET /api/admin/products?active=true` (active products only), flattened to a variant-level `<select>` (label: `{productName} - {size}[ - {colorName}]`, price shown alongside); quantity stepper (min 1); "إضافة" adds to the order — if the variant is already in the list, quantities are summed rather than duplicated. Each line item shows product/variant name, editable quantity, computed line total (EGP), and a remove (trash) button. No stock-availability check/warning is shown at add-time in this UI (stock is only validated server-side at submit).
- [ ] **Payment & notes** card: طريقة الدفع (`<select>` over `PAYMENT_METHODS` — COD / PAYMOB (labeled "بطاقة (تجريبي)" = card, marked test/trial) / INSTAPAY_PREPAID, default COD), كوبون (اختياري) (free-text coupon code, LTR input), ملاحظات إدارية (free text, **pre-filled with "طلب من لوحة الإدارة"** = "order from the admin panel" as a default value the admin can edit or clear).
- [ ] **Live preview**: once client + address + ≥1 item + valid payment method are all set (`canPreview`), a debounced (400ms) `POST /api/admin/orders/preview` call recomputes and displays subtotal, coupon discount, senior-promo free value, shipping fee, COD fee, and final total (all live-recalculated server-side via `buildCheckoutSummaryFromLines` — the exact same pricing/shipping engine used by the real storefront checkout) — re-fires on every item/address/payment/coupon change. Preview card is hidden until `canPreview` is true; shows a spinner while recalculating and hides the numbers underneath while stale.
- [ ] **Submit**: `POST /api/admin/orders` with the same payload shape as the preview call; disabled while `!canPreview`, while a preview is in flight, or while already submitting. On success, redirects to `/admin/orders/{new id}` (the detail page) with a toast (server-provided message or "تم إنشاء الطلب"). On failure, shows the server's Arabic error message via toast (form state is preserved for retry).
- [ ] **Order-creation semantics** (server, `POST /api/admin/orders` → `lib/checkout/place-order.ts` `placeOrder()`): runs through the exact same `placeOrder` engine as customer self-checkout, with `skipCartClear: true` (so it never touches the selected customer's actual storefront cart, honoring the page's stated promise) and `createdByAdmin: true` (tags stock-ledger entries with "Admin order creation" instead of "Customer checkout" for audit purposes). Initial order status follows the same rule as customer checkout: `COD`/`PAYMOB` → immediately `CONFIRMED` (stock committed, not just reserved); `INSTAPAY_PREPAID` → `CREATED` (stock held in `stockReserved` only, pending admin confirmation/cancellation — per the `OrderStatus` enum's own code comment). After creation, the order is passed through `assignOrderToGovernorate()` (the same auto-routing used for customer orders — see `routed-orders.md`) — a routing failure here is caught and logged server-side (`console.error`) but does **not** fail the order-creation request; the order is still created, just possibly unrouted.
- [ ] "إلغاء" cancels back to `/admin/orders` list with no confirmation (no unsaved-changes warning even with items already added).

### Detail (`/admin/orders/[id]`)
- [ ] Header: order id (8-char), current-status badge, "رجوع للطلبات" back button (`router.back()`, not a fixed link).
- [ ] **Status card** — `<select>` over all 7 `ORDER_STATUSES` (no restriction on which transitions are allowed — any status can be selected from any other, including re-opening a CANCELLED order or jumping straight to DELIVERED), "تحديث الحالة" button (disabled if unchanged or already updating). No confirmation prompt for any transition, including CANCELLED. Submits `PATCH /api/admin/orders/{id}` with `{ status }` only (no cancellation-reason input field anywhere in this UI — server defaults `cancellationReason` to the literal `"admin"` whenever status transitions to CANCELLED without an explicit reason in the payload).
- [ ] **Admin notes card** — explicit internal-only disclaimer text (see Business requirements), `<textarea>`, "حفظ الملاحظات" button disabled when unchanged or saving. Saved independently of status (`PATCH` with `{ adminNotes }` only).
- [ ] **Customer card** — read-only name/phone display (this is *not* where you change the linked customer — see "ربط الطلب بحساب عميل" below).
- [ ] **Shipping address card** — read-only formatted address (governorate/city/area/street) plus the customer's own delivery notes on that address (labeled "ملاحظات العميل على العنوان" to distinguish from admin notes).
- [ ] **"ربط الطلب بحساب عميل" (re-link order to a different customer account) card** — independent search-and-select of any customer (same client-search API as create), then a dependent address `<select>` scoped to that (possibly different) customer's saved addresses; auto-preselects the address already on the order if the same customer is kept, else defaults to their `isDefault`/first address. "تحديث الحساب والعنوان" submits `PATCH` with `{ userId, savedAddressId }`. Server re-validates the target user is a `CUSTOMER`, that the saved address belongs to them, **recomputes shipping fee and COD fee from scratch** against the new address (using either the just-edited item weights if items were edited in the same request, or the existing order's item weights otherwise) — this can silently change the order total when only the account/address changes, which the UI does communicate implicitly (the totals footer updates) but doesn't explicitly call out as "this changed your total."
- [ ] **Line items card** — editable table: thumbnail, product+variant name, quantity `<input type=number>` (inline, live in local state only), unit price (read-only), computed total (local, live), المقاس (size) and اللون (color) columns **parsed heuristically from the stored `variantName` string** (not from structured `Variant.name`/`colorName` fields) via regex/Arabic-character detection (`getSize`/`getColor` helpers) — this is fragile display-only logic worth flagging, not reproducing blindly. Remove button per row (client-side only until saved). Add-item row: debounced product/variant search (same pattern as create), quantity, "إضافة" (merges quantity into an existing line rather than duplicating). "حفظ البنود وإعادة الحساب" (save items and recompute) button, disabled while empty or saving.
  - There's also an unused `groupItemsByCategory` effect that re-sorts `editableItems` by a category token parsed out of `variantName` (expects a `"nk-<code>-..."` naming convention) — runs on every `editableItems` change but is effectively inert for variant names that don't start with `"nk"` (the majority, based on the SKU/slug conventions seen in Products), since `getCategory` then returns `""` for everything and the sort is a no-op. Likely dead/legacy code from an earlier variant-naming scheme.
  - Server-side on item save (`PATCH` with `{ items }`): fully replaces the order's `OrderItem` rows (`deleteMany` + `create`), re-validates every variant exists, requires every referenced product to have a non-null `weightGrams` (400 "لا يمكن إعادة حساب الشحن: وزن بعض المنتجات غير متوفر" if any is missing — a real product-data-quality dependency), recomputes pricing via `computePricing` (re-applies the order's existing coupon code and current senior-verification/promo-enabled state — **not** the coupon/promo state at original order time, so pricing can drift if the coupon or promo config changed since), recomputes shipping via `getPhase1ShippingFee` against the *current* shipping address, recomputes COD fee if `paymentMethod === "COD"`, and guards every computed monetary field against negative values or exceeding Postgres `int32` (400 "قيمة الطلب تتجاوز الحد المسموح" if so).
  - **Stock reconciliation on item edit** is state-machine-aware and partner-aware: if the order is still `CREATED` (reservation-only) the reservation is adjusted; if already committed (`CONFIRMED`+) the commitment is reconciled; if the order has an `assignedPartnerId`, the same reconciliation happens against that partner's `PartnerInventory` instead of the shared pool. Insufficient stock at any point returns 400 "كمية غير متوفرة في المخزون لتعديل الطلب بهذه الأصناف" and the whole transaction rolls back (items are NOT partially updated).
  - Editing items on a CANCELLED order is explicitly blocked (400 "لا يمكن تعديل أصناف طلب ملغى") whenever the edit would actually change stock lines (a no-op "edit" that resolves to the same lines is allowed through).
  - Editing items **and** cancelling in the same request is explicitly rejected (400 "لا يمكن تعديل أصناف الطلب مع إلغائه في نفس الطلب") — these must be two separate saves.
- [ ] **CREATED → non-CREATED/non-CANCELLED transition side-effects** ("leaving CREATED"): stock moves from reserved to committed (partner-aware), `reservationExpiresAt` is cleared, an audit log entry is written (`logOrderConfirmed` specifically when moving to CONFIRMED, else a generic `logOrderStatusChange`), and if the order's payment method is `INSTAPAY_PREPAID`, any `PENDING` `PaymentAttempt` rows are marked `CAPTURED` — i.e. **moving an InstaPay-prepaid order out of CREATED is treated as the admin's manual confirmation that payment was received** (there is no separate "mark payment captured" control anywhere in this UI; changing status does double duty as payment confirmation for this payment method).
- [ ] **CANCELLED transition side-effects**: stock is released (if still reservation-only) or restored (if already committed), partner-aware; `OrderAuditLog` "cancelled" entry written with the reason (defaults `"admin"`); happens in the same DB transaction as the status update (15s max-wait / 60s timeout on the transaction).
- [ ] Totals footer recomputes from the live `order` state after any successful save (status/items/account link) — always shows subtotal, conditionally discount (with coupon code if any), shipping (with provider name), conditionally COD fee, and bold final total.

## States
- [ ] Empty state (list) — `EmptyState`, `ShoppingBag` icon, title "لا توجد نتائج للبحث" (search active) or "لا توجد طلبات" (no search) — **no description text** on this one (unlike products/categories empty states).
- [ ] Loading state (list) — full-card skeleton on first load only; subsequent refetches show inline "جاري التحديث…" spinner with dimmed table, old data preserved (same pattern as Products).
- [ ] Loading state (detail, create) — single full-page skeleton block until the primary record loads; secondary data (client list, variant options, address list) loads independently with its own small inline spinners/"جاري تحميل…" text rather than blocking the whole page.
- [ ] Error state (list) — destructive toast "فشل تحميل الطلبات" on fetch failure; `AbortController` cancels stale requests on filter/page change, same as Products.
- [ ] Error state (detail) — destructive toast "فشل تحميل الطلب" if the initial order fetch fails; every mutating action (status update, notes save, account re-link, item save) shows its own destructive toast with the server's message or a generic fallback ("فشل التحديث"/"فشل"/"خطأ في الاتصال") and does not reset the form on failure.
- [ ] Error state (create) — the preview call failing silently clears `summary` to `null` (hides the preview card's numbers, shows nothing else — no toast for a failed *preview*, only for a failed *submit*); submit failures do toast.
- [ ] Permission-restricted state — enforced at `app/(admin)/layout.tsx` + each API route's own `requireAdmin()` (401/403 mapped to Arabic messages); no finer-grained permission tiers found (see Notes).

## Edge cases
- [ ] Courier export with a mixed-status selection — silently exports only the `READY_TO_SHIP` subset with zero indication of which/how-many were dropped; only errors out if literally none qualify. `[NEEDS PM INPUT: should the rebuild surface "N of M orders were not READY_TO_SHIP and were skipped" explicitly? Current behavior is silent.]`
- [ ] CSV export beyond 200 selected orders — hard 400 rejection (whole request fails, not truncated to the first 200) with a message stating the limit.
- [ ] Changing an order's linked customer/address recomputes shipping/COD fee/total from the new address without any explicit "your total changed" callout beyond the totals footer updating post-save.
- [ ] Editing line items on an order where any referenced product now has `weightGrams = null` (e.g. edited elsewhere after the order was placed) — blocks the entire item-save with a specific error rather than silently using a fallback weight.
- [ ] Insufficient stock discovered mid-item-edit — entire transaction rolls back; no partial item update ever lands.
- [ ] Cancelling an order that was already `CANCELLED` — `transitioningToCancelled` guard requires `existing.status !== "CANCELLED"`, so re-selecting CANCELLED on an already-cancelled order is effectively a same-status PATCH; combined with the button being `disabled={status === order.status}`, this path isn't normally reachable from the UI, only via direct API misuse.
- [ ] Manual order creation for a customer with no saved addresses — fully blocked from this screen (no inline address entry); admin must detour to `/admin/clients/{id}` first (see Elements & behavior).
- [ ] Coupon entered on manual-create that turns out invalid/expired/inapplicable — surfaces only through the live preview recalculating without the discount (no dedicated "invalid coupon" message distinct from "discount just isn't applied"); `appliedCouponCode` in the preview response reflects whatever coupon (if any) actually validated and applied.
- [ ] Admin selects PAYMOB on manual-create — label explicitly marks it "(تجريبي)" (trial/test), signaling this payment method isn't a fully live path even though it's selectable and would immediately confirm the order (`immediateConfirm` includes PAYMOB). `[NEEDS PM INPUT: confirm PAYMOB's actual production readiness before the rebuild treats it as a fully supported manual-order payment method.]`
- [ ] Race between two admins editing the same order's items/status concurrently — no optimistic-concurrency guard; last write wins, no conflict surfaced to either admin (consistent with Products/Categories).

## Notes
- **No admin/superadmin distinction** — identical to every other screen in this batch; all order mutations (including cancellation and manual creation) are available to any `User.role === "ADMIN"`.
- Status transitions are **not** a constrained state machine in the UI or API — any of the 7 statuses can be selected from any other at any time via the dropdown, with only a few status-*pair*-specific side effects (leaving CREATED, entering CANCELLED) rather than a general transition-validity check. If the redesign wants to add guardrails (e.g. block SHIPPED→CREATED), that's a product decision, not something implied by current behavior — flag to PM if desired.
- Changing status is the **only** way to mark an InstaPay-prepaid order's payment as captured — there is no separate "confirm payment received" action. A rebuild must preserve this coupling (moving off CREATED = payment confirmed) or explicitly redesign it as a product decision, since decoupling it without a plan could silently stop marking `PaymentAttempt`s as `CAPTURED`.
- The size/color columns on the order-detail item table are derived by string-parsing `variantName` (format assumptions: size is often the last or second-to-last dash-segment; an Arabic-script segment is assumed to be the color) rather than reading the canonical `Variant.colorName`/`Variant.name` fields directly (which the order item snapshot doesn't retain structured — `OrderItem` only stores the flattened `variantName` string). This is inherent to how `OrderItem` snapshots variant info (by design, for historical-accuracy-at-order-time), not a bug to silently "fix" by joining back to the live `Variant` row (which could show today's variant state, not what was actually ordered) — but the *parsing heuristic itself* is fragile and worth a product/tech conversation before the rebuild reproduces it as-is.
- `groupItemsByCategory` in the order-detail page appears to be dead/no-op code for the current variant-naming convention (expects `variantName` to start with `"nk-"`) — confirm with PM/eng whether this is safe to drop in the rebuild or whether some historical orders still rely on it.
- The manual order-creation flow and customer self-checkout share the exact same `placeOrder()` engine and the exact same auto-routing (`assignOrderToGovernorate`) — parity between "what a customer can do at checkout" and "what an admin can do on their behalf" should be treated as intentional and preserved, not two independently-evolving flows.
- Order deletion doesn't exist anywhere in this surface — orders are immutable-by-identity once created; only status (including CANCELLED) and content (items/account/notes) can change.
