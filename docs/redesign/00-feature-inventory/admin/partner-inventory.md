# Admin — Partner Inventory

Route(s): `app/(admin)/admin/partner-inventory`
Key files: `components/dashboard/{empty-state,kpi-card,page-header,pagination,panel-card,search-input,table-scroll}.tsx`, `lib/admin/variant-sort.ts` (`sortVariants`), `lib/format-en-numbers.ts`, `hooks/use-toast.ts`
API: `GET /api/admin/partners?partnerType=AGENT|DISTRIBUTOR&limit=200` (partner picker), `GET /api/admin/partner-inventory?partnerId=...` (table data), `POST /api/admin/partner-inventory` (single-variant stock write)
Models: `Prisma.Product`, `Prisma.ProductVariant`, `Prisma.PartnerInventory` (unique on `partnerId_variantId`), `Prisma.InventoryLedger` (audit trail, `reason: "MANUAL_ADJUSTMENT"` for edits made here)

## Business requirements
- **Goal/KPI**: gives admin/ops staff a single screen to inspect and directly correct any partner's real stock numbers — this is the "fix a partner's inventory by hand" tool, used when a partner's self-reported stock drifts from reality (miscounts, damaged goods, manual reconciliation after a physical audit).
- **Trust/credibility signal**: every manual edit here writes an `InventoryLedger` row (reason `MANUAL_ADJUSTMENT`, default note "Admin dashboard stock edit", both available/reserved deltas recorded) — this is the audit trail that lets ops answer "who changed this partner's stock, and by how much, and when." That audit trail must survive the redesign unchanged; it's the only accountability mechanism for a screen that otherwise lets admins silently overwrite a partner's numbers.
- **Friction point**: nothing loads until an admin explicitly picks a partner from a dropdown — for an admin managing many partners, there's no "all partners, all low-stock variants" cross-partner view; each partner must be inspected one at a time.
- **Operational risk**: the server actively **prevents** setting `stockAvailable` below the existing `stockReserved` (both in a same-request `stockReserved` bump and against the *existing* reserved value) — this guards against orders holding reservations that would suddenly exceed physical stock. This constraint is business-critical and must be preserved exactly, not relaxed for UX convenience in a redesign.
- **Modern-look rationale**: this is a dense operational data-grid screen (like the partner/admin orders tables) — a redesign can improve information density and inline-edit affordance, but the inline "type a number, dirty-state highlight, click save per row" pattern is intentionally low-friction for bulk corrections and should be preserved as a pattern (see below), not replaced with a modal-per-edit flow that would slow down bulk reconciliation work.

## Elements & behavior
- [ ] **Permission gate** — `requireAdmin()` on both GET and POST; 401 if not logged in, 403 if logged in but not admin-role. No client-side role branching beyond that — if the API 403s, the fetch's `catch`/failure path shows a toast ("فشل تحميل الشركاء" / "فشل تحميل المخزون") rather than a dedicated forbidden screen.
- [ ] **Partner picker** — single `<Select>`, populated by combining two separate API calls (`partnerType=AGENT` and `partnerType=DISTRIBUTOR`, each capped at 200), so it lists both agents and distributors together (agents' rows use partnerType AGENT even though the reports/analytics screen restricts *that* screen to AGENT-only — there is no such restriction here). Each option shows `name · وكيل|موزع · governorate`. Failing to load the partner list shows a toast, leaving the select empty (not disabled — the user just sees no options).
- [ ] **Refresh button** — appears only once a partner is selected; re-runs the same `load()` query with current filters/pagination; spins the icon while `fetching`.
- [ ] **Empty pre-selection state** — before any partner is chosen, the entire results area is replaced by a single `EmptyState` ("اختر شريكاً للبدء") — no KPI cards, no table, no filters are rendered at all until `partnerId` is set.
- [ ] **4 KPI cards** (shown only once a partner is selected, computed **client-side** from the currently-loaded page of rows, not server-aggregated — see Edge cases): إجمالي المتاح (sum of `stockAvailable` across loaded variants), إجمالي المحجوز (sum of `stockReserved`), مخزون منخفض (count where `sellable <= 3`), يحتاج إعداد (count where `inventoryId === null`, i.e. no `PartnerInventory` row exists yet for that variant/partner pair).
- [ ] **Filter toolbar**: "مخزون منخفض فقط" toggle button (client sends `lowOnly=true`, server-side filters products where *any* variant has `sellable <= 3`), "يحتاج إعداد فقط" toggle (server-side filters products where *any* variant has no inventory row), and a 400ms-debounced search box (server-side `q`, matches product name/slug/category name OR variant SKU/name/color name, case-insensitive `contains`). Changing any filter or the partner resets pagination to page 0.
- [ ] **Table** columns: المنتج (product name) / المتغير (variant name + colorName, with a small color swatch dot rendered from `colorHex` if present, plus a "يحتاج إعداد" outline badge inline when `inventoryId === null`) / SKU (monospace) / المتاح (an editable `<Input>` — see inline-edit below) / المحجوز (`stockReserved`, read-only display) / قابل للبيع (`sellable = max(0, available - reserved)`, shown as a badge — default-styled if >0, destructive if 0) / آخر تحديث (`updatedAt` formatted via `formatDateEn`, or "لم يسجل" if no inventory row exists yet) / حفظ (per-row save button).
- [ ] **Inline stock edit** — typing in a row's المتاح input tracks a local `drafts` map keyed by variant id; the input gets a gold-tinted background/border while its draft value differs from the server value ("dirty"); the row's save button is disabled unless dirty (or already saving) and shows a spinner while that specific row is saving (`savingVariantId`, so only one row's button spins at a time even though nothing technically blocks firing multiple saves).
- [ ] **Save validation** (client-side, before the request): the typed value must parse as a non-negative integer, else a toast blocks the request ("أدخل رقم مخزون صحيح"); it must also be `>= stockReserved` for that variant, else a toast blocks it with the exact reserved number interpolated into the message. **Server-side re-validates independently** (`stockAvailable >= 0`, and `nextReserved <= stockAvailable` inside the same DB transaction) and returns `apiBadRequest` if violated — this is correctly double-guarded (client convenience + server authority) and both layers should be preserved.
- [ ] **On successful save**: server upserts the `PartnerInventory` row, writes one `InventoryLedger` entry with the exact available/reserved deltas, returns the updated row; client patches just that one variant's fields in local state (no full table refetch), clears that variant's draft, and shows a "تم حفظ المخزون" success toast. On failure: an error toast with the server's message, or a generic fallback if the error wasn't JSON/had no message.
- [ ] **Pagination** — `PaginationBar` only renders when `total > 0`; page size is adjustable (`onPageSizeChange`), default 20, server-side `limit`/`offset` (limit capped 1-100 server-side regardless of what the client requests).

## States
- [x] Empty state (no partner selected) — dedicated `EmptyState` component, described above; distinct from...
- [x] Empty state (partner selected, zero results) — a second `EmptyState` instance inside the table panel, copy varies: "لا توجد نتائج مطابقة" if a search/filter is active, else "لا توجد منتجات" (bare, for a partner with literally no product catalog match — note this checks *active* products store-wide, not partner-specific existence, so this really means "no active products in the whole catalog matched," which for a normal store should rarely if ever be empty).
- [x] Loading state — a full-width centered spinner + "جاري التحميل" replaces the table entirely on `loading` (true only on partner-change/first load, not on subsequent filter-only refetches — those instead dim the existing table via `opacity-70` under `fetching`, keeping stale rows visible while new data loads, matching the pattern from `partner/reports`).
- [ ] Error state — like `partner/reports`, there is **no dedicated visual error state**: failed partner-list fetch shows a toast only; failed inventory fetch shows a toast AND stops loading, which leaves whatever was previously rendered (or nothing, on first load) — no persistent inline error banner or retry affordance beyond the manual "تحديث" refresh button.
- [ ] Permission-restricted state — not distinguished from a generic fetch failure toast; a non-admin hitting the API gets 401/403 surfaced only as the same generic toast copy as any other failure.

## Edge cases
- [ ] **KPI cards are computed from the current page only, not the full filtered result set.** With pagination active (`total` > `pageSize`), "إجمالي المتاح"/"إجمالي المحجوز"/"مخزون منخفض"/"يحتاج إعداد" only reflect the ~20 rows currently loaded, not the partner's true totals across all pages — this reads as a real total to an admin but silently isn't one. Flag this prominently for the rebuild: either make the KPIs a genuine server-aggregated total, or relabel them (e.g. "in this page") to avoid misleading ops staff.
- [ ] A variant with `inventoryId === null` (no `PartnerInventory` row yet) still renders as a fully editable row with `stockAvailable` defaulting to display `0` — saving on it correctly `create`s rather than `update`s the row (verified server-side via `upsert`), but the UI gives no visual distinction beyond the "يحتاج إعداد" badge that this is a *creation*, not an *edit*.
- [ ] Typing a non-integer, decimal, or negative number into the stock input is only caught on save-click (client-side parse via `Number.parseInt`), not on keystroke — a user can type garbage and only find out it's invalid when they click حفظ.
- [ ] If `stockReserved` somehow exceeds the newly typed `stockAvailable` at save time (e.g., a concurrent order reserved more stock between page-load and this save), the server transaction detects it and returns a bad-request rather than silently clamping — confirm the toast surfaces the *current* reserved number, not a stale client-side one, since the check re-reads `existing.stockReserved` from the DB inside the transaction at save time, not from the client's last-known value.
- [ ] Switching partners while a save is in-flight for the previous partner — `savingVariantId` is not reset on partner change, so verify there's no stale "row is saving" spinner bleeding into the new partner's table if a variant id collision or stale-closure race occurs (the `saveStock` closure captures `partnerId` at call time via the outer scope, so a very fast partner-switch mid-save could plausibly post to the *new* `partnerId` state value — worth a deliberate check, not just an assumption, before the rebuild treats this as safe).
- [ ] `q` search is capped server-side at 100 characters silently; no client-side max-length enforcement or feedback if a longer string is pasted in.

## Notes
- This is functionally the admin-side counterpart to a partner adjusting their own stock (if such a partner-facing edit screen exists elsewhere — cross-check `partner/products` and `partner/restock-requests` inventories for overlap/duplication of this capability from the partner's own side).
- The `InventoryLedger` write here uses a fixed reason `MANUAL_ADJUSTMENT` — if the rebuild's admin surface adds more granular reasons (e.g. distinguishing "physical recount" vs "damage" vs "correction"), that's a new feature decision, not implied by current behavior.
- Distinct from `admin/products` (catalog/content management — name, images, pricing) — this screen only ever touches `PartnerInventory` stock numbers, never product content.
